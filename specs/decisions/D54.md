# D54 — `generator` attempts to regenerate itself; fails, stays hand-written

## Context

With `llm-endpoint` twice self-hosted (`D51`, `D52`/`D53`), the next,
deeper step the self-hosting mechanism was built for: using the real
`generator` to regenerate itself from its own current spec, through
the now-fixed `llm-endpoint`.

## Decision

**Attempted, reviewed, and rejected — the discipline worked.** The call
itself succeeded (no `model_call_error`, no timeout) and produced a
five-file `generator` package (`__init__.py`, `data.py`, `prompt.py`,
`generator.py`, `cli.py`), well-architected and citing the right
requirement IDs throughout — including, independently, the same
`_as_dict()` adapter this corpus's own hand-written `generator.py`
already carries, for the identical reason (`ModelResponse.md` fixes a
JSON shape, not a Python type).

It fails to import. `generator.py`'s own line `from cache_manager.data
import CacheKey, CachedResult, Miss` assumes `cache-manager` is a
package with a `.data` submodule; the real, currently-installed
`cache-manager` (`D48`) is a single flat module with those names
defined directly in it. Confirmed by hand: `import generator` raises
`ModuleNotFoundError: No module named 'cache_manager.data';
'cache_manager' is not a package` before any acceptance criterion could
even be attempted.

**Kept the existing, already-verified `gen/generator/generator.py` in
place.** Per this corpus's own standing rule — a generation attempt is
swapped in because it passes verification, not because a call merely
completed (`D51`'s own framing) — an import failure is as decisive a
rejection as a failed `AC-GEN-*` assertion would have been; there was
no reason to run the full suite against code that cannot be imported at
all.

## Consequences

**A real, generalizable risk, not specific to this one attempt:**
`SpecBundle.dependency_interfaces` (`R-ASSEMBLE-002`) gives a
dependency's public data/behavioral contract — function signatures,
type fields — but says nothing about how that contract is organized
into files or submodules, because no component's `interface/` spec in
this corpus has ever needed to say so (nothing before this attempt
depended on another *generated* component's internal layout; every
real dependency edge so far was hand-written code a human laid out
once). A generating model can use the right *names* correctly while
guessing wrong about *import paths* — invisible until two independently
generated components actually need to interoperate, which this attempt
is the first real instance of. Not resolved here: doing so would mean
either standardizing a module-layout convention corpus-wide (a real
design decision, not a one-line fix) or having `spec-bundle-assembler`
expose a dependency's actual public import path explicitly. Flagged in
`notes/backlog.md` for whoever attempts the next cross-component
self-regeneration.

This also means: of the two components generated purely through this
corpus's own self-hosting mechanism so far (`llm-endpoint` x2),
`generator` is the first instance of the mechanism correctly rejecting
its own output. That is the intended behavior, not a shortfall — the
same provenance-hit-vs-blind-trust discipline this corpus has applied
consistently now also holds up against a tool regenerating itself from
its own current spec.

Linter: 0 failures once this file exists. No code changed as a result
of this decision — `gen/generator/generator.py` is unchanged from `D53`.
