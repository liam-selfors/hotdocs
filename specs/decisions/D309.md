# D309 — An agentic generation mode in a sandbox that fails closed

## Context

Single-shot generation writes a whole component in one reply and never
sees it run. A model that can import its own module, run its own tests
and revise catches most of what the verifier would otherwise reject, at
the cost of running model-written code on the user's machine.

## Decision

A new component, `agentic-generator`, gives the model the tool loop of
`llm-tool-endpoint` over a sandbox directory holding only its spec
bundle, rendered by `generator`'s own `render_prompt_sections`, plus
`work/` for the candidate and `scratch/` for its own tests
(`specs/architecture/agent-sandbox.md`). Code runs with a scrubbed
environment, resource limits and an OS sandbox denying network access,
writes outside the sandbox and reads of the repository: `sandbox-exec`
on macOS, checked in a spike; `bwrap` on Linux, specified but not yet
run on Linux. With no OS sandbox it fails closed: the two code-running
tools are refused unless the caller opts in with
`allow_unisolated_exec`, and the isolation level is recorded in the
result.

`work/` is the candidate; `scratch/` is discarded. The result is a
`GenerationResult` with `mode` `"agentic"`, the transcript's hash, its
turn and tool-call counts and the isolation. An agentic result is
never cached.

A canary criterion plants a token in `acceptance/` and `verification/`
and checks that no tool result ever carries it.

## Consequences

The model never sees acceptance criteria or tests, exactly as in
single-shot mode. Agentic generation is opt-in (`--mode=agentic`).
