# D20 — Cross-step literal substitution: bare bound identifiers only, resolved at compile time; anything else is a compile error

## Context

Resolved `criterion-compiler`'s open question on the exact boundary of
"literal data" (`R-COMPILE-007`) for cross-step fixture references —
`step-phrase-grammar.md`'s own text already asserted an answer in prose
("still a literal substitution, not evaluation") without ever stating
the precise rule.

## Decision

A bare identifier occupying an entire leaf/scalar position within the
literal syntax — whether the whole argument value or nested inside a
larger literal (`{"owner": user_id}`) — is literal substitution if it
exactly matches a fixture bound by an earlier `Given` step in the same
criterion. Resolved at **compile time** by simple lookup against that
fixture's already-known literal value — never by runtime computation,
which is the property that keeps this safe under R-COMPILE-007's
anti-code-execution intent. An unresolved bare identifier is a compile
error, never silently treated as a literal string.

Anything beyond a bare identifier in a leaf position (an operator, a
field/index access, concatenation, a function-like call) crosses into
expression evaluation and is a compile error.

**Deliberately excluded, not overlooked:** field/index access into an
already-bound literal (`foo.id`) would actually be no less safe
(compile-time-only, pure structural traversal), but is excluded anyway
because allowing it means extending the step-phrase grammar table
itself (D2-level governance weight) for a need nothing in this corpus
has raised yet.

See `specs/components/criterion-compiler/requirements/R-COMPILE-007.md`
and `specs/architecture/step-phrase-grammar.md` for the current,
authoritative rule.
