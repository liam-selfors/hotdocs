# D141 — AC-PACKET-003 invited faking impact-analyzer directly; compliance_flags sub-shape was still undocumented

## Context

Fourth `review-packet-builder` retry (after `D140`'s three fixes): 7 of
11 pass, 4 fail, for two distinct causes — one test-authoring artifact
traced to a genuine spec wording defect, and one still-undocumented
sub-shape causing the same kind of per-round guessing `D140` already
fixed once for `residual_risk`.

**`AC-PACKET-003`** failed, but not because of the candidate — its own
`regenerated_components = sorted(components.keys())` is exactly
correct per `R-PACKET-011`'s architecture. The generated test's own
Gherkin ("Given a blast radius of two components **from
impact-analyzer**") directly invited test-authoring to write a fake
`gen/impact-analyzer/impact_analyzer.py` and expect it to be called —
but `R-PACKET-011` is explicit that this component never calls
`impact-analyzer` directly, only `provenance-tracker.check_readiness`.
The resulting test wrote two fakes that were never wired together: its
fake `provenance_tracker.check_readiness` builds `components` keyed by
the raw `changed_ids` passed in (`{"R-FOO-001": {...}}`), never calling
the fake `impact-analyzer` at all, then asserted
`regenerated_components == ["comp-alpha", "comp-beta"]` — the blast-
radius ids only the *unused* fake would have produced. Exactly the
"spec wording describes a dependency the architecture doesn't have"
shape `D133`/`D139` already found twice; `R-PACKET-003`'s own prose
("the blast radius `impact-analyzer` computed") has the same defect at
its root, inviting a reader to picture `impact-analyzer` as directly
in scope.

**`AC-PACKET-005`/`009`/`011`** failed for a cause distinct from the
"forgot to filter when clean" plain bug `D140` already flagged as
expected to self-correct: it did *not* self-correct, and a closer look
shows why — `compliance_flags.license_scan`/`secret_scan`'s own entry
shape is still undocumented. Four rounds, four different guesses:
round 1/2's candidates wrapped each component's scan result as
`{"component_id", "result"}` and filtered on an ad hoc guess at which
key meant "clean" (`findings`/`flags`/`clean`/`violations`, whichever
a given test's fake happened to use); round 4's test (`AC-PACKET-011`)
expected the *opposite* — the raw per-component scan value
concatenated with no wrapper at all, a bare list of flag entries.
Nothing anywhere states what field name signals "this component's scan
is clean" — but `license-scanner`'s own `LicenseScanResult.blocked`
and `secret-scanner`'s own `SecretScanResult.flagged`
(`interface/data/*.md` in each component's own spec) already are
exactly that signal, verbatim, flowing through `provenance-tracker`
unmodified. Nothing in `review-packet-builder`'s own bundle ever named
them, so every round invented a new ad hoc key instead of using the
one that already exists.

## Decision

`AC-PACKET-003`'s Gherkin rewritten to frame the scenario entirely
through `provenance-tracker`'s own `components` map — never mentioning
`impact-analyzer`. `R-PACKET-003` reworded to cite
`provenance-tracker`'s `VerifyReport.components` (`D90`) as the source,
not `impact-analyzer` directly — the exact dependency boundary
`R-PACKET-011` already establishes, now stated consistently in both
places.

`R-PACKET-005`/`ReviewPacket.md` amended: `compliance_flags.license_scan`
is `{"component_id", "result"}` entries for exactly the components
whose `license_scan.blocked` (matching `license-scanner`'s own
`LicenseScanResult.blocked`) is `true`; `secret_scan` is the same
keyed on `.flagged` (`secret-scanner`'s own `SecretScanResult.flagged`)
— never a heuristic guess across several possible key names.

`review-packet-builder` is retried next against both fixes.
