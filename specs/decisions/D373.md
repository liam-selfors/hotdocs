# D373 — Criteria can drive a component's page in a headless browser

## Context

A javascript asset's logic is pure exports over JSON, run in Node by
`asset_runner`; its `init(document)`, which wires a page to them, is
never called by a test (`specs/architecture/asset-kind-javascript.md`).
Nothing in `hotdocs` loads a page, acts on it or reads what it shows.

The dmt test drive showed what that leaves out. Its documentation site
is one self-contained page, `target/docs/index.html`, written by
`comp-docs-site` and inlining three assets: `page.js` (docs-site),
`viewer.js` (erd-viewer-render) and `explorer.js` (erd-viewer-interact).
`comp-docs-server` serves it on loopback. Every pure export passed its
criteria, yet whether the tabs switch, the dictionary filter hides
rows, a click on an entity opens its panel, the three scripts agree on
the events they exchange (`dmt:select`, `dmt:viewer`, `dmt:export`)
or the page throws on load was checked by no criterion, and the agent
driving the test drive had no tool to look. The three `init` functions,
about 140 lines, and the composition of three components' assets on
one page were unverified.

## Decision

1. A **test driver** is a program a component's tests use to exercise
   what it produces. It has a definition and an adapter, is looked up,
   provisioned and recorded in provenance the way an asset kind's
   environment is, reaches test authors only, and has no strength check
   of its own (`specs/architecture/test-drivers.md`).
2. A component or capability declares the drivers its criteria use in
   frontmatter, `drivers: [browser]`, and gets each declared driver's
   pytest fixture in every criterion, baseline, mutant and scenario run.
3. The built-in driver `browser` is Playwright for Python with its
   Chromium, provisioned into `.hotdocs/env/driver-browser/` on first
   use, behind a fixed fixture API: open a local file or loopback URL,
   find elements by role, label, text, test id or CSS, act on them, and
   read text, values, attributes, console errors, blocked requests,
   dialogs and downloads (`specs/architecture/test-driver-browser.md`).
   Tests never import Playwright, so its API can change without
   re-authoring a test.
4. The browser may reach only the opened file's directory and loopback
   hosts; every other request is refused and listed, so "works offline"
   is a criterion like any other.
5. Screenshots are taken for people reading a failure, never asserted
   on. Judging how a page looks is left to a later decision.

## Consequences

A component whose page matters declares `drivers: [browser]` and states
in its criteria what a user does and sees; the page's wiring and the
composition of its assets are verified on every generation, and a
mutant in any Python or javascript that the page reaches is killed by
the same tests. In dmt, `comp-docs-site` and the `P-ERD-EXPLORATION`
scenarios would declare it; the viewer components keep testing their
pure exports through `asset_runner`.

Each browser test starts its own Chromium, about a second, and each
mutant runs the suite again; a component with many browser tests and
many mutation sites verifies noticeably slower. A project that never
declares the driver never installs it. Provisioning downloads
Playwright and Chromium (about 150 MB) once per project.

A Chromium or Playwright update changes `versions`, which is
`environment differs` (`D345`): the committed code is re-verified, not
regenerated.

Regenerated: `spec-linter` (`R-LINT-036`, an undefined driver),
`spec-bundle-assembler` (driver guidance, `R-ASSEMBLE-017`),
`test-probe` (driver stubs, `R-PROBE-009`), `run-environment`
(provisioning and the plugin, `R-RUNENV-003`, `D383`),
`verifier-orchestrator` (`VerificationReport.drivers`),
`capability-scenario-verifier` (`prepare_capability` and drivers in its
key), `provenance-writer` and `provenance-checker` (`drivers` in the
manifest and key), the new `comp-driver-browser`, and the components
their code hashes reach. `docs-site-renderer` and
`provenance-tracker-ui` declare the driver and gain one browser
criterion each (`AC-DOCS-012`, `AC-UI-012`), so the corpus exercises
it. The Playwright pin is `1.64.1`.
