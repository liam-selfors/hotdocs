# D300 — A `spec-reviewer` that checks each criterion from its test author's view

## Context

`D298` states the criterion-visibility rule, but nothing checks it. In
the tool's own regeneration each violation was found only after a
generation and a failed verification, then diagnosed by hand. A user
running `hotdocs` outside a supervised session has neither the time nor
the context for that diagnosis. Separately, `spec-linter`'s glossary
conflict rule (`R-LINT-015`) takes a model-backed judge that no caller
ever passed, so the rule always reported `skipped`.

## Decision

A new component, `spec-reviewer`, exposed as `hotdocs spec check`:

- **Deterministic layer.** For each criterion it builds the exact
  `CriterionBundle` the test author will receive and reports every
  backticked token in the criterion that appears nowhere in the bundle's
  other text. The step-grammar, reply-format and lint-rule gaps of the
  regeneration were all of this kind.
- **Model layer.** One model call per criterion, given only that
  criterion's bundle, asks the model as that test's author whether it
  can write the test, and what it would have to guess or what behavior
  goes unstated, with proposed spec text for each.
- **Judged lint.** With a model, it passes `glossary_judge` to `lint`, so
  `R-LINT-015` runs. `hotdocs lint` itself stays model-free: the linter
  is at the root of the bundle-hash tree.
- **Proposals.** `--write-proposals` writes them under
  `.hotdocs/proposals/`. Nothing is applied automatically; the command is
  advisory and gates nothing unless `--strict` is given.

## Consequences

The component is new and has no dependents, so landing it forces no
regeneration. `spec-completeness-assistant` can use it in place of its
generator previews.
