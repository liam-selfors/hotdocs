# D42 — Settle `component_doc_words` on `component_size`; promote it to the shared Query surface

## Context

Flagged while implementing `D41`'s `R-LINT-027`: `corpus-graph-builder`'s
`R-GRAPH-009` already specified a `component_size` DuckDB view computing
the same `component_doc_words` count `spec-linter`'s `rule_size_caps`
computes independently in Python — two parsers for one number, exactly
the "two independently-written implementations that could silently
disagree" risk `R-LINT-020`'s own rationale already warns about for
reference resolution, just never checked for this dimension.

Investigating before trusting either implementation surfaced three real
bugs, none of them hypothetical:

1. `component_size`'s SQL used `read_text(path, filename:=true)` —
   `filename:=true` is a `read_json`/`read_csv` keyword; `read_text`
   already returns a `filename` column unconditionally and errors on
   the unknown parameter. The view as specified would never have run.
2. `trim()` without an explicit character set strips spaces only, not
   newlines — every file's trailing `\n` survived, producing a
   spurious empty token after splitting that inflated every
   component's count by exactly one word.
3. `read_text` also returns full raw file bytes, including a
   `component.md`'s YAML frontmatter block — a count Python's parser
   correctly excludes, inflating affected components by their
   frontmatter's own word count (and *only* that, since every other
   unit file is frontmatter-free by `R-LINT-016`).

All three were found by actually running the SQL against DuckDB, not by
reading it — the view had never been executed before, since nothing in
the real bootstrap calls into DuckDB for any rule, a fact this decision
also surfaces but does not resolve (see `notes/backlog.md`).

## Decision

**Fixed the SQL** (bugs 1–3 above) and verified it byte-for-byte against
`spec-linter`'s existing Python computation across all 21 real
components — zero mismatches once corrected.

**Settled on the DuckDB implementation as the single source of truth.**
`gen/spec-linter/spec_linter.py`'s `rule_size_caps` now queries the
corrected `component_size` view directly (`_component_doc_words`, a
real `duckdb` call) instead of summing `len(doc.body.split())` over an
in-memory file list. This is this bootstrap's first real external
dependency — a deliberate, documented exception to its original
zero-dependency design goal (`verification/spec-linter/BOOTSTRAP.md`),
justified by the same reasoning `R-LINT-020`'s own graph-query adoption
already established: running one shared definition for real costs a
dependency; maintaining two independently-written algorithms costs
correctness, silently, the moment they drift.

**Promoted `component_size` into `graph-query-engine.md`'s shared
"Query surface"** — the sixth shared view, by the same rule that
already promoted `component_provenance`: a second real consumer
(`spec-linter`, alongside `corpus-graph-builder`'s own, still-unbuilt
use) is exactly the signal to stop letting it live as one component's
private definition. `R-GRAPH-009` no longer redefines the SQL inline;
it points at the shared view, same as it already does for `nodes`/
`edges`/`component_provenance`.

## Consequences

There is now exactly one definition of `component_doc_words` in this
corpus, actually executing, verified correct. The numbers themselves
are unchanged (every component's `component_doc_words` is identical to
before the switch) — this was a correctness and duplication fix, not a
behavior change.

`spec-linter` ends this decision at 3986/4000 `component_doc_words` —
tightened again during this same work (the changelog entries for
`D40`–`D42` were consolidated into one bullet to make room), the same
margin-management this component has now needed at every single
addition since `D40`. The architecture's own tracked tension
(`pipeline-decomposition.md`'s note, `notes/component-sizing-playbook.md`)
keeps proving itself out in practice rather than staying hypothetical.

A related, larger finding surfaced but deliberately not fixed here —
`R-LINT-003`/`004`/`008`/`009`/`018`'s bootstrap implementation never
actually queries `nodes`/`edges` despite `R-LINT-020`/`021` claiming
exactly that, and the `nodes`/`edges` view SQL itself likely carries the
same `read_text(filename:=true)` bug just fixed here, unverified because
nothing has ever actually run it — tracked in `notes/backlog.md` for a
dedicated follow-up, not folded into this one.

Linter: 0 failures, 17 warnings. Pytest: 42 passed (no new cases — the
existing suite already locks in `component_doc_words`'s exact values,
so the switch only needed to reproduce them, not add new assertions).
See `R-LINT-012`, `R-GRAPH-009`, and `graph-query-engine.md`'s "Query
surface" for the current, authoritative text.
