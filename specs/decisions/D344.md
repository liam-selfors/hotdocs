# D344 — Python is an asset kind with its own adapter and an optional project environment

## Context

`D343` made every non-Python kind a definition plus an adapter the
pipeline loads by path, but left `python` native: its layout,
environment and mutation rules are spread across `generator`,
`verifier-orchestrator` and `specs/architecture/mutation-runs.md`, and a
project's Python code is verified in `hotdocs`' own environment, so it
can import a package the project never declared (`D340`). One contract
for every kind was the intended end state, and the pipeline regenerates
in this wave anyway, so doing it now costs no extra regeneration.

## Decision

- `python` is a kind like any other: a definition,
  `specs/architecture/asset-kind-python.md`, and an adapter,
  `comp-kind-python`. Every component has one implicit `python` asset,
  its code directory; it is never declared.
- The adapter carries Python's mutation sites, exactly the rules
  `mutation-runs.md` stated, which `verifier-orchestrator` now takes
  from `strength_sites`/`apply_site`; a parity criterion pins them.
- `provision` gives Python an environment of the project's own when
  the project commits `environments/python/requirements.lock`, and
  reports the `interpreter` every pytest run of the component uses.
  Without a lock nothing changes: the `hotdocs` corpus and existing
  projects run in `hotdocs`' environment.
- `generator` checks a reply's `.py` files with the adapter's
  `layout_errors`, a syntax check, as `malformed_layout`.
- Provenance records the `python` asset first, so the Python version
  and the lock's hash are part of every key.
- `surface-checker`'s import and dependency checks stay the surface
  gate for `python`; its guidance texts are empty, the generator prompt
  and `test-author` rules still carry Python's conventions.

## Consequences

Every manifest misses once for the new `assets` entry, inside the
regeneration that is running anyway, and again whenever
`comp-kind-python` or its definition changes, as with a verifier version;
the Python version is recorded as major.minor so a patch release does
not. `comp-kind-python` is generated first, by the pipeline that
predates it, and every later generation finds the committed adapter;
its parity and calibration criteria are what keep a wrong adapter from
landing, since it is verified with its own mutation sites.

`verifier-orchestrator`, `test-probe`, `surface-checker` and
`capability-scenario-verifier` run a component's code under the
interpreter `provision` reports; the agentic sandbox's `check_import`
and `run_scratch_tests` still use `hotdocs`' own, a known gap for
projects with a lock. Two changes ride along: an environment failure of
any kind now fails `compiled` criteria as well as generated tests, since
both run the code; and `AC-GEN-024` reports an unknown kind as
`environment`, as `R-GEN-021` already said. Moving Python's guidance into its
definition, and comparing its surface with `library.md`, are later
changes to `comp-kind-python` and `surface-checker` alone.
