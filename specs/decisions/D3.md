# D3 — No automatic retry within a merge; retry_feedback is an optional, developer-supplied signal

## Context

An earlier design ran an automatic best-of-k retry loop, feeding a failed attempt's per-requirement pass/fail projection back into a second, automatic `generator` call. That coupled "retry happens" to "retry is silent," which turned out to be the wrong bundling.

## Decision

`merge-orchestrator` calls `generator` **exactly once** per cache-miss, non-sealed component per merge attempt. A failure — `model_call_error` or a failing verification — blocks that component immediately; nothing calls `generator` again within the same merge. Recovery is re-running the merge: every already-passed component is a cache hit, only the failed one gets a fresh attempt. An optional `retry_feedback` (a bare `R-id` list, never Gherkin text or rationale) may be supplied by whoever invokes the next merge attempt, passed through verbatim to `generator`'s one call for the named component — `merge-orchestrator` never derives this itself from any stored attempt history; the decision to retry informed, and what to say, stays entirely with the human or script initiating the call. `merge-tracker` offers a read-only convenience surfacing a component's last per-requirement failures, so a developer knows what they could pass — it never feeds the pipeline itself.

## Consequences

A transient miss costs one conscious re-run, not a mandatory spec investigation; a genuine spec gap gets a deliberate pause before the next attempt, informed by the full per-attempt record.
