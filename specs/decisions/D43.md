# D43 — Fix `nodes`/`edges`/`component_docs`/`component_context`

## Context

`D42` fixed `component_size` by actually running its SQL against real
DuckDB rather than trusting the written text, and flagged (in
`notes/backlog.md`) that the same `read_text(path, filename:=true)`
bug almost certainly affected the corpus's other shared views, since
nothing had ever executed any of them either. This decision follows
through on that flag.

## Decision

Installed the `yaml` and `duckpgq` community extensions (both load
fine in this environment) and ran every remaining Query Surface view
against the real corpus. Found and fixed two distinct bug classes:

**`read_text(path, filename:=true)`** — invalid, same as `D42`'s
finding. Present in four of `nodes`'s seven branches (guarantee,
requirement, acceptance, capability_scenario), two of `edges`'s six
branches (`covers` from `acceptance/` files and from capability
scenarios), and `component_docs`'s own `read_text` call.
`read_yaml_frontmatter` genuinely supports `filename:=true` — confirmed
by running it, not assumed — so those branches were already correct;
only `read_text` needed the parameter removed, since it already
returns `filename` unconditionally.

**Missing DOTALL flag in `component_context`** — a different bug,
found only once `nodes`/`edges`/`component_docs` were already fixed
and `component_context` could be tested at all. `regexp_extract(body,
'##\s*Purpose\s*\n(.*?)\n##', 1)` without the `'s'` flag doesn't match
across newlines, so a multi-line `Purpose` section — nearly every one
in the corpus — silently extracted to an empty string instead of
erroring. The equivalent Python (`spec_linter.py`'s `_extract_purpose`)
already passes `re.DOTALL`; this view's SQL had drifted from that
without anyone noticing, because nothing had ever run it to notice
with.

Every fixed view was verified against the real corpus, not just
against "does it run": `nodes`'s seven kind-counts and `edges`'s five
edge-type counts were each cross-checked against an independent
file-system/frontmatter count (exact match in every case),
`component_docs`'s row count matches the component count, and
`component_context` now returns real multi-line `Purpose` text instead
of empty strings.

## Consequences

All six Query Surface views (`nodes`, `edges`, `component_docs`,
`component_context`, `component_provenance`, `component_size`) are now
verified to actually run and produce correct results against this
corpus. This closes the first of the three gaps `D42` flagged.

The second gap remains open and deliberately unaddressed here:
`spec-linter`'s `R-LINT-003`/`004`/`008`/`009`/`018`/`020`/`021` still
describe themselves as "implemented as queries over `nodes`/`edges`"
while the real bootstrap code is plain Python that never calls
`duckdb`. Fixing the SQL text was a bounded, low-risk unit of work;
rewiring seven working, previously-tested rules to actually run SQL
instead is a materially larger and riskier undertaking — a deliberate
decision to treat as a separate follow-up rather than fold into this
one. See `notes/backlog.md`.

Linter: 0 failures, 17 warnings (unchanged — these are
architecture-document changes; `spec-linter` doesn't consume these
views yet, so nothing in the corpus's own lint behavior moved).
Pytest: 42 passed (unchanged). See `specs/architecture/
graph-query-engine.md`'s "Query surface" section for the current,
verified SQL.
