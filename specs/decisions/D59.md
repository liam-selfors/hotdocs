# D59 — 200 of 200 `kind: compiled` criteria reclassified to `generated-test`

## Context

Beginning real implementation work on `criterion-compiler` (the sealed
component that mechanically compiles `kind: compiled` criteria against
`specs/architecture/step-phrase-grammar.md`'s fixed step vocabulary)
surfaced something no prior decision had ever checked: whether the
corpus's existing `kind: compiled` criteria are actually *written* in
that grammar. They are not — not approximately, not mostly, not one of
them. A programmatic check against the grammar's six templates found 0
of 200 fully conformant (some partially match in isolation — notably
the `Then the <artifact> contains a <severity>-severity finding for
rule <rule-id>` template, which many `spec-linter` criteria's `Then`
clause happens to match verbatim — but every one of the 200 fails on
at least one `Given`/`When` step, which is written as ordinary prose).

In practice, this means `compiled`'s whole trust argument — the
strongest tier specifically *because* nothing agent-generated sits
between the criterion and the check (`criterion-compiler`'s own
`Purpose`) — has never actually applied to any shipped criterion.
Every `kind: compiled` criterion across every already-built component
(`cache-manager`, `corpus-graph-builder`, `generator`,
`graph-query-engine`, `llm-endpoint`, `spec-bundle-assembler`,
`spec-linter`) has in fact been verified the same way a `generated-test`
criterion is: a hand-written pytest function derived from its prose,
confirmed against `interface/`+`requirements/`, no mechanical
grammar-compilation step ever involved. This was never flagged before
now because `criterion-compiler` never existed to notice.

A narrower, related concern already existed in `verification/
spec-linter/BOOTSTRAP.md` — a worry that `AC-LINT-011` specifically
might be mis-assigned `compiled` when its underlying check needs
judgment, not structure, and should be `llm-judge`. That note is about
*semantic* fit for one criterion; this finding is about *syntactic*
fit for all 200, and is strictly broader — resolving it moves
`AC-LINT-011` off `compiled` too, but whether it specifically belongs
at `llm-judge` rather than `generated-test` remains that older note's
own open question, not resolved here.

## Decision

Reclassified all 200 `Kind: compiled` criteria, corpus-wide, to `Kind:
generated-test` — a mechanical, metadata-only correction matching how
every one of them has actually been verified since the day it was
written, not a change to any already-passing test's behavior.
`criterion-compiler` itself is unaffected: its own spec, the grammar,
and its path to a real implementation are all still correct and still
worth building — `constraints.md`'s own "characterization coverage"
clause already anticipated testing it against a hand-authored
reference fixture suite, not real corpus content, which is exactly how
its implementation now proceeds (`D60`, tracked separately). `Kind:
compiled` remains available and meaningful for any criterion written
from this point forward that is deliberately, literally authored in
the step-phrase grammar — this decision empties the category of
mislabeled stragglers, it does not retire it.

No lint rule depends on `Kind`'s specific value (only its presence,
`R-LINT-010`), so this edit trips no rule. Confirmed no already-written
verification suite for a built component asserts a specific `Kind`
value as part of its own test logic — the handful of literal `"Kind:
compiled"` strings found outside `criterion-compiler/`'s own fixtures
are synthetic test data exercising `spec-linter`'s generic
presence-only check, not assertions about real corpus content, and
were left unchanged.

## Consequences

Every already-shipped component's real trust posture is unchanged in
practice (the same hand-written tests still back the same behavior) —
only the label now tells the truth about which mechanism actually
backs each criterion. Any future component spec's acceptance criteria
MUST be checked against the real grammar before being written as
`compiled`, not assumed compliant by habit — the exact mistake this
decision corrects.

Linter: 0 failures. Pytest: all 96 tests across all seven built
components re-verified unchanged (this was a `specs/`-only edit, no
`gen/` or `verification/` code touched).
