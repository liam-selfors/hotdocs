# D140 — review-packet-builder's spec_diff base ref, changed_ids semantics, and residual_risk item shape were all undocumented

## Context

Third `review-packet-builder` retry (after `D139`'s two generator fixes
and the `AC-PACKET-008` rewrite): 5 of 11 still fail, for three distinct
causes — two real spec gaps and one plain candidate bug.

**`AC-PACKET-001`** — `spec_diff` came back empty. The candidate computed
it as `git diff HEAD -- specs` (working tree against `HEAD`), but the
generated test committed every change (clean working tree) and expected
the diff between the feature branch's tip and `main` instead. Nothing in
`R-PACKET-001` or `interface/library.md` ever said which ref `spec_diff`
is computed against — the identical, previously-unspecified gap
`R-IMPACT-010` already closed for `impact-analyzer`'s own "the prior
commit": the merge-base between `HEAD` and the repo's default branch,
never `HEAD~1` (meaningless past one commit) and never working-tree-vs-
`HEAD` (empty once everything is committed, which a real PR always is
by review time).

**`AC-PACKET-002`** failed too, for an unrelated reason: this generated
test's fixture has no git repository at all — it writes `R-FOO-002.md`
to disk and calls `build_review_packet(["R-FOO-002"], repo_root)`
directly, expecting `changed_requirements` to simply be the `R-id`-
shaped subset of its own `changed_ids` argument. The candidate instead
tried to rediscover changed requirements from a git diff of file paths
under `specs/`, found none (no repo), and returned `[]`. `changed_ids`'s
own semantics were never documented anywhere: is it an opaque hint
merely forwarded to `provenance-tracker.check_readiness` for blast-
radius purposes, or the caller's own already-known, authoritative list
of every id that changed, of which `changed_requirements` is a trivial
filter? The first real cold-generation attempt (`round 1`, undocumented
until now) happened to guess the latter and passed; this one guessed
the former and failed — a real interface-documentation gap, not a
candidate defect either time.

**`AC-PACKET-008`** failed for a third reason, this time a genuine
candidate bug: the candidate appended a bare string to `residual_risk`
(`"comp-foo: mutation_score 0.92 ..."`), but the generated test reads
`field(entry, "component_id")` on each entry, expecting a structured
record. `interface/data/ReviewPacket.md` only ever showed
`"residual_risk": []` — an empty example with no illustrative entry
shape — so every round has guessed a different one (round 1: `{"id",
"source", "warning"}`; this round's test: `{"component_id", ...}`;
this round's candidate: a bare string). Pinning down one concrete shape
removes the guesswork for every future round, same as `R-PACKET-008`'s
own worked example already does for the *content* of a residual-risk
finding.

`AC-PACKET-005`/`009`'s separate failures (compliance_flags not coming
back empty when clean) are a real, simple candidate bug against an
already-clear `AC-PACKET-005` Gherkin ("both fields explicitly empty,
not omitted") — no spec change needed; expected to self-correct on
retry via `retry_feedback`.

## Decision

`R-PACKET-001` amended: `spec_diff` MUST be computed as the diff
between the merge-base of `HEAD` and the repo's default branch, and
`HEAD`, over `specs/` — reusing `R-IMPACT-010`'s already-ratified
convention rather than inventing a second one.

`interface/library.md` amended: `changed_ids` is documented as the
caller's own authoritative list of every spec id that changed in this
PR (component ids, `R-id`s, `AC-id`s, capability ids) — never
independently rediscovered from git by this component.
`changed_requirements` (`R-PACKET-002`) is simply its `R-id`-shaped
subset.

`interface/data/ReviewPacket.md` amended: `residual_risk` entries are
objects with `component_id` and `message` fields, with a concrete
worked example replacing the bare empty-array placeholder.

`review-packet-builder` is retried next against all three.
