# D148 — a diff-status filter is incompatible with the empty-tree fallback; build_review_packet must tolerate no git repo at all

## Context

Twentieth `review-packet-builder` retry (after `D147`'s empty-tree
fallback and existed-at-base rule): a severe regression, only 3 of 12
passing. Two distinct causes, both self-inflicted by `D147`'s own
fixes interacting with pre-existing, previously-passing scenarios.

**Every criterion whose fixture never sets up a git repository at
all** (`AC-PACKET-002`/`003`/`004`/`005`/`006`/`008`, by design, since
`R-PACKET-002`/`library.md` already states those fields depend only
on `changed_ids` and `provenance-tracker`, never git) now fails with
`RuntimeError: git rev-parse HEAD failed: fatal: not a git
repository`. `build_review_packet` calls git unconditionally near its
own top, with no tolerance for `repo_root` not being a repository at
all — only `AC-PACKET-009`'s own new zero-*commits* scenario was ever
stated; a repo_root that is not a git repository at all (no `.git`
directory) is a stricter, distinct case nothing said to tolerate.

**`AC-PACKET-007`'s own genuine two-commit transition scenario**
(passing in every prior round) now fails too: the candidate's
`_exemption_changes` filters on `git diff --name-status`'s own
per-file status letter, requiring `M` (modified), before ever reading
`component.md`'s content at base vs `HEAD`. Against the empty tree —
`R-PACKET-001`'s own new fallback (`D147`), now the base for every
no-feature-branch scenario — every file in the repo shows status `A`
(added), never `M`, so the status filter discards every real
transition before the content comparison ever runs. The two `D147`
fixes directly conflict: the fallback that was supposed to make
multi-commit, no-feature-branch history visible instead permanently
disabled the one piece of logic that reads it.

## Decision

`R-PACKET-009` extended: `build_review_packet` MUST tolerate
`repo_root` not being a git repository at all, not only one with zero
commits — treating every git call's result as empty on failure,
never letting it raise out of `build_review_packet`. Every field
depending only on `changed_ids`/`provenance-tracker` MUST still be
produced correctly regardless of `repo_root`'s own git state. New
`AC-PACKET-009` scenario for the no-repository case.

`R-PACKET-007` amended: a genuine `sealed` transition MUST be
detected by reading `component.md`'s own content at the base and at
`HEAD` directly (`git show <rev>:<path>`), **never** by filtering on
`git diff --name-status`'s own per-file status letter — the base is
sometimes the empty tree, against which every file shows `A`, never
`M`, which would otherwise silently and permanently disable
transition detection for exactly the scenario `R-PACKET-001`'s own
fallback exists to handle. Reading non-existence at the base as "not
sealed" is already the complete, correct signal on its own.

`review-packet-builder` is retried next.
