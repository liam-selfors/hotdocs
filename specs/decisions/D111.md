# D111 — provenance-tracker's check_readiness must resolve dependency modules relative to its own repo_root parameter

## Context

With test-author's Round 12 fixes (`D110`) landed, a fresh `provenance-tracker` generation attempt first hit an unrelated, one-off generation-variance bug (a candidate that wrote its own output files under a doubly-nested `provenance-tracker/provenance_tracker/` path instead of flat `provenance_tracker/`, breaking its own module resolution) — resolved by simply retrying generation with a different seed; not a spec gap, not reproduced on the next attempt.

The following attempt reached real functional results: 3 of 5 criteria passed (`AC-TRACK-004/007/008`), but `AC-TRACK-009`/`010` failed. Diagnosis traced every one of these failures to one root cause: `check_readiness`'s own dependency loader (`_load_gen_module`) resolves `_GEN_ROOT` from `Path(__file__).resolve().parent.parent` — this component's own on-disk location — never from the `repo_root` argument `check_readiness(repo_root, ...)` was actually called with, and caches by module name alone in `sys.modules` with no `repo_root` key. A real generated test for `AC-TRACK-009` wrote a fake `impact-analyzer` under an isolated `repo_root` (exactly the convention `test-author`'s own `R-AUTHOR-010` documents and requires for writing a fake), but `check_readiness` loaded the sandbox's real `impact-analyzer` instead, defeating the fixture's isolation entirely and silently returning results computed against the wrong corpus. `AC-TRACK-010`'s three failures are the same bug cascading: a faked `provenance-checker`/`capability-scenario-verifier` never actually used, with the real ones — given a tmp_path with no real provenance data — returning misses/skips instead of the fake's intended results.

This exact file-relative pattern was found, by inspection, to already exist in `impact-analyzer`'s own dependency loader, predating this session — the candidate most likely copied it as a plausible precedent to follow. Fixing `impact-analyzer` itself is out of scope here (an already-stable, previously-verified component, the same category of deferred risk as `verifier-orchestrator`'s own tracked gap, `D106`) and is recorded as a separate, tracked known limitation rather than fixed in this decision.

## Decision

New `R-TRACK-011`: `check_readiness` MUST resolve every dependency module relative to its own `repo_root` parameter — `<repo_root>/gen/<dependency-slug>/<module_name>.py` (flat) or `<repo_root>/gen/<dependency-slug>/<module_name>/__init__.py` (package) — never relative to this component's own file location, and never trusting a `sys.modules` cache entry keyed by module name alone across two different `repo_root` calls in the same process. New `AC-TRACK-011`, exercising two separate `repo_root`s with distinctive fakes in the same process to prove isolation.

`provenance-tracker` is retried against this amendment.

**Self-correction before this even landed**: the first retry hit a NEW `ImportError` on `AC-TRACK-010` — the package-shape path above was originally written (in both this requirement and, found by the same check, `test-author`'s own `R-AUTHOR-010`) as `<dependency-slug>/__init__.py`, missing the `<module_name>/` level the real, established convention requires. The candidate implemented the spec literally, including that mistake. Both requirements are corrected in place to the full, correct path shown above — a spec-authoring error on this session's own part, not a model or candidate defect.
