# D95 — AttemptRecord.md states VerificationReport.requirement_results' real dict-of-string shape explicitly

## Context

`provenance-tracker`'s first real cold-generation (bootstrapping it for real, the first of the seven still-unbuilt components) passed four of its five `AC-TRACK-*` criteria but failed `AC-TRACK-008`: `last_requirement_failures` returned `[]` where `['R-FOO-002']` was expected. The candidate's `_failing_requirement_ids` assumes `requirement_results` is a list of per-requirement objects, each with an id field and a pass/fail field — a reasonable-looking guess that does not match the real shape `verifier-orchestrator`'s own `VerificationReport.requirement_results` actually uses: a flat dict keyed by `R-id`, mapping directly to the string `"pass"` or `"fail"` (confirmed against a real `VerificationReport` produced by a real `verify()` call during this same bootstrap).

This is a genuine spec gap, not just an implementation defect: `provenance-tracker` does not (and should not, per `D93`'s one-directional dependency graph) depend on `verifier-orchestrator` for behavior, so its own assembled spec bundle never included `verifier-orchestrator`'s `interface/data/VerificationReport.md` for the generator to read. `AttemptRecord.md` documented `verification` only as an opaque `{ "...": "a VerificationReport" }` placeholder — correct as far as it goes (this component genuinely doesn't need the rest of that type), but it left the one sub-field `last_requirement_failures` actually has to introspect completely unspecified, with nothing authoritative for a cold-generation attempt to read.

## Decision

`AttemptRecord.md`'s `verification` field documentation states `requirement_results`' concrete shape explicitly, inline, as the one piece of `VerificationReport`'s content this component actually reads — a flat JSON object mapping each `R-id` string directly to `"pass"` or `"fail"`, nothing nested. `R-TRACK-008` states the same shape directly rather than only citing `AttemptRecord.md` by reference. No new dependency edge is added — `provenance-tracker` still never depends on `verifier-orchestrator`; this is a narrower, local statement of the one field shape this component needs, the same kind of targeted inline documentation `D49` already used for `impact-analyzer`'s own `depends_on_guarantees` shape once a real candidate guessed wrong about something undocumented in any `SpecBundle`.

`provenance-tracker` is regenerated with `--retry-feedback=R-TRACK-008` against the corrected spec.
