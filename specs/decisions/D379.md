# D379 — A miss caused only by dependency code re-verifies before regenerating

## Context

A component's `spec_bundle_hash` covers every file under each direct
dependency's code directory (`R-ASSEMBLE-007`), so any regeneration of a
dependency makes every dependent miss and regenerate too, even when
nothing the dependent was generated from has changed: its own spec,
its dependencies' interfaces and the glossary are the same. The
`D371` and `D372` waves regenerated eight components whose specs were
untouched, each costing a model call and a seed gate. Splitting a large
component into smaller ones, which the spec review of 2026-11-26
recommends for the verifier, would multiply such misses.

`D345` already handles the analogous case for environments: a miss
only in asset versions re-verifies the committed code first and
regenerates only if that fails.

## Decision

1. `spec-bundle-assembler` reports, beside the unchanged
   `spec_bundle_hash`, `spec_bundle_parts`: a `dependency_code` hash
   over the dependencies' code files and a `spec` hash over every other
   input (`R-ASSEMBLE-007`).
2. `provenance-checker`'s key carries the parts, and the manifest
   records them (`provenance-writer`, `R-PROV-023`). A
   `spec_bundle_hash` miss whose only difference is `dependency_code`,
   every gate version and the assets value matching, has `reason`
   `dependency code differs` (`R-PROVCHECK-011`).
3. `component-gate-runner` treats `dependency code differs` as it treats
   `environment differs` (`R-GATE-011`): it verifies the committed code
   against the new dependency code, runs both scans, and on a pass
   writes provenance with the current hash and parts, calling no model.
   Any other outcome regenerates as before.

## Consequences

A dependency's regeneration costs its dependents one verification each
rather than a generation, unless a criterion fails against the new
code. The mutation bar still applies, so a dependent whose tests no
longer kill mutants is regenerated.

`spec_bundle_hash` is unchanged, so every existing manifest still hits.
A manifest written before this decision has no `spec_bundle_parts` and
gets no re-verification on its next dependency-code miss; the manifest
written then carries them.

Regenerated: `spec-bundle-assembler`, `provenance-checker`,
`provenance-writer`, `component-gate-runner`, and the components their
code hashes reach.
