# D340 — Components declare asset kinds; projects may define their own

## Context

Every component is generated, verified and mutation-tested as a Python
package. Several already carry another language or format as string
constants that no gate treats as what it is: JavaScript and CSS in
`docs-site-renderer` and `provenance-tracker-ui`, DuckDB SQL in
`graph-query-engine` and `spec-linter`, a macOS sandbox profile in
`agentic-generator`, model prompts in five components, and JSON and TOML
shapes stated only as prose (`notes/asset-kinds-survey.md`). `D335`
reached the JavaScript only by mutating it inside Python strings. A
project built with `hotdocs` will need other languages, documents and
data files, and has no way to say so.

## Decision

- `specs/architecture/asset-kinds.md` defines an asset kind by seven
  parts: layout, environment, surface, running criteria, strength check,
  test author guidance and generator guidance. `python` is the first
  kind and today's behaviour.
- A component declares its assets in frontmatter; with none declared it
  has one `python` asset, so nothing changes until a component opts in.
- Every kind declares the environment its assets need, the `python`
  kind included, and a project provisions only the environments of the
  kinds it declares, under `.hotdocs/env/<kind>/` from committed
  lockfiles. `hotdocs` runs in its own Python environment, which no
  project asset uses. An environment that cannot be provisioned fails
  the criteria that need it, with `failure_origin` `"environment"`; it
  never skips them. Provenance records each asset's environment versions
  and lockfile hash.
- A project defines its own kind with a definition document and an
  adapter component, `comp-kind-<kind>`, which `hotdocs` generates and
  verifies like any other; components using the kind depend on it.
- `agent-skills/hotdocs-asset-kind/` gives an agent the procedure for
  defining a kind reliably, starting from the strength check.
- The first kind after `python` is `javascript`, for
  `docs-site-renderer` and `provenance-tracker-ui`. It is built after
  `refine-authoring-agentic` lands, because it changes the generator's
  layout rules, the verifier's mutation sites, the surface checker and
  the test author's guidance, which that branch reworks.

## Consequences

Nothing regenerates now: the contract document is implemented by no
component yet. Each kind adopted later is its own decision and
regenerates the components that declare it plus the pipeline components
it changes.
Today a project's Python components are verified in `hotdocs`' own
environment, so they can import packages the project never declared;
the `python` kind's environment closes that gap when it is adopted.
