# D139 — generator's prompt also needs a universal dual-access rule; review-packet-builder's own AC-PACKET-008 was unsatisfiable

## Context

Second `review-packet-builder` retry (after `D138`'s fix): `AC-PACKET-001`
now passes, but 7 of 11 still fail, for two distinct, precisely
diagnosed causes.

**Six criteria** (`003`, `004`, `006`, `009`, `010`, `011`) all failed
with `regenerated_components`/`verification_results`/
`provenance_hit_status` coming back empty, despite each one's fake
`provenance_tracker.check_readiness` clearly returning a populated
`components` dict. Diagnosed directly: the candidate reads
`dict(getattr(report, "components", {}) or {})` — bare attribute
access on `report` itself — but every one of these six generated
tests' fakes returns a plain `dict` for `check_readiness`'s result (the
real, installed `check_readiness` returns a `VerifyReport` dataclass,
but nothing says a fake may not legitimately return a dict instead,
per this corpus's established duck-typing convention). The candidate
correctly used dual dict-or-attribute access (`_get`) for every field
*nested inside* a `components[id]` entry, but not for `report`'s own
top-level `components`/`capabilities` fields — the exact same
inconsistent, partial application of a pattern the model already knows
that `D112` found in `provenance-tracker`'s own generated tests. This
is the second time a candidate has gotten this specific shape of bug
wrong — `provenance-tracker`'s own `R-TRACK-012` (`D121`) closed it
for a candidate reading its *dependencies'* return values; this is now
a review-packet-builder candidate making the identical mistake reading
*its* dependency's (`provenance-tracker`'s) return value. Two
independent components, same bug shape — exactly the "recurring
defect, not one component's spec gap" signal `D138` acted on minutes
earlier for the `repo_root`-relative-loading class.

**`AC-PACKET-008`** failed for an unrelated, spec-level reason: its own
Gherkin requires "a component whose `component_doc_words` is within 5%
of the hard-fail threshold" to appear in `residual_risk` — but
`component_doc_words` is `spec-linter`'s own metric
(`R-LINT-012`), never a field of `provenance-tracker`'s `VerifyReport`,
`ProvenanceCheckResult`, `verification_report`, `license_scan`, or
`secret_scan` at any level. `R-PACKET-011`'s own architecture is
explicit that `review-packet-builder` reads *only* from
`provenance-tracker`'s `check_readiness` and depends on no other
component (`depends_on: [comp-provenance-tracker]` alone, `D90`) — so
this criterion demanded data the component's own declared architecture
can never supply. This was `R-PACKET-008`'s own prose
("e.g. a size-cap warning nearing its hard-fail threshold") taken
over-literally into a concrete acceptance criterion without checking
whether `VerifyReport` actually carries any such signal — the same
"spec describes behavior the stated architecture can't deliver" shape
`D133` found in `decision-drift-detector`'s first attempt. A real
signal that *is* available this way: `mutation_score` below `1.0`
while a criterion's own `overall` still reads `"pass"` — present
directly in `verification_report`, non-blocking, and worth a human's
attention, same spirit as the doc-words example without requiring a
dependency this component deliberately doesn't have.

## Decision

New `R-GEN-019`: the prompt MUST always instruct every candidate,
regardless of `depends_on`, that any value read from a dependency call
— including the dependency function's own top-level return value, not
only values nested within it — MUST use dual dict-or-attribute access,
never a bare `.attr` access alone. Cross-cutting scaffolding like
`R-GEN-018`, landed the same way (hand-edited, permanent exception).
New `AC-GEN-020`. `PROMPT_VERSION` → `v7`, `GATE_VERSION` →
`generator@1.4.0`.

`R-PACKET-008`'s example and `AC-PACKET-008`'s Gherkin are both amended
to a `mutation_score`-below-`1.0`-despite-passing scenario, achievable
entirely through `provenance-tracker`. `review-packet-builder` is
retried next against both fixes.
