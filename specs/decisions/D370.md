# D370 — test-author keeps no cache; a faulty test is authored afresh

## Context

Issue #23. A generated test for `comp-docs-site`'s `AC-DOCS-004` had a
logic bug: it passed `test-probe`, then failed against a correct
implementation. Each of three attempts reported the criterion `fail`
with `failure_origin` `"implementation"` and the same message.

The loop's repeated-failure rule (`R-LOOP-007`, `test-reuse.md`) did
fire: after the second attempt it deleted the test file so the third
would author it again. But `test-author` checked `cache-manager` before
any model call (`R-AUTHOR-004`), found the entry the first authoring
stored under the same key, and wrote the same faulty test back. The
same restore defeats `test-reuse.md`'s other two re-author paths, a
cached test failing its probe (`R-VERIFY-019`, `D307`) and a test
failing alone in the mutation sandbox, and a person deleting a test by
hand. There was no way out.

A component test's reuse is already the committed file and its
`D341` header: a test is reused while its header is current, and its
spec text changes both the header and the cache key. So the cache hit
only when a test was missing although its inputs had not changed,
which is exactly when a caller had deleted it as faulty. The one real
use was capability scenarios: `R-SCENARIO-003` (`D68`) dispatched them
to `test-author` every run and relied on the cache to make an unchanged
scenario cheap, although their tests are committed too, under
`verification/capabilities/<P-id>/generated-test/`.

## Decision

1. **`test-author` keeps no cache** (`R-AUTHOR-030`). It neither reads
   nor writes `cache-manager`, drops it from `depends_on`, and every
   result's `cache_hit` is `false`. A test a caller deleted is always
   authored afresh, so each re-author rule does what it says.
   `GATE_VERSION` stays `generated_test@3.0.0`: no existing test is
   made invalid, and raising it would change every component's
   provenance key, in every project.
2. **A capability scenario reuses its committed test** (`R-SCENARIO-007`).
   The callable `run_capability_gates` builds returns the committed
   file without calling `test-author` when its first line is the
   `D341` header for the scenario's criterion bundle (`testing` `""`),
   and authors it otherwise. The scenario verifier's `GATE_VERSION`
   is unchanged: neither its execution nor its key changes.
3. **`hotdocs generate <comp> --reauthor=<AC-id>,...`** (`R-GATE-012`).
   On a provenance miss, before anything else runs, the named tests are
   deleted so that verification authors them afresh. An id that is not
   one of the component's `generated-test` criteria is a usage error.
   On a hit nothing is deleted. The gate runner's CLI text moves to
   `specs/architecture/generate-cli.md` to keep the component under the
   word cap.

`specs/architecture/test-reuse.md` is unchanged: its rules were right,
and editing it would regenerate `spec-bundle-assembler` and its
dependents.

## Consequences

- With the issue's test, the third attempt now authors `AC-DOCS-004`
  afresh; `--reauthor=AC-DOCS-004` does the same from the first attempt.
- A re-authored test costs one model call, as it always should have.
  A scenario test is authored only when its header is stale or the file
  is missing, as before, but now from the committed file, not the
  local cache, so a fresh clone needs no model call for it.
- A faulty scenario test still has no automatic re-author rule: a
  failing scenario is not attributed to its test or the system. Deleting
  the committed file now re-authors it; a rule is in
  `notes/backlog.md`.
- Regenerates `test-author` and its dependents (`tools/cascade_plan.py
  comp-test-author`, twelve components); `capability-scenario-verifier`
  and `component-gate-runner` are among them.
