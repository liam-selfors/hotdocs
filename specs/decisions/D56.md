# D56 — Three real bugs found re-attempting generator's self-regeneration

## Context

`D55` closed the import-path gap behind `D54`'s failure. Re-attempting
`generator`'s self-regeneration with `dependency_usage` in place (per
`D55`'s own "Consequences" — the real test, done separately) surfaced
three further bugs, none of them a repeat of `D54`'s failure class, each
found by actually running real code against the real repo rather than
trusting a successful-looking parse.

**1. Self-referential delimiter collision.** `generator` is the one
component in this corpus whose own generated source legitimately needs
to contain a literal instance of its own file-transfer delimiter,
since that delimiter is itself part of what `generator.py` implements
and documents. The first real retry produced a model response that
correctly reproduced a worked example of the fixed
`-----BEGIN FILE: <path>-----`/`-----END FILE-----` delimiter inside
its own regenerated `_SYSTEM_PROMPT` string literal — and the old
non-greedy parsing regex matched that inner, illustrative end-marker
first, truncating the real file well before its actual end (41 lines
captured instead of the real file's full length). No other component's
generation could ever hit this, since no other component's own source
needs to contain this exact literal text.

**2. Degenerate empty-files caching.** Inspecting `.hotdocs/cache/`
before retrying (specifically to avoid a predictable cache-hit replay
of the broken truncated result) found that `generate()` had been
writing every non-`model_call_error` response to cache unconditionally
— including a response that parsed to zero files, an empty/no-error/
no-refused result that violates `GenerationResult.md`'s own "exactly
one of files (non-empty)/model_call_error/refused populated" contract.
This had already silently poisoned the cache twice this session: once
for an `llm-endpoint` retry that returned `files: []`, once for the
truncated `generator` attempt above.

**3. Undocumented cache-manager payload schema.** A second retry (with
the nonce fix in place) produced a complete, non-truncated 448-line
file that correctly used `cache-manager`'s real flat
`CacheKey`/`CachedResult`/`Miss` imports — directly confirming `D55`'s
fix works. Running it for real raised
`cache_manager.SchemaValidationError: payload for gate type 'generator'
is missing required key(s): ['component_id', 'model']`.
`cache-manager`'s own `_REQUIRED_PAYLOAD_KEYS` table (real, enforced,
defined since `D50`) was never documented in any spec file —
`CachedResult.md`/`R-CACHE-007.md` only ever asserted generically that
gate-type-specific validation happens, without enumerating what any
gate type's schema actually requires. A real caller, writing correctly
against every *documented* part of this component's contract, had no
way to know this beyond reading `cache_manager.py`'s own source.

## Decision

Fix all three at the layer where each bug actually lives — never by
hand-patching a generated candidate (`SPEC_GUIDELINES.md` §8):

1. `generator.py`: a fresh `uuid.uuid4().hex` nonce per `generate()`
   call, embedded in both the system prompt's BEGIN/END FILE markers
   and the per-call-compiled parsing regex (`re.escape(nonce)`). The
   model is told to copy it verbatim, and — specifically for this one
   component — told to describe the delimiter format in prose rather
   than reproduce the literal token sequence if it needs to document
   this format inside its own generated code. `PROMPT_VERSION` bumped
   `v2` → `v3` (a substantive prompt-text change, `R-GEN-003`).
2. `generator.py`: `cache_manager.put()` now only runs when
   `_parse_files()` returned at least one file. `GATE_VERSION` bumped
   `generator@1.0.0` → `generator@1.1.0` — gate_version is part of the
   cache key (`R-CACHE-005`), so this orphans both pre-existing
   poisoned entries without any manual cache deletion.
3. `R-CACHE-007.md`: documented all six gate types' exact required
   payload keys directly in spec, transcribed from `cache_manager.py`'s
   own `_REQUIRED_PAYLOAD_KEYS`, with an explicit note that this is a
   shallow key-presence check, not a full schema validator — closing
   this gap the same way `D55` closed the import-path gap.

## Consequences

A third retry of `generator`'s self-regeneration, with both the nonce
fix and the now-documented cache-manager schema in place, is the real
test of whether this closes the loop completely — done separately, not
assumed here, and swapped into `gen/generator/generator.py` only if it
then passes full, independent verification against `generator`'s own
real `AC-GEN-*` acceptance criteria, exactly as both successful
`llm-endpoint` self-hosting swaps (`D51`, `D53`) were.

Three bugs found in one retry sequence, none a repeat of any prior
one, is itself a signal worth naming plainly: self-hosted regeneration
of the tool that does the regenerating keeps finding real gaps that
only exist *because* this is the one component recursive enough to
expose them — not evidence the methodology is unsound, but evidence
that "verify fully before swapping, never assume a completed call is a
correct one" is still the load-bearing discipline here, same as `D54`.
