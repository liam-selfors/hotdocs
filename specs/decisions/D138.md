# D138 — generator's universal prompt must forbid bare import as a dependency-loader's primary strategy

## Context

First real cold-generation attempt for `review-packet-builder`: 10 of 11
criteria failed. Diagnosed directly against `AC-PACKET-001`'s failure —
`_load_provenance_tracker()` tried `import provenance_tracker` (a bare,
unqualified import) as its *first* strategy, falling back to a
`repo_root`-relative file load only if that bare import raised
`ImportError`. Inside the real test run, `provenance-tracker` is already
on `sys.path` (one of this component's own transitive dependencies,
loaded once per pytest process), so the bare import always succeeds and
always returns that one process-wide module — never the fake the
generated test wrote under its own isolated `repo_root`/`tmp_path`. The
real `check_readiness` then ran for real against the wrong `repo_root`
and crashed trying to locate `provenance-checker` under a directory that
never had it, which is why most of the other ten criteria failed too:
every one of them drives `build_review_packet` through this same loader.

This is the identical defect class closed three times already this
session, once per affected component — `R-TRACK-011` (`D111`,
`provenance-tracker`), `R-VERIFY-013` (`verifier-orchestrator`), and
`R-DRIFT-004` (`D134`, `decision-drift-detector`) — each restating, after
the fact, that a runtime dependency loader must resolve strictly from the
`repo_root` parameter it was actually called with, never from
`Path(__file__)`, and never by trusting a `sys.modules` entry that might
already be cached from a different `repo_root`'s call earlier in the
same process. A fourth independent component just reinvented the same
mistake in a new shape — the bare `import <module>` statement is a
*third* way to hit the identical `sys.modules`-staleness failure mode
(`__file__`-relative path and bare-name `sys.modules` lookup being the
other two), simply never named explicitly before now because no prior
candidate had tried it. Four occurrences across four unrelated
components is no longer "this component's spec was under-specified" —
it is generator's own universal prompt that is under-specified: nothing
in `_SYSTEM_PROMPT` (`gen/generator/generator.py`) tells every candidate,
up front, that *any* dynamic dependency load — however it is attempted —
must be `repo_root`-relative. Restating this once more in
`review-packet-builder`'s own spec would only guarantee a fifth
component reinvents it next.

## Decision

New `R-GEN-018`: `_SYSTEM_PROMPT` MUST always include an instruction,
for every candidate generated regardless of that component's own
`depends_on`, that any dynamic runtime load of a dependency module
(whether by bare `import <module_name>`, by a `sys.modules` cache
lookup keyed on the bare module name, or by resolving a file path
relative to the candidate's own `__file__`) MUST instead resolve the
dependency strictly from the `repo_root` parameter the candidate's own
function was actually called with — `<repo_root>/gen/<dep-slug>/
<module_name>.py` (flat) or `<repo_root>/gen/<dep-slug>/<module_name>/
__init__.py` (package) — and MUST NOT trust a bare-named `sys.modules`
entry that a different `repo_root`'s earlier call in the same process
may have already populated. This is the same cross-cutting, always-
included category `R-GEN-015`'s output-layout instruction already
established — generator's own fixed scaffolding, not bundle content,
so outside `R-GEN-001`'s "constructed from exactly the bundle's fields"
boundary. New `AC-GEN-019`.

`generator` is hand-authored, permanent-exception infrastructure (per
`SPEC_GUIDELINES.md` §8) — `_SYSTEM_PROMPT` is edited directly rather
than cold-regenerated, mirroring how `R-GEN-014`/`D41` and
`R-GEN-015`/`D46` were each landed by hand before. `review-packet-
builder` is retried next against the amended prompt; no change is made
to its own spec, since the defect was never there.
