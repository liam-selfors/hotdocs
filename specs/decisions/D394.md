# D394 — A miss caused by a new hash formula or new gates re-verifies the committed code

## Context

Issue #30: a project of 46 components, every one ready, upgraded hotdocs
with no spec, code or dependency change, and every provenance check
missed. `D382` changed which `component.md` text `spec_bundle_hash`
covers, and `D383` moved the verifier to `verifier-orchestrator@4.0.0`,
so each manifest misses on the hash and on `gate_versions`. Both reasons
sent `hotdocs generate` to regenerate everything with fresh model calls,
risking regressions in code that already passed. The only re-record tool,
`tools/rerecord_provenance.py --rehash`, works on the `hotdocs` repository
alone.

## Decision

`provenance-checker` names two more misses whose committed code is
re-verified, not regenerated (`R-GATE-011`):

- `hash formula differs` (`R-PROVCHECK-012`): the hash misses but git
  shows none of the component's spec inputs changed since its manifest
  was committed. Without git, or with an uncommitted or modified
  manifest, it stays `spec_bundle_hash differs`, so it errs only toward
  regenerating.
- `gates differ` (`R-PROVCHECK-013`): only `gate_versions` entries other
  than `generator` differ. A stricter gate is run again on the committed
  code; a new generator still regenerates (`D313`).

`dependency code differs` (`R-PROVCHECK-011`) allows the same gate
differences. Re-verifying runs every criterion and both scans; code that
fails today's spec is regenerated as before.

## Consequences

After an upgrade, `hotdocs generate <component>` re-records each
component that passes without a model call (`QUICKSTART.md`). Regenerated:
`provenance-checker`, `component-gate-runner`; their dependents
re-verify (`D379`).
