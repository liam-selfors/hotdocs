# D132 — ProvenanceInputs must remain a real, importable dataclass, never only a duck-typed Any

Fifth real cold-generation attempt (after `D131`'s `R-PROV-016`
`_to_jsonable` fix): `mutation_score=1.0`, but 8 of 16 criteria failed,
all with the identical `AttributeError: module 'provenance_writer' has
no attribute 'ProvenanceInputs'`. Diagnosed directly: this round's
candidate correctly implements `R-PROV-014`'s dual dict-or-attribute
access throughout (`inputs: Any`, a `_field()` helper used
consistently) but, reasoning that duck-typing made a concrete class
unnecessary, dropped the `ProvenanceInputs` dataclass entirely — every
earlier round had defined it. Eight already-passing generated tests
construct one by name
(`provenance_writer.ProvenanceInputs(component_id=..., ...)`), matching
`interface/data/ProvenanceInputs.md`'s own documented type and this
corpus's universal (if previously unstated) convention: every other
component with a documented `interface/data/` type defines it as a
real dataclass in its own module (`cache-manager`'s `CachedResult`,
`license-scanner`'s `LicenseScanResult`, `secret-scanner`'s
`SecretScanResult`).

Dual access and a real, constructible class are not in tension:
`write_provenance`/`build_manifest` can and should accept either an
instance of the real class or an equivalent plain dict, exactly as
`R-PROV-014` already requires — the class's existence is about a
callers having a documented, importable name to construct against,
not about narrowing what the functions accept. New `R-PROV-017`
states this directly, citing the sibling components' own classes as
the established pattern. Retrying generation next.
