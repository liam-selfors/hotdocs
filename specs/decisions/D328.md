# D328 — Committed tests predating the criterion header are stamped once, guarded by git

## Context

`D320` made `verify` treat a cached generated test as stale unless its
first line is `# hotdocs-criterion: sha256:<hex>` of its criterion and
requirement text (`R-VERIFY-019`), and `D324` bumped the gate to
`verifier-orchestrator@2.2.0`, so every manifest missed once. Twelve
components whose specs did not change still held tests written before
the header existed. Re-recording their provenance (`D297`) runs `verify`
with no test author, so each such test counted as absent and every
criterion failed, though the tests are the ones their manifests had
already verified. Re-authoring them would have cost a model run per
criterion for no change in what is checked.

## Decision

`tools/stamp_criterion_headers.py` prepends the header to a committed,
headerless test only when git shows the test last committed no earlier
than its criterion file and its covered requirement file, so the test
was written against exactly the text the header names. Any other test
is left headerless and its criterion is authored afresh. The header's
hash comes from the real `spec-bundle-assembler`'s `CriterionBundle`,
as `verify` computes it. The tool is a one-time migration; tests
authored since `D320` carry the header already.

## Consequences

The twelve components re-record without a model call and keep the tests
that verified them. The stamp's claim is only as good as git history:
a criterion edited in the same commit as its test was regenerated
counts as current, which is the case that regeneration produces.
