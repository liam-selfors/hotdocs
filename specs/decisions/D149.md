# D149 — exemption_changes must scan the git diff's own paths, never filter against changed_ids

## Context

Twenty-second `review-packet-builder` retry (after `D148`'s two
fixes): 10 of 12 pass. `AC-PACKET-008`'s failure is unrelated test-
authoring noise (a malformed path literal baked into a fake's own
source, visible as literal embedded quote characters in the
`FileNotFoundError` — a one-off generation glitch, not investigated
further). `AC-PACKET-012`'s markdown scenario failed for a real
reason: its fixture's two real commits genuinely transition
`comp-everything-thing` from unsealed to sealed, but
`build_review_packet` is called with `changed_ids=["R-FOO-001"]` (an
`R-id`, matching this corpus's own convention that `changed_ids` is
whatever spec ids the caller's blast-radius computation named) — the
candidate's own `_compute_exemption_changes` filters its scan down to
`{c for c in changed_ids if c.startswith("comp-")}` first, which is
empty here, so `comp-everything-thing` is never even considered
despite the diff genuinely containing its sealed transition.

This over-applies the `changed_requirements`/`R-PACKET-002` pattern
("filter `changed_ids` down to its `R-id`-shaped subset") to a field
that doesn't work that way: `exemption_changes` must discover sealed/
override changes from the git diff's own file paths directly,
independent of which ids the caller happened to pass — a real
exemption on a component `changed_ids` never named would otherwise be
silently missed.

## Decision

`R-PACKET-007` amended: `sealed`/`pinned_overrides` are discovered
entirely from the diff's own file paths, never filtered against or
restricted to `changed_ids` — contrasted explicitly with
`R-PACKET-002`'s own, different, changed_ids-filtering rule, so a
future reader can tell the two apart by field rather than reapplying
one pattern to both. `review-packet-builder` is retried next.
