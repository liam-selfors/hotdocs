# D93 — hotdocs generate and hotdocs verify stay separate commands; only check-capability folds into verify

## Context

`D92` combined `hotdocs generate`, `hotdocs check-capability`, and `hotdocs verify` into one `hotdocs build` command, reasoning that `verify` already had to compute whether provenance was current and the only thing missing was acting on a miss. On reflection this went one step too far: a developer genuinely wants `generate` and `verify` as independently runnable commands — `generate` to deliberately produce or refresh a component's code and provenance, `verify` to confirm current state without necessarily triggering new generation. Only `check-capability` folding into `verify` was actually wanted — that merge rests on a different, narrower justification (`verify` already has to determine whether a capability's provenance is current to report on it, so acting on that determination costs nothing additional) that doesn't extend to component generation, which is a deliberate, potentially expensive, code-producing action a developer should trigger by name.

## Decision

`hotdocs generate <component-id> --model=... [--seed=...] [--retry-feedback=...]` returns as `component-gate-runner`'s own command, unchanged from its pre-`D92` shape (`D86`/`D91`): one component, check-then-generate-verify-scan-write-provenance, nothing else. It writes its own `AttemptRecord`s by calling `provenance-tracker`'s `write_attempt_record` again — the dependency cycle `D92` was solving for no longer exists, since `provenance-tracker` no longer calls back into `component-gate-runner` for anything.

`hotdocs verify [--changed=...] [--model=...] [--format=...]` keeps the asymmetry this component's own design already implies: for every component in scope, it only ever **checks** `provenance-checker` — read-only, no model calls, never triggers `component-gate-runner` — since generating new code is a deliberate action `generate` owns, not a side effect `verify` should spring as a surprise. For every intersecting capability, it **checks-then-runs** `capability-scenario-verifier`'s own gauntlet, same as `D92` already established — capability-scenario verification doesn't produce new source code, it only exercises what already exists, so `verify` triggering it costs nothing a developer wouldn't expect from a command named "verify." `--model` is required only when some capability in scope actually needs a fresh run; a scope that's already fully current never needs it.

`component-gate-runner` depends on `provenance-tracker` again (one direction only); `provenance-tracker` depends on `capability-scenario-verifier` and `provenance-checker`, never on `component-gate-runner`. `capability-scenario-verifier` keeps no standalone CLI (`D92` stands for that half) — `hotdocs verify` is the only way a developer reaches it.
