# D93 — The payoff: knowing what a decision touches before it is ratified

## Context

The user's last ask of the decisioning-structure initiative: it
should be easy to determine the impact of altering a decision before
it is ratified. Before `D92`, answering this would have meant a new,
separate mechanism — `decision_lineage` had no backward-traversal
shape, and nothing modeled `builds_on` at all yet. After `D92`, the
question is already a graph query: everything that transitively
points at a decision via `supersedes`/`builds_on` is exactly what
`edges` now exists to answer.

## Decision

New `find_decision_impact(repo_root, decision_id) ->
DecisionImpactReport` (`R-DRIFT-003`) on `decision-drift-detector`:
walks `edges` backward from `decision_id`, collecting every decision
whose `supersedes`/`builds_on` points at it transitively, plus every
live file citing it — deliberately unfiltered by staleness, since
"what would need review if I change this" is a different question
from `find_decision_drift`'s "what already looks stale." `decision_id`
need not resolve to a real file yet, so this works on a decision
still being drafted, directly serving the "before it is ratified"
requirement.

Also fixed, caught while touching this component for the first time
since `D92`: `R-DRIFT-001`, `library.md`, and `component.md`'s Scope
text were all written before that redesign and still pointed at
`decision_lineage` for the `supersedes` relationship, which now lives
in `edges` instead.

## Consequences

Closes the full loop the user asked for across `D86`–`D93`: a
glossary promotion criterion, real `supersedes`/`builds_on` relationships,
a temporal/graph query surface, a commit-ancestry staleness diagnostic,
and now the forward-looking impact query — the same underlying graph
model answering both "is this already stale" and "what would this
change affect" through two different traversal directions over the
same edges. This is the natural stopping point for the initiative as
scoped; the real build (an actual `generate()` call for `graph-query-
engine`'s and `decision-drift-detector`'s now-substantially-redesigned
code) remains queued behind the same exhausted API credits as every
other pending component this session.
