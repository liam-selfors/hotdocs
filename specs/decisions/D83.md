# D83 — Dependents must import criterion_compiler lazily, relative to repo_root

## Context

A real `generate()` call for `verifier-orchestrator` produced a candidate with a static top-level `import criterion_compiler` statement. It failed the moment its tests ran from a working directory that never added `pipeline/criterion-compiler/` (criterion-compiler's real, `sealed: true` location) to `sys.path` itself — nothing in this corpus's specs said how a dependent should locate a sealed, `pipeline/`-hosted module it depends on directly rather than through an injected callable. `capability-scenario-verifier`'s own real implementation had already independently arrived at the correct pattern (lazy import at call time, resolved relative to its own `repo_root` parameter, trying `pipeline/criterion-compiler` then `gen/criterion-compiler`) — its own code comment even claimed this was "the same way any other component in this corpus resolves a sibling component's module," which was not true: it was never promoted from that one implementation to a requirement anywhere.

## Decision

Backfilled as `R-COMPILE-014`: any component depending on `criterion_compiler` directly MUST resolve it lazily, at call time, relative to its own `repo_root` parameter — never a static top-level import, which only works by the accident of whatever process happened to run first and breaks across callers given different `repo_root` values in the same process (a real `repo_root` versus a test's isolated `tmp_path` copy, since a module already cached in `sys.modules` is never reloaded from a different location). The caller tries a plain `import criterion_compiler` first, then adds `repo_root / "pipeline" / "criterion-compiler"` and `repo_root / "gen" / "criterion-compiler"`, in that order, to `sys.path` before retrying.
