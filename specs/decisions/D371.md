# D371 — hotdocs verify scans the repository afresh for secrets

## Context

`secret-scanner`'s `scan(repo_root)` reads every file in the repository
and its allowlist. `component-gate-runner` runs it once per generation
and `provenance-writer` stores the result in that component's manifest.
On a provenance hit, `provenance-checker` returns the stored result
verbatim, and `provenance-tracker` treated a flagged one as that
component not being ready.

The provenance key covers only the component's spec bundle, never the
other files the scan read or the allowlist. In issue #25, a planted
test fixture in one component of a 46-component project was allowlisted
by a ratified decision after 33 others had been generated. `hotdocs
verify` reported all 33 as `secret_scan blocked`, citing a line that no
longer held the fixture, while a fresh scan was clean. Only regenerating
each of them would clear it, and `provenance-tracker-ui` and
`review-packet-builder` showed the same phantom flags.

`component-gate-runner`'s re-verification on an environment change
(`D345`, `R-GATE-011`) also refused a flagged scan and fell back to
regenerating, which cannot change a finding in another component's file.

## Decision

1. The whole-repository secret scan is a fact about the repository at
   one moment, never about one component
   (`specs/architecture/repository-secret-scan.md`).
2. `provenance-tracker`'s `check_readiness` calls `scan(repo_root)` once
   per call, when the scope holds a component and no
   `precondition_error`, and reports it as `VerifyReport.secret_scan`.
   A flagged scan, or one that raises, adds exactly one
   `not_ready_reasons` entry naming `secret_scan` and its findings. A
   component's stored `secret_scan` stays in `components` as recorded
   and is never read (`R-TRACK-016`). `comp-secret-scanner` joins its
   `depends_on`.
3. `provenance-tracker-ui` no longer reads a component's stored scan for
   its status. `review-packet-builder`'s `compliance_flags.secret_scan`
   holds at most one entry, for the repository scan, with
   `component_id` `null`.
4. `R-GATE-011` accepts a re-verification whatever the secret scan says.
   The scan is still recorded.

Manifests keep their `secret_scan` field and its meaning: the scan the
generation ran. Nothing else changes in what they record.

## Consequences

An allowlist change, or removing a planted secret, takes effect at the
next `hotdocs verify`, with no regeneration. A real secret is reported
once, with its file and line, instead of once per component.

`hotdocs verify` now runs a full secret scan. It is cached by the
content of every file, so an unchanged tree costs a cache lookup; a
cold scan of this repository takes about eight seconds. A configured
`VAR-COMPLIANCE-WEBHOOK-URL` can now be notified by `hotdocs verify`
too, the one network call its component half makes.

Regenerated: `provenance-tracker`, `component-gate-runner`,
`provenance-tracker-ui` and `review-packet-builder`. The
`P-MERGE-VISIBILITY` scenario is re-authored and re-run; its capability
file now states the secret-scanner stand-in its repository holds, since
a scenario's author sees interface files but not the architecture
documents they implement.
