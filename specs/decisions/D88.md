# D88 — Piece 3: making the supersede chain queryable

## Context

`D87` made `supersedes`/`status: deprecated` real for the first time,
with a mechanical consistency check (`R-LINT-029`). That check needs
somewhere to query the relationship from, and the user's actual ask —
"temporal insight into what decisions were in force at any given
time" — needs the same data plus each decision's own ratification
commit, joined together.

`graph-query-engine` already owns exactly this kind of shared query
surface (six views at the time: `nodes`, `edges`, `component_docs`,
`component_context`, `component_provenance`, `component_size`), each
one promoted there once a second real consumer needed it. Decision
records were not part of that graph at all — no `nodes` row, no
`edges` row — so this needed a genuinely new view, not a query against
existing ones.

## Decision

New `decision_lineage` view (`R-GQE-008`): `id`, `title`, `status`,
`last_ratified_commit`, `supersedes` — one row per
`specs/decisions/*.md`. Built via `read_text` + regex extraction,
deliberately not `read_yaml_frontmatter`'s struct auto-detection,
because `R-GQE-002`'s own documented lesson (`D44`) already found that
mechanism silently drops a column absent from every file in a glob at
once — true today of both `supersedes` (one real row) and
`last_ratified_commit` (absent on any non-ratified record, if one
exists).

Kept as its own dedicated view rather than extending `nodes`/`edges`:
neither existing view has an equivalent column for either new field,
and widening their shape risks every current consumer
(`impact-analyzer`, `spec-bundle-assembler`, `spec-linter`'s other
rules, `corpus-graph-builder`) for a fact only decision records need.
`R-LINT-029` now states explicitly it must query this view rather than
scan independently, mirroring `R-LINT-021`'s existing discipline for
traceability queries.

New real tests confirm the view surfaces the real `D31`/`D17`
supersession from `D87` correctly, and that an absent `supersedes`
reads as `NULL`, not an empty string — both against the current,
unfixed `gen/graph-query-engine` code, so they fail today as expected.

## Consequences

The query surface this enables — "what was the state of decision `X`
as of commit `Y`" — is now a straightforward join between this view
and ordinary git commit ordering, which stays outside
`graph-query-engine`'s own scope (it reads spec files, not git
plumbing) by design. Piece 4, the actual staleness diagnostic that
performs that join against a spec file's own last-modified commit, is
its own, separate decision — a new capability with no existing
component boundary it fits inside, tracked next.
