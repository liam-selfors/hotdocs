# D121 — check_readiness must use dual dict-or-attribute access when reading a dependency's own return value

## Context

With `D119`/`D120` landed, `verifier-orchestrator` finally passes real `dependency_interfaces` content to `test-author` for every bootstrap-driven criterion. The next `provenance-tracker` retry reused the same cached candidate (`provenance_tracker.py`'s own code was unchanged — the spec driving its generation hadn't changed), but test-authoring, now working from real dependency shapes for the first time, wrote fakes that finally matched `provenance-checker`'s and `impact-analyzer`'s real, documented return shapes exactly. This immediately crashed the real candidate: `check_readiness` reads a `provenance-checker` result via bare `result.hit` and each `impact-analyzer` `impacted` entry via bare `entry.component_id` — never tolerating a dict, despite this corpus's own duck-typing convention (`D94`) meaning any dependency may return either shape.

This bug was invisible in every earlier round because every earlier fake guessed the wrong shape for an unrelated reason first (wrong arity, bare list instead of an object) — this is the first time a fake has been accurate enough to let the candidate's own downstream code run at all. This confirms the whole `D119`/`D120` investigation was addressing a real, now fully resolved, root cause: test-authoring is now exercising this component's actual behavior for the first time, not just its ability to survive a wrong guess.

## Decision

New `R-TRACK-012`: `check_readiness` MUST read every field of a value a dependency returns using dual dict-or-attribute access. New `AC-TRACK-012`. `provenance-tracker` is regenerated against this amendment.
