# D372 — The license scan reads only a component's code and assets

## Context

`license-scanner` scores `gen/<component>/`'s content against the
reference corpus as the share of its 9-token windows that match
(`R-LICENSE-001`). It read every file under that directory: the
component's own `.provenance.json`, `.overrides.json` and `__pycache__`
bytecode among them. Those files add windows that match nothing, so the
score of the same code fell once a manifest existed or the code had been
imported.

Re-running `CS-COMPLIANCE-001` for `D371` showed it. A component whose
code copies a GPL corpus entry scored at or above the 0.70 block
threshold inside `hotdocs generate` and 0.13 when `hotdocs license-scan`
rescanned it after the manifest was written, so the rescan passed what
the gate had blocked. A regeneration scans with the previous manifest
still in place, so its recorded score was understated the same way.

## Decision

A component's content is the files under `gen/<component>/` except
those whose name starts with `.`, `.pyc` files, and everything under a
directory named `__pycache__` or starting with `.` (`R-LICENSE-012`).
The score and the cache key's `gate_inputs_hash` read the same files.

`license-scanner`'s `gate_version` is unchanged. It is part of every
component's provenance key, and changing it would make every manifest
miss, while a score only changes for a component whose recorded scan
read its own manifest.

## Consequences

A rescan and the gate agree, and writing provenance never changes a
score. A manifest recorded by a regeneration before this decision may
hold an understated `similarity_score`; `hotdocs license-scan
<component-id>` reports the true one.

Regenerated: `license-scanner` and, by its code hash, the eight
components that depend on it: `provenance-writer`, `provenance-checker`,
`provenance-tracker`, `component-gate-runner`, `corpus-graph-builder`,
`docs-site-renderer`, `provenance-tracker-ui` and
`review-packet-builder`.
