# D29 — provenance-checker decides whether a component's prior verification can be trusted, distinct from cache-manager's cache_hit

## Context

A cache hit only ever meant "a candidate was produced," never "a candidate was verified" — trusting it to skip verification undermined the methodology's own evidentiary chain.

## Decision

`provenance-checker` reads a component's committed `.provenance.json` and compares `spec_bundle_hash`/`gate_versions` against the current ones. A match is honored unconditionally for a component with no `llm-judge`-kind criterion; for one that has at least one, only when `VAR-TRUST-JUDGE-PROVENANCE` resolves `true` (default `true` — a governance-maturity choice a project may tighten later). A **sealed** component is never checked against it at all — its `spec_bundle_hash` reflects only its spec, never its hand-maintained real content, so a hit would never catch a direct edit. The field that records this is named `provenance_hit`, distinct from any per-gate `cache_hit` field.
