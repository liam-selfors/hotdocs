# D152 — sealed-transition detection must compare against the file's own first commit, never the PR diff-base

## Context

Thirty-first `review-packet-builder` retry (after `D151`'s three-
condition fix): 11 of 12 pass. The one remaining failure is a third
distinct shape of the same recurring sealed-detection defect — this
time a three-commit, no-feature-branch history: commit 1 adds
`comp-sealed-foo` unsealed, commit 2 seals it (a genuine transition),
commit 3 makes an unrelated change. `R-PACKET-001`'s own empty-tree
fallback (no feature branch) makes the PR diff-base the empty tree,
against which `comp-sealed-foo`'s `component.md` "doesn't exist" —
`D151`'s own three-condition fix correctly excludes it under that
rule (no base existence, no transition counted), but that silently
drops a transition that unambiguously happened, two commits back,
within this exact history. `D151`'s fix closed the false positive
(`D147`/`D151`'s own "born sealed" case) at the cost of reopening a
false negative for exactly the multi-commit case `D147`'s own empty-
tree fallback was introduced to handle in the first place.

Both failure modes trace to the same root choice: using
`R-PACKET-001`'s own PR diff-base as the comparison anchor for an
in-file field transition. That base answers "what counts as this PR"
for *rendering a diff* — a different question from "did this
specific file's own `sealed` field ever genuinely flip." The latter
has a comparison point that answers it directly and needs no
PR-diff-base concept at all: the file's own first commit reachable
from `HEAD`.

## Decision

`R-PACKET-007` corrected a third time: a `sealed` transition is
detected by comparing the file's content at **its own first commit**
in `HEAD`'s history (`git log --follow --format=%H -- <path>`, oldest
result) against its content at `HEAD` — never against
`R-PACKET-001`'s own PR diff-base at all. This sidesteps both earlier
failure modes at once, independent of commit count or feature-branch
topology. `gen/<component>/.overrides.json` keeps its original,
simpler rule (existence at `HEAD`, absence at the PR diff-base) since
an override has no in-file prior state to compare and a reviewer
specifically needs to see one newly introduced *in this PR*, not
merely at any point ever. `review-packet-builder` is retried next.
