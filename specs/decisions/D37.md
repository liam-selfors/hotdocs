# D37 — dependency_usage: a dependent sees its dependency's real, current usage surface

## Context

A real self-regeneration attempt for `generator` failed to import because it guessed wrong about a dependency's real module layout — nothing required a component to state how a dependent should actually import it. A static, hand-written alternative was considered and rejected (goes stale the moment a dependency's internal shape changes); so was feeding a dependent's real usage back into a dependency's own regeneration (reintroduces a cycle, lets accumulated calling patterns steer behavior instead of the dependency's own normative contract).

## Decision

`spec-bundle-assembler` derives a third field, `dependency_usage`, alongside `dependency_interfaces`/`dependency_context`: for each real dependency, its actual importable module path and the signature/docstring of each public top-level symbol its current `gen/` code defines — introspected directly, never from source text or `acceptance/`. Fail-to-empty for a dependency with no real code yet. Strictly one-directional: a dependency's own bundle never carries anything about how its dependents use it. Generation calls within one merge's blast radius must be sequenced so a component's `generator` call never starts before every `depends_on` target in that blast radius has completed its own.

## Consequences

A drift-check comparing dependents' real usage against a dependency's documented contract was discussed as a safer way to capture the same underlying goal the rejected feedback-loop idea reached for — deliberately not built, tracked as a deferred follow-up.
