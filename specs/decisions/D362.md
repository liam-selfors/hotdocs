# D362 — The dependency-name check reads code, never strings or comments

## Context

Issue #17. A component that loads its dependency by path, as every
component must, wrote

    spec = importlib.util.spec_from_file_location(
        "erd_layout", str(directory / "erd_layout.py"))

`surface-checker`'s dependency-name check (`R-SURF-002`) matched
`<alias>.<name>` over each file's text, and the dependency's module name
is always an alias, so the string `"erd_layout.py"` counted as a use of
an attribute `py`. Every attempt failed with `erd-layout has no py, which
the candidate uses`, and no model reply could fix it: the loader is
correct. The hand tool the check was ported from (`D311`) skipped the
names `py` and `md`; the port did not, and a skip list would still miss a
name in a comment or a docstring.

The same report's second fault, a traceback after the loop's last surface
failure, is `D359`'s.

## Decision

`R-SURF-002` collects uses from each file's syntax tree: the attribute
name of every attribute access on a bare name that is an alias. Text
inside a string literal or a comment is never a use. A file that does not
parse gives no names; the import check has already reported it.

How an alias is found is unchanged.

## Consequences

A loader that names its dependency's file passes the check.
`surface-checker` is regenerated, then `generation-loop` and
`component-gate-runner` without spec changes, since each holds the one
before it in its bundle. An expression inside an f-string is code and
still counts.
