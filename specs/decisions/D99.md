# D99 — a commit MUST confirm hotdocs verify is ready across the full blast radius, not just the one component just regenerated

## Context

`hotdocs generate` operates on exactly one component at a time, by design (`D86`/`D93`) — no component sequences a multi-component change on a developer's behalf, the same decentralization `D87` removed `merge-orchestrator` to achieve. That design leaves a real gap unaddressed: regenerating one component can change its public contract or behavior in a way a *downstream* dependent silently relied on, and nothing in the existing workflow actually requires anyone to check that before the change becomes committed, shareable state. `SPEC_GUIDELINES.md` §6 step 3 explicitly says of `hotdocs verify`, "nothing requires it to run before a commit" (`D87`), and `provenance-tracker`'s own `constraints.md` repeats the same posture — both written when `hotdocs verify`'s main job was confirming a single developer's own in-progress work, not standing as the one check that could catch a blast-radius-wide regression before it ships.

This isn't a hypothetical: bootstrapping the still-unbuilt components this session surfaced several real, previously-undiscovered cross-component bugs (`D83`-`D85`, `D59`-`D61`, `D95`-`D98`) purely *because* a component was exercised for real against its actual dependents for the first time. The same risk applies in reverse, on every future regeneration — a component's own `AC-*` criteria passing in isolation says nothing about whatever already depends on it.

## Decision

**Committing any regenerated component(s) MUST be preceded by a passing `hotdocs verify` run scoped to the full blast radius of every component actually changed** — `--changed=<id>...` naming each one, letting `impact-analyzer` compute the transitive blast radius the same way it always has, never hand-picked by the developer. A commit MUST NOT proceed while that run reports `ready: false`. This is still never an automated, programmatic gate (`D87` stands: no component enforces this itself, there is no CI/CD yet, `.hotdocs/` stays non-authoritative) — it is a stated workflow requirement a developer (or an agent acting as one) follows by discipline, the same posture every other un-automated rule in this corpus already has (e.g. `R-ASSEMBLE-011`'s dependency-ordering requirement for `hotdocs generate` itself).

`SPEC_GUIDELINES.md` §6 step 3's "nothing requires it to run before a commit" is narrowed: `hotdocs verify` itself still enforces nothing programmatically, but running it — over the correct, full blast radius — before committing is now a stated MUST, not optional good practice. Step 6 (Commit) states this precondition directly. `provenance-tracker`'s `constraints.md` "Never a gate input" bullet is narrowed the same way: never an *automated* gate, but now a documented precondition for the commit step specifically.

This governs the working methodology, not any single component's own requirements — no `R-id` changes, since no component's own behavior changes; only the stated development workflow does.
