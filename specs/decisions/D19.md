# D19 — `spec_bundle_hash` stays raw bytes, permanently; cache-hit-rate concern moves to a lint rule, not the hash function

## Context

Resolved `spec-bundle-assembler`'s open question: raw bytes vs. a
normalized form for `spec_bundle_hash`, raised over concern that
cosmetic diffs (e.g. trailing whitespace) could cause unnecessary
cache misses.

## Decision

Raw bytes, confirmed as the **permanent** answer, not provisional
pending cache-hit-rate data — the risk a normalized hash introduces
isn't something more data would resolve. These are Markdown files, and
Markdown is not whitespace-insensitive: two-or-more trailing spaces are
CommonMark's hard-line-break syntax; indentation is load-bearing inside
nested lists and code fences. The open question's own example
("trailing whitespace stripped") is exactly the kind of normalization
that could make two **meaningfully different** spec bundles hash
identically — a correctness risk, not just a missed optimization.

The cache-hit-rate concern is still addressed, at a different layer:
`spec-linter` gains `R-LINT-019`, a fail-severity rule rejecting
trailing whitespace anywhere in a spec file (frontmatter included).

## Consequences

The cosmetic diff never reaches a committed file in the first place, so
the cache-hit benefit is real rather than approximate, and the hash
function stays simple (raw bytes, nothing taught to ignore anything)
and therefore trustworthy. Implemented in the real
`gen/spec-linter/spec_linter.py` and covered by a real pytest test, per
this project's standing discipline of validating every spec change
against the actual tool.

See `specs/components/spec-bundle-assembler/component.md`'s resolved
open question and `specs/components/spec-linter/requirements/
R-LINT-019.md` for the current, authoritative rule.
