# D32 — Per-attempt persistence (`.hotdocs/attempts/`) and `llm-endpoint`'s call log

## Context

Before `D31`, a failed generation attempt's full `VerificationReport`/
`GenerationResult` detail was discarded within the merge, collapsed to
a bare `retry_feedback` `R-id` list fed to the next automatic attempt.
`D31` retired that automatic retry, which removed the only mechanism
that ever preserved *any* trace of an attempt's full detail (a later
best-of-k sample's result sharing one provenance manifest with the
earlier, flagged one). A blocked merge commits no provenance at all
(`R-MERGE-012`), so without a fix, a failed attempt's full diagnostic
detail would exist only in `merge-orchestrator`'s process memory for
the duration of one merge, then vanish — exactly what a developer needs
to decide, per `D31`'s new workflow, whether a failure looks transient
or spec-genuine.

A corpus-wide audit for similar gaps, run alongside this decision, also
found `llm-endpoint`'s `model_call_error` promised a four-category
vocabulary (`R-ENDPOINT-004`) that no field anywhere actually captured
— it collapsed to a boolean by the time it reached `TrackingRecord`,
making "how many failures were rate-limits vs. auth errors" unanswerable
even in principle. Fixed here, since it's the same shape of problem and
the same work.

## Decision

**`merge-tracker` gains `write_attempt_record` (`R-TRACK-007`)**: one
`AttemptRecord` per component per merge attempt, written to
`.hotdocs/attempts/<component_id>/` — the full `GenerationResult` and,
if reached, the full `VerificationReport`, taken as direct parameters
from `merge-orchestrator`, the same "caller's own facts, handed over
directly" pattern `TrackingRecord` already uses. A **separate** store
from `TrackingRecord`, not a change to that type's deliberately
flattened shape (`R-TRACK-002`) — `AttemptRecord` is the full-detail
companion a human reads when the summary says "blocked" and they need
to know why.

**`merge-orchestrator` calls it (`R-MERGE-021`)** right after each
component's generation (and verification, if reached) concludes, for
every outcome, before evaluating the block decision — same "both
outcomes get recorded" posture `R-MERGE-019` already has for the
end-of-merge `TrackingRecord`, and the same "this call's own
success/failure never alters the merge outcome" rule (`R-TRACK-005`,
extended to cover both write functions).

**`model_call_error` becomes a structured object** (`{category,
message}`, `category` one of `network`/`auth`/`rate_limit`/`timeout`),
not a boolean. `ModelResponse` also gains a `backend` field —
output-side only; `R-ENDPOINT-002`'s input contract (callers never name
a backend) is unchanged. **`llm-endpoint` gains its own call log**
(`R-ENDPOINT-006`, `.hotdocs/calls/`) — caller-agnostic, transport-level
only, since it's already the one chokepoint every model call passes
through regardless of caller.

## Consequences

The methodology's core traceability promise ("never silent") now
actually holds for the one place `D31` could otherwise have quietly
weakened it. Two complementary layers exist: `llm-endpoint`'s log
(vendor-level — "how many calls, what's our error rate by backend") and
each caller's own attempt record (semantic-level — "which `R-id`s
failed, why"). Both are plain `read_json`-queryable, no bespoke API, per
this corpus's established `.hotdocs/` convention.

See `specs/components/merge-tracker/requirements/R-TRACK-007.md` and
`specs/components/llm-endpoint/requirements/R-ENDPOINT-006.md` for the
current, authoritative rules.
