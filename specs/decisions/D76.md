# D76 — Extract component-gate-runner out of merge-orchestrator's per-component gauntlet

## Context

`merge-orchestrator` crowds two independent `SPEC_GUIDELINES.md` §4 size dimensions at once: `component_doc_words` over its 4000-word hard-fail ceiling, and `fan_out` (15) already past its own warn threshold — the exact "look closely" signal `R-LINT-022` exists to catch. This is not a new problem: `D14` already extracted `capability-scenario-verifier` out of this same component the first time these dimensions crowded together, mirroring `verifier-orchestrator`'s existing per-component dispatch pattern. The component has since grown past the ceiling again, and the same kind of self-contained sub-responsibility is extractable a second time: everything from a provenance check through generation, verification dispatch, compliance scanning, and provenance-write for one impacted component, currently inlined across `R-MERGE-003/004/005/006/008/009/015`, is a cohesive "run one component through its gauntlet" unit that the top-level sequencer only needs to call, never re-implement.

## Decision

A new component, `component-gate-runner`, owns that per-component gauntlet: given one impacted, non-sealed component id (sealed components are routed around it entirely, same as before), it checks `provenance-checker`, calls `spec-bundle-assembler` and `generator` on a miss, dispatches `verifier-orchestrator`, runs `license-scanner`/`secret-scanner` unconditionally, and calls `provenance-writer` once those conclude — returning one `ComponentPipelineResult` (the same shape `MergeResult.components[id]` already had). `merge-orchestrator` keeps everything that is genuinely merge-wide rather than per-component: the spec-linter/impact-analyzer gates, scheduling calls to `component-gate-runner` across the blast radius in dependency order with no fail-fast, the capability-scenario-verifier dispatch, the overall block decision, the atomic commit, the review packet, and merge-tracker reporting.

Wiring the real `test_author`/`judge` closures (`D65`'s single-bundle-argument shape, capturing `model`/`seed`/`llm_backend`/`repo_root`) stays exclusively `merge-orchestrator`'s job, unchanged from before — it already independently needed the same closures for its own `capability-scenario-verifier` call (`R-MERGE-014`, now `R-MERGE-014` unchanged), so centralizing the one wiring site there and passing the already-wrapped callables down to `component-gate-runner` avoids a second, duplicate wiring implementation rather than splitting it across two components.

Per `SPEC_GUIDELINES.md` §4's own observation about this exact shape of split: fan-out is not expected to vanish (the coordinator still calls the new component), but in this instance it does drop in practice, because every one of `component-gate-runner`'s own downstream calls (`provenance-checker`, `spec-bundle-assembler`, `generator`, `verifier-orchestrator`, `license-scanner`, `secret-scanner`, `provenance-writer`) was previously a direct `merge-orchestrator` dependency used for nothing else — none needed to remain a direct `merge-orchestrator` dependency after the split. The dimension this split actually targets, as the guidance predicts, is `component_doc_words`.
