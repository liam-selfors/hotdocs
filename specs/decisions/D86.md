# D86 — Generation moves out of the automated merge pipeline; merge-orchestrator becomes a pure provenance gate

## Context

Until now, `merge-orchestrator` called `component-gate-runner` (`D76`) automatically, once per impacted component, to generate, verify, scan, and write provenance inline as part of `run_merge` — an unattended, fully automated path from "spec changed" to "code regenerated and merged." A deliberate reversal: a human developer now owns producing `gen/` content and its provenance explicitly, before ever attempting a merge; the merge itself only ever checks that provenance already exists and is current, never produces it.

This does not weaken the provenance gate — a merge still MUST be blocked if any impacted component lacks valid, current-spec-matching provenance, same as always. What changes is *who* triggers the work that produces that provenance, and *when*.

## Decision

`component-gate-runner` keeps its entire existing per-component gauntlet (`R-GATE-001` through `007`, unchanged in content) but is no longer a library-only dependency `merge-orchestrator` calls — it gets its own CLI, `hotdocs prepare <component-id>`, invoked directly by a developer, independently of any merge attempt. Because it is no longer called *by* `merge-orchestrator`, it now wires its own real `test_author`/`judge` closures itself (previously `merge-orchestrator`'s job, shared across one wiring site for both callers under `D76`) — there are two independent wiring sites again, one in `prepare`, one in `merge-orchestrator`'s own `capability-scenario-verifier` call, simply because `prepare` is no longer a sub-call of anything. `component-gate-runner` also takes over writing `merge-tracker`'s per-component attempt record (previously `merge-orchestrator`'s `R-MERGE-021`) — it is the one actually making the attempt now, so it is the one with the detail to record.

`merge-orchestrator` drops every requirement that depended on calling `component-gate-runner`, `generator`, `verifier-orchestrator`, or either scanner (`R-MERGE-021`/`022`/`023`, retry_feedback entirely, dependency-ordered scheduling). In their place, a single new requirement: for every impacted component, sealed or not, check `provenance-checker` directly for a hit against the current `spec_bundle_hash` — a miss blocks that component with a reason naming it and pointing at `hotdocs prepare`; `merge-orchestrator` MUST NOT call `generator`, `verifier-orchestrator`, or either scanner under any circumstance. Sealed and non-sealed components are no longer special-cased differently at merge time at all — both go through the identical provenance check; the difference between them lives entirely inside `prepare` now (`R-GATE-007` still forces a sealed component's own unconditional characterization-test re-run, just at `prepare` time instead of merge time).

**An accepted trade-off, stated explicitly rather than left implicit:** a sealed component's safety against an un-re-verified `source_path` edit previously came from `R-GATE-007`'s unconditional re-check happening automatically on every single merge attempt. That unconditional guarantee is gone — it now depends entirely on a developer actually re-running `hotdocs prepare` after editing a sealed component's `source_path`, the same discipline every other component already requires for its own changes. This is a real, deliberate narrowing of an existing safety property, not an oversight.

Recovery from a blocked merge is now two steps, not one: a developer runs `hotdocs prepare` on whatever component needed it (optionally with `retry_feedback`, now `prepare`'s own parameter, not `run_merge`'s), *then* re-runs `run_merge`, which re-checks provenance and proceeds once it is current. `merge-tracker` itself is unchanged in role — still local-only, gitignored, non-gating (`D10` stands) — "informing" a merge's accept/reject decision, as intended here, means the provenance system (`provenance-checker`/`provenance-writer`), not `merge-tracker`.
