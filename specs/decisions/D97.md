# D97 — R-AUTHOR-010 clarified — the convention governs faking a dependency, never importing the component under test itself

## Context

`D96`'s fix got three of `provenance-tracker`'s five `AC-TRACK-*` test authorings past their prior failures, but a retry (forced by `D95`'s own spec change, which changed every criterion's assembled bundle content) surfaced two further, narrower problems with the very instruction `D96` just added, both traceable to the same ambiguity: `R-AUTHOR-010`'s opening sentence ("No component in this corpus is statically importable by another") does not say *by what* — a reasonable reader applies it to the component under test too, not only to a dependency the component under test calls internally.

`AC-TRACK-008`'s authored test took this literally: instead of a plain `from provenance_tracker import last_requirement_failures` (which `pytest`'s own working directory/`PYTHONPATH`, already set to the component's own `gen/<component>/` directory by `verifier-orchestrator`'s `_run_pytest`, resolves correctly whether the component is a flat module or a package — no custom loader ever needed for this), it wrote its own ad hoc loader for the component *under test itself*, and — with no worked example covering the package case — got the path wrong (`gen/<component>/__init__.py` directly, omitting the real nested `<module_name>/` directory a package actually lives under).

`AC-TRACK-009`'s authored test correctly limited the dynamic-loading technique to genuine dependencies, but the worked snippet `D96` provided only demonstrated the flat-module shape; faking a dependency by writing to `gen/<slug>/__init__.py` directly (an attempt to improvise the package shape without a worked example of it) does not match either of the two exact paths every real dependency-resolving component in this corpus actually checks (`gen/<slug>/<module_name>.py` or `gen/<slug>/<module_name>/__init__.py`) — the fake was never found.

## Decision

`R-AUTHOR-010` is amended, not superseded: its opening statement now says explicitly that this governs how the component under test resolves *its own* dependencies, never how a test imports the component under test itself — that import is always a plain `import <module_name>` / `from <module_name> import ...`, since the test always runs with the component's own `gen/<component>/` directory on `PYTHONPATH`, and Python's own import system already handles both the flat-module and the package shape correctly for that case with no special handling. The worked snippet is narrowed to the one case it actually needs to cover unambiguously: **always install a fake dependency as the flat-module shape** (`<repo_root>/gen/<dependency-slug>/<module_name>.py`, never the package shape) — every real dependency-resolving component in this corpus checks the flat path first, so a fake written there is always found regardless of which shape the real, unfaked dependency happens to use elsewhere. `module_name` is stated precisely as the dependency's own slug with hyphens replaced by underscores, closing the specific `__init__`-as-a-literal-module-name confusion a real candidate test fell into.

No new requirement; `R-AUTHOR-010`'s own text changes in place, `PROMPT_VERSION` → `v4`. `test-author` is cold-regenerated a fourth time; `AC-AUTHOR-010`'s own assertions are extended to also check the flat-only instruction and the corrected `module_name` wording appear in the prompt. `provenance-tracker`'s `AC-TRACK-008`/`009` are re-authored and re-verified once this fix is in place. `AC-TRACK-010`'s own failure this same retry (a malformed response with no matching marker pair) is unrelated to this fix — ordinary model non-determinism on a retry, not a reproducible spec gap — and is left to a plain re-attempt.
