# D57 — Two more real gaps, found re-attempting generator's self-regeneration a third time

## Context

`D56` fixed the nonce-delimiter collision and the empty-files cache-
poisoning bug. A third real retry, with both fixes in place, produced
a complete, non-truncated 489-line candidate that correctly imported
`cache-manager`/`llm-endpoint` flat — directly confirming `D55`'s
`dependency_usage` fix still holds. Running it for real against a
sandboxed copy of the real dependencies crashed:

```
AttributeError: 'NoneType' object has no attribute '__dict__'
```

inside `exec_module`, while `cache_manager.py` evaluated its own
`@dataclass(frozen=True)` class bodies. Root cause: the candidate
loaded `cache-manager`/`llm-endpoint` dynamically, per call, from
`repo_root` via `importlib.util.spec_from_file_location` +
`module_from_spec` + `exec_module` — a deliberate, reasonable choice
to correctly support `generate` being invoked against two *different*
`repo_root` values within one process (exactly the shape of this
session's own pre-swap-in verification harness: stage an untested
candidate elsewhere, exercise it against real dependencies, without a
static `sys.path` import silently reusing whichever `repo_root`'s
module happened to load first). But it never registered the loaded
module in `sys.modules` under its load-time name before running its
code — and `dataclasses`' internals look up
`sys.modules[cls.__module__]` to resolve a class's own annotations
during that exact class-body evaluation, so skipping the registration
step crashes on any dependency that defines a dataclass.

Unlike `D54`/`D55`/`D56`'s findings, this bug is not a spec/methodology
gap by itself — it's a plain implementation mistake in one candidate's
chosen technique. But the *correct* technique was never documented
anywhere this corpus's own `generator` requirements would have told a
future candidate to follow, so the fix belongs in spec regardless: the
next candidate choosing this same, legitimate technique has no reason
to get it right either, absent that documentation.

Separately, re-examining `D56`'s own fix surfaced a second gap:
`R-CACHE-007.md`'s new schema table told a human reader everything
needed, but a dependent's real `SpecBundle.dependency_interfaces`
(`R-ASSEMBLE-002`) never includes a dependency's `requirements/` —
only its `interface/`. A cold-mode caller generating against
`cache-manager`'s real contract would never actually see the table
`D56` added, making that fix real but mute for exactly the scenario it
was meant to fix.

## Decision

1. New `R-GEN-014` (acceptance: `AC-GEN-015`): documents that a static
   `sys.path`-relative-to-`__file__` import remains valid (always
   correct in production, since this component's installed location
   and its `repo_root` always coincide there), but an implementation
   choosing per-call dynamic loading from `repo_root` instead — to
   correctly avoid stale-module reuse across differing `repo_root`
   values in one process — MUST register the loaded module in
   `sys.modules` before `exec_module`. `generator.py`'s own
   `_SYSTEM_PROMPT` gained an explicit warning against this exact
   pitfall, naming this decision directly. `PROMPT_VERSION` bumped
   `v3` → `v4` (a substantive prompt-text change, `R-GEN-003`).
2. `cache-manager`'s payload-schema table moved from
   `requirements/R-CACHE-007.md` to `interface/data/CachedResult.md`
   — the one location `R-ASSEMBLE-002` actually surfaces to a
   dependent — restoring `SPEC_GUIDELINES.md` §10's one-definition
   rule (`R-CACHE-007` now points to it rather than repeating it).

Neither fix touched `gen/generator/generator.py`'s own working
dependency-loading code (it already uses the safe, static technique,
and was never in violation) — only its frozen prompt text and
`cache-manager`'s spec changed.

## Consequences

A fourth real retry, with both this decision's fixes and `D56`'s in
place, is the next real test — done separately, not assumed here.

Three real retries in this one self-regeneration sequence have now
each found a genuinely new, previously-undetected gap (D54's import-
path assumption, D56's three bugs, D57's two more) without ever
repeating a prior failure class. Restated plainly, same as `D56`: this
is the discipline working as intended, not evidence against it — but
it is also a fair prompt to ask, before a fifth billed call, whether
continuing to chase a fully self-hosted `generator` is worth more real
cost right now, versus treating the hand-authored bootstrap
(`verification/generator/BOOTSTRAP.md`) as a durable, acceptable
outcome and moving the methodology's attention to building out the
corpus's remaining spec-only components with the generator that
already works.
