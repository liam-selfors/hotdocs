# D44 — Extract `graph-query-engine`; rewire `spec-linter`'s graph rules

## Context

`D43` closed the first of two gaps it found: all six Query Surface
views actually ran and produced correct results, but they lived as
hand-embedded SQL prose inside `specs/architecture/
graph-query-engine.md` — the spec document was also, silently, the
implementation, exactly the spec/gen separation this methodology
otherwise enforces everywhere else, broken for its own infrastructure.
The second gap `D43` left open: `spec-linter`'s `R-LINT-003`/`004`/
`008`/`009`/`018`/`020`/`021` described themselves as "implemented as
queries over `nodes`/`edges`" while the real bootstrap code was plain
Python that never called `duckdb` at all.

## Decision

**Extracted a real component.** `specs/components/graph-query-engine/`
now owns the six shared views for real: each gets its own requirement
(`R-GQE-001`–`006`) citing the exact `SPEC_GUIDELINES.md` section it
reads under as its data contract, an `interface/data/` schema file, and
a loader contract (`R-GQE-007`, `load_views(con, repo_root)`,
idempotent). The SQL is a real generated asset
(`gen/graph-query-engine/views.sql`) plus a thin Python loader — a
second, explicitly-flagged bootstrap exception alongside
`spec-linter`'s own, documented in `verification/graph-query-engine/
BOOTSTRAP.md`. `specs/architecture/graph-query-engine.md` was trimmed
to the adoption history and decision rationale only — no second copy
of the SQL.

**Rewired all five graph-shaped `spec-linter` rules** onto it:
`rule_reference_resolution` (`R-LINT-003`), `rule_acyclic_graph`
(`R-LINT-004`), `rule_forward_traceability` (`R-LINT-008`),
`rule_backward_traceability` (`R-LINT-009`), and
`rule_depends_on_guarantees_resolution` (`R-LINT-018`) now query
`nodes`/`edges` instead of independently-written frontmatter parsing or
traversal code (`R-LINT-020`/`021`). `spec-linter`'s own `component.md`
now declares `depends_on: [comp-graph-query-engine]`, matching what it
actually imports.

Two confirmed, deliberate exceptions, not oversights — each backed by a
corpus-wide grep before being relied on:

- `R-LINT-003`/`004`'s `depends_on`/`realizes`/`uses_var` checks each
  keep one small, residual, native-Python check for `architecture`-doc
  frontmatter. `nodes`/`edges` are scoped to component-level data only
  (per `graph-query-engine`'s own "Query surface" section);
  `specs/architecture/pipeline-decomposition.md` is the one other
  `FRONTMATTER_BEARING_TYPES` doc_type in this corpus with a real
  non-empty `depends_on` — `product`/`var`/`decision` docs never
  populate it. `rule_acyclic_graph`'s DFS three-color cycle detection
  stays native Python rather than adopting `duckpgq`'s `MATCH` syntax —
  consistent with `D18`/`D20`: no other view needs graph-traversal
  syntax to exist in this engine, so a new query grammar for one caller
  would be exactly the premature complexity those decisions reject.
- `R-LINT-009`'s iteration and reported line number stay a native
  `_collect_covers` scan: `nodes`/`edges` resolve whether a `Covers:`
  target exists, but don't model which `product` doc owns a given
  `CS-id` (`R-GQE-001` leaves `capability_scenario` rows' owner
  deliberately unset — the `covers` edge carries that relationship, not
  a reverse lookup) — there is no view-only path back to the right doc
  and line to report against.

**Two real bugs found while wiring this engine into a second, sparser
caller** — `spec-linter`'s own test suite, which builds minimal
synthetic corpora rather than always using this repo's real one, unlike
every prior verification of this engine:

- `read_yaml_frontmatter` raises when its glob matches zero files
  (`read_text` already tolerates this natively). Every one of
  `spec-linter`'s 42 tests hit this identically via `nodes`'s
  `specs/vars/*.md` arm, since the fixture never creates a `specs/vars/`
  directory. `load_views` now pre-checks each such glob and substitutes
  a typed empty relation when it has zero matches — the same posture
  `R-GQE-005` already required for zero `.provenance.json` files.
- `read_yaml_frontmatter`'s struct-column auto-detection silently drops
  a declared frontmatter key from its result schema — a bind-time
  "column not found" error, not a null value — when that key is absent
  from every file in the glob at once. `edges`'s `uses_var`/
  `depends_on_guarantees` arms hit this against the same fixture, where
  no test component sets either field. Tried forcing an explicit schema
  via `read_yaml`'s `columns`/`auto_detect` parameters first — confirmed
  by hand that frontmatter-mode column detection still silently
  intersects with whatever keys are actually present, ignoring an
  explicitly requested wider schema. Rewrote those four `edges` arms to
  read raw text and extract each field by regex over the flow-style
  `key: [a, b]` syntax instead (`R-GQE-002`) — confirmed via
  corpus-wide grep that every real `depends_on`/`realizes`/`uses_var`/
  `depends_on_guarantees` value already uses that syntax, never YAML
  block-list style — and confirmed the rewrite produces the exact same
  323 edges on this repo's real corpus as the original did, before
  switching it in.

## Consequences

Both gaps `D43` left open are closed. `graph-query-engine` is now the
single real owner of all six shared views; every adopter named in
`specs/architecture/graph-query-engine.md`'s "Scope of adoption"
section that claimed to query them for real now actually does, for
`spec-linter`'s rules at least — `impact-analyzer`, `corpus-graph-
builder`, `capability-scenario-verifier`, and `review-packet-builder`
still only reference the engine from their own specs and remain
unverified the same way `spec-linter` was before this decision; that
stays open, tracked in `notes/backlog.md`, not resolved here.

`notes/backlog.md`'s "R-LINT-003/004/008/009/018/020/021 claim an
implementation that doesn't exist" item is resolved by this decision.
