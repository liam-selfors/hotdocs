# D98 — R-TRACK-009/010 state that each dependency is loaded lazily, only when actually needed

## Context

Two consecutive real cold-generation attempts at `provenance-tracker` (the second one specifically retried with `--retry-feedback=R-TRACK-009,R-TRACK-010` after the first attempt's candidate called `capability-scenario-verifier`'s wrong function name and eagerly loaded `impact-analyzer` even in the whole-corpus-scope branch where it is never called) reproduced the same eager-loading defect in a different shape each time: the first candidate loaded all three dependencies (`impact-analyzer`, `provenance-checker`, `capability-scenario-verifier`) unconditionally at the top of `check_readiness`; the retried candidate still loaded `capability-scenario-verifier` unconditionally (breaking a component-only, no-capabilities-in-scope test that correctly never faked it) and still loaded `impact-analyzer` unconditionally (breaking a whole-corpus-scope test that correctly never faked it either, since `changed_ids` was never given).

Bare `--retry-feedback` (a list of `R-id`s with no further detail, `R-GEN-012`) was not enough to fix this reliably a second time — plausible, since neither `R-TRACK-009` nor `R-TRACK-010` ever said *when* each dependency's module may be loaded, only when its function is logically called. A reasonable reading treats "load a dependency's module" and "call a function on it" as separable concerns, and a candidate can satisfy the letter of "only call `impact-analyzer` when `changed_ids` is given" while still loading (importing) the module unconditionally as a matter of code structure — which fails hard the moment a deployment or a test genuinely doesn't have that dependency's module present, exactly the shape every real generated-test case for this component takes.

## Decision

`R-TRACK-009` and `R-TRACK-010` now state explicitly, not just implicitly through describing when each function is *called*: each dependency (`impact-analyzer`, `capability-scenario-verifier`) MUST be loaded (imported/resolved) lazily, at the exact point its function is about to be called, never eagerly at the top of `check_readiness` or in any shared setup step that runs regardless of scope. `impact-analyzer` is loaded only inside the `changed_ids`-given branch; `capability-scenario-verifier` is loaded only when at least one product capability's `realizes`-set actually intersects the resolved scope. `provenance-checker` is the only dependency always genuinely needed (every scope checks at least the components in it), so it alone may be loaded unconditionally.

`provenance-tracker` is regenerated via the new sandboxed `bootstrap_component.py` driver (generate + verify in an isolated copy, swapped into the real `gen/`/`verification/` trees only on a full pass) with `--retry-feedback=R-TRACK-009,R-TRACK-010` against this clarified spec.
