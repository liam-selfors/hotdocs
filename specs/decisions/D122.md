# D122 — R-TRACK-010 must state exactly how the realizes edge is computed, mirroring capability-scenario-verifier's own internal convention

## Context

With `D121` landed, the next `provenance-tracker` retry reached 6 of 7 criteria passing — `AC-TRACK-010` (the capability half) was the only failure. Diagnosis: the real candidate's `_list_capability_realizes` scans a nonexistent `specs/capabilities/` directory for each file's own `realizes` field — backwards from this corpus's real, established convention (`D77`): a component declares which capability it realizes, on its own `component.md`; a capability's own file, under `specs/product/<name>.md`, has no reverse-pointer field at all. The correct mechanism — scan every `specs/components/*/component.md` for its own `realizes:` frontmatter — already exists, working, inside `capability-scenario-verifier`'s own private `_collect_realizes_edges` function, but that mechanism is internal code, never exposed anywhere in `capability-scenario-verifier`'s public `interface/` docs — so nothing in `dependency_interfaces` could have told a test author or a real candidate the real mechanism. This was a genuine spec ambiguity in `R-TRACK-010`, not a guessing mistake with a knowable right answer sitting unused.

## Decision

`R-TRACK-010` is amended to state the mechanism explicitly: the `realizes` edge is computed by scanning every component's own `component.md`, never a capability's own file, mirroring `capability-scenario-verifier`'s own internal convention by name. `provenance-tracker` is regenerated against this amendment.
