# D82 — Found by auditing the biggest remaining component's dependencies before ever generating it

## Context

`merge-orchestrator` (15 dependencies, this corpus's largest fan-out)
is the first and only component that must itself *construct* the
`judge`/`test_author` closures `verifier-orchestrator` and
`capability-scenario-verifier` each independently call. A
pre-generation audit of its dependency contracts — the same proactive
check that found `D81` — found that the single-`bundle`-argument shape
those two components call with exists only inside
`capability-scenario-verifier`'s own real `gen/` source (the only one
of the two actually built); nothing in either component's
bundle-visible `interface/` ever stated it as a rule.

Checking the one cross-reference that did exist — both components'
`interface/library.md` claimed `judge` was "the same injectable-callable
pattern as `spec-linter`'s R-LINT-015" — against `spec-linter`'s real
code found the claim is simply false: `spec-linter`'s `judge` is
`judge(term, local_text, glossary_text) -> tuple[bool, str] | None`,
a narrow three-positional-argument shape for one specific task,
unrelated to the single-`bundle`-argument convention the other two
components actually use.

## Decision

Promoted the real, confirmed contract to `glossary.md` ("Injected
`judge`/`test_author` callable shape"): `judge(bundle) -> outcome` and
`test_author(bundle) -> outcome`, with duck-typed outcome handling
(a dict with `result`/`verdict`/`model_call_error`/`file` keys, or an
object with the same attributes) — confirmed directly from
`capability-scenario-verifier`'s real `_dispatch_llm_judge`/
`_dispatch_generated_test`. `bundle` itself is not one universal shape:
`verifier-orchestrator` now states (`R-VERIFY-003`) it passes the same
`CriterionBundle` `test_author` receives, reusing an already-specified
shape rather than inventing a second one; `capability-scenario-verifier`
now states (`R-SCENARIO-003`, split out from `R-SCENARIO-001` by
`D84` once the latter grew past the per-file word cap) its own
narrower, purpose-built bundle,
since no single component's `CriterionBundle` applies to a
cross-component capability scenario.

Corrected the false "same pattern as spec-linter" claim in both
components' `library.md`. Added to `R-MERGE-004`: since neither
`llm_endpoint.complete` nor `test_author.author_test` matches the
single-argument shape themselves (both require a `model` argument with
no default), `merge-orchestrator` must wrap each in a closure
capturing `model`/`seed`/`llm_backend`/`repo_root` itself — the only
layer with a model identifier to capture, stated explicitly for the
first time.

Also fixed, found in the same audit pass: `R-MERGE-011`'s "either
scanner reported a blocking flag" never named either field.
`LicenseScanResult.blocked` and `SecretScanResult.flagged` are
different names for the same concept across the two scanners — now
stated explicitly.

## Consequences

Seventh occurrence of the "fact one component needs from a dependency
was never promoted anywhere a `SpecBundle` surfaces" gap class this
session (`D61`, `D62`, `D65`, `D67`, `D69`, `D76`, `D80`), and the
second (after `D81`) caught proactively before a real `generate()` call
was ever spent on the affected component. Unlike the others, this one
also surfaced an active *misstatement* (the false spec-linter
cross-reference), not just a silent gap — worth remembering that a
convention being named and cited somewhere is not the same as the
citation being checked against the thing it cites.

`verifier-orchestrator` itself remains mid-build (blocked on API
credits, last real candidate at 12/13 tests before this session's
pause) — its own `judge` wiring, once built, should be checked against
this now-documented contract rather than left to a fifth independent
guess.
