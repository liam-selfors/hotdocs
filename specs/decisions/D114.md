# D114 — dependency_interfaces resolves a dependency's own transitively-referenced types, one level deep

## Context

`D110` and `D112` both flagged, as a deliberately deferred known limitation, that `dependency_interfaces` never resolves a type referenced by a dependency's own documented signature but owned by a different, undeclared component. `provenance-tracker`'s own bootstrap (`D111`–`D113`) hit exactly this for real: `provenance-checker`'s `ProvenanceCheckResult.verification_report` field is documented only as an opaque placeholder (`{"...": "a VerificationReport"}`), since `provenance-checker` correctly never depends on `verifier-orchestrator`, `VerificationReport`'s real owner. With no real shape anywhere in `dependency_interfaces`, test-authoring for `AC-TRACK-010` had no way to construct a realistic fake `verification_report` and guessed a `passing: True` field that doesn't exist on the real type, rather than the real `requirement_results` flat mapping.

Deferred twice already with the expectation that `provenance-tracker`'s own bootstrap would either hit it for real or not — it did, so per that stated plan this is addressed directly rather than deferred a third time.

## Decision

New `R-ASSEMBLE-013`: for each dependency, `dependency_interfaces`' entry additionally resolves any bare type name that dependency's own interface text mentions but does not itself own — searching the whole corpus for exactly one component that does, one level deep only, skipping silently on no match or more than one match. New `AC-ASSEMBLE-015`.

`spec-bundle-assembler` is cold-regenerated against this amendment; `provenance-tracker` is retried once more.
