# D92 — hotdocs build combines generation and verification into one command; component-gate-runner writes its own attempt records to break a dependency cycle

## Context

`hotdocs generate`, `hotdocs check-capability`, and `hotdocs verify` were three separate commands performing closely related work: the first two check-then-do for one component or capability, the third only ever reads what they already produced. `provenance-tracker`'s `check_readiness` already has to compute, for every item in scope, whether its provenance is current — the same computation `component-gate-runner`'s and `capability-scenario-verifier`'s own provenance checks make internally. The only thing `verify` was missing was acting on a miss instead of just reporting it, the same check-then-do pattern already used everywhere else in this corpus.

Combining them this way creates a real structural problem, not just a naming one: `component-gate-runner` depends on `provenance-tracker` (to call `write_attempt_record`). If `provenance-tracker` now also depends on `component-gate-runner` (to trigger generation on a miss), that is a two-node dependency cycle `spec-linter`'s `R-LINT-004` would correctly reject.

## Decision

`hotdocs build [<component-id>] [--changed=<spec-id>...] [--retry-feedback=<R-id>,...] [--repo-root=<dir>] [--format=json|text]` replaces `hotdocs generate`, `hotdocs check-capability`, and `hotdocs verify` entirely. Owned by `provenance-tracker`: for every component in the given scope (a single id, a blast radius, or the whole corpus), it calls `component-gate-runner`'s `run_component_gates` (which still checks provenance first and skips real work on a hit — nothing about that per-component gauntlet changes); for every capability whose realizing set is now fully covered, it calls `capability-scenario-verifier`'s `run_capability_gates` the same way. It reports one `ready` verdict with per-item detail, same shape `VerifyReport` already had. `--retry-feedback` is only meaningful when the scope is a single component id.

**Breaking the cycle:** `component-gate-runner` no longer depends on `provenance-tracker` at all. It writes `AttemptRecord`s to `.hotdocs/attempts/<component_id>/` directly itself — a plain, documented JSON write, not a call into `provenance-tracker`'s own code — the same "write a shared file format without depending on the component that reads it" pattern this corpus already uses on the read side (e.g. `provenance-tracker`'s own predecessor reading `provenance-writer`'s manifests directly rather than depending on its caller's result type). `provenance-tracker` keeps reading `.hotdocs/attempts/` for `last_requirement_failures` and its own UI — it owns the read side, `component-gate-runner` owns the write side, and neither depends on the other for it.

`component-gate-runner` and `capability-scenario-verifier` retire their own standalone CLIs (`hotdocs generate` as a bare verb, and `hotdocs check-capability`) — the same precedent `D91` already set for `generator`'s. Both remain real components with their own requirements and library functions, called internally by `hotdocs build` and never by a developer directly.
