# D92 — Decisions belong in the graph, not beside it

## Context

`D88` gave decision supersession a query surface via a dedicated
`decision_lineage` view, reasoned at the time as the lower-risk choice
over extending `nodes`/`edges` (avoiding any risk to existing
consumers for a fact only decision records needed). The user then
asked to explore decisions as genuine graph citizens directly — the
same `nodes`/`edges` shape every other spec kind (component,
capability, var, guarantee, requirement, acceptance, capability
scenario) already uses, not a parallel, decision-only view.

Re-examined against that ask, `D88`'s own reasoning does not hold up:
`nodes`' shape (`id`, `title`, `status`, `kind`,
`owner_component_id`) already fits a decision record exactly — every
field a decision has either maps directly or is cleanly `NULL`. The
risk `D88` was avoiding (widening an existing view's shape) does not
actually materialize, since no new column is needed on `nodes` at
all — only a new `kind` value and two new `edges` `edge_type`s, the
same pattern `depends_on`/`realizes`/`uses_var`/`depends_on_guarantees`
/`covers` already established.

## Decision

`nodes` gains an eighth kind, `decision`, read via
`read_yaml_frontmatter` (safe despite `D44`'s sparse-column gotcha —
`id`/`title`/`status` are unconditionally required on every decision,
never absent corpus-wide the way `supersedes`/`builds_on` are).
`edges` gains two new `edge_type`s, `supersedes` (scalar) and
`builds_on` (list-valued), extracted via `read_text` + regex for
exactly the sparse-column reason `D44` already established for
`uses_var`/`depends_on_guarantees`.

`decision_lineage` is narrowed to `id`/`last_ratified_commit` only —
the one fact with no equivalent column in `nodes`/`edges`.
`status`/`supersedes`/`builds_on` move there entirely, becoming the
single canonical source for those facts (`SPEC_GUIDELINES.md` §10):
keeping them in both places would have meant two independently
queryable definitions of the same fact, exactly what that section
warns against. `R-LINT-029`/`030` now query `nodes`/`edges` instead.

This decision `supersedes: D88` — not a partial amendment, the entire
mechanism `D88` specified (the five-column view) is replaced by a
structurally different one, meeting the full-replacement bar
`supersedes` requires. `D88.status` flips to `deprecated` as the
sanctioned metadata-only edit that mechanism itself requires.

## Consequences

The first real, in-session use of `supersedes` on a same-session
decision rather than a months-old one — the mechanism `D87`
formalized applies identically regardless of how much time passed
between ratification and supersession. Real tests confirm the new
`nodes`/`edges` shape against the current, unfixed
`gen/graph-query-engine` code (both correctly fail), and the narrowed
`decision_lineage` against the same.
