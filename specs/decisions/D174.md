# D174 — capability-scenario-verifier's gate functions were specified but never built, and its scenarios were never run

## Context

`R-SCENARIO-004` (`D89`) required `check_capability_provenance` and
`run_capability_gates`, and `provenance-tracker`'s readiness check calls
them for every capability a scope touches. The built module has
neither, since it was generated before `D89` and never regenerated; its
tests passed because they predate the requirement. Auditing the spec
before regenerating found more than the missing functions:

- **Three signatures for one function.** `R-SCENARIO-004` said
  `(capability_id, repo_root, model, seed, llm_backend)`; `library.md`
  said `(…, judge, test_author)`; `provenance-tracker`'s `R-TRACK-010`
  (`D125`) and code call it with `judge=`/`test_author=` keywords, and
  build those from `llm_backend.judge`/`.test_author` attributes that no
  backend has.
- **Scenarios were never run.** The built dispatch marked a
  `generated-test` scenario `pass` once `test_author` returned a file,
  and a `compiled` one once it compiled. A capability whose scenarios
  all failed would have been reported passing.
- **`test-author` could not take the bundle.** `author_test` needs a
  component-scoped `CriterionBundle`; the capability bundle has no
  `component_id` or `criterion_id`, so its output path was
  `verification//generated-test/…`.
- **A capability with no scenarios passed**, and **editing a scenario
  did not invalidate a recorded pass**: the key hashed only realizing
  components' code.
- `interface/cli.md` said only "None", yet by `D162` the file's
  existence is what makes a CLI need coverage.

## Decision

`model`/`seed`/`llm_backend` is the one signature (`D92`; the same
posture as `component-gate-runner`), and `run_capability_gates` builds
its own `test_author` and `judge` (`R-SCENARIO-007`/`008`), the judge
contract being `component-gate-runner`'s `R-GATE-010` restated: a bundle
never carries another component's requirements, and editing the glossary
to share it would change every component's spec hash. A pseudo component
id `capabilities/<P-id>` lands generated tests beside the record.

Scenarios are decided by running them (`R-SCENARIO-005`); the key also
covers the capability's own file and a `gate_version` (`R-SCENARIO-006`);
a capability with no scenarios fails. Unlike `component-gate-runner`
(`D166`), a recorded failure **is** a hit: the key is the code itself,
so any fix changes it, and a read-only `hotdocs verify` can report the
failure without a model. `interface/cli.md` is removed, honoring `D92`
rather than inventing a CLI.

## Found, not changed here

`provenance-tracker` still calls `run_capability_gates` with
`judge=`/`test_author=` and must be changed (its `R-TRACK-010` snippet
and `_make_judge`/`_make_test_author`) to pass `model`, `seed`, and
`llm_backend`.
