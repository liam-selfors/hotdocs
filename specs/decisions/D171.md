# D171 — verifier-orchestrator verifies a sealed component at its source_path

## Context

`D170` found that `verify` had no notion of a sealed component.
`SPEC_GUIDELINES.md` §8 says a sealed component's code lives at
`source_path`, never under `gen/`, with characterization tests in
`verification/<component>/` "the normal way", yet `verify` looked only
under `gen/<slug>/` and for cached tests under
`verification/<slug>/generated-test/`. Run on `criterion-compiler`
(15 criteria, a hand-maintained suite named `test_ac_compile_NNN_*`) it
reported interface drift and failed every criterion.

The suite's own fixtures had hidden the gap. Its generated `foo`
component was labelled `sealed: true` with a `source_path`, an accident
that made it lint-clean (a sealed component needs no `realizes`) while
being tested as if generated. Its `bar` dependency was the inverse,
`sealed: false` with a `source_path`.

## Decision

`R-VERIFY-017`: for `sealed: true`, `verify` loads the code from
`source_path`, and verifies each `compiled` or `generated-test`
criterion by the hand-maintained characterization tests in
`verification/<slug>/test_*.py`, matched to a criterion by function
name (`test_` plus the criterion id lowercased, hyphens as
underscores). A criterion with no matching test fails, loudly, with
`no characterization test`: an unmatched criterion is not silently
skipped. Mutation testing does not run, since mutating legacy code in
place proves nothing about it; `mutation_score` is `null` and never
gates.

The hand-test fixtures are corrected to what they claim: `foo` is a
non-sealed component realizing a capability `P-FOO`, `bar` is sealed.
Regenerated directly, per the `D58` exception, against the hand suite.
