# D185 — hotdocs-cli split in two, because one module overflowed a model response

## Context

`hotdocs-cli` covered routing and project setup in one component. Its first
generation round produced an 825-line module and passed five of seven
criteria that ran. After the spec grew with the multi-provider endpoint's
details, the next round's generation call returned no files at all, with no
error. Reproducing the call and keeping the raw reply showed why: the reply
was 11 KB, began in the middle of a function, and held one `END FILE` marker
and no `BEGIN FILE`. The front of an over-long response had been lost, so
nothing parsed. The module, at roughly 30 KB and growing, no longer fit in one
response.

## Decision

Two components, each cohesive and well under that size: `hotdocs-cli`, the
dispatcher and verb table; and `hotdocs-init`, project setup and provider
configuration. The dispatcher routes `init` like any verb, except that
`hotdocs-init` is loaded from the tool's own checkout (the project does not
have it yet) and receives the dispatcher's input, output, environment, and
working-directory arguments. Requirements `R-CLI-005`–`011` became
`R-INIT-001`–`007` unchanged apart from ids and `main` no longer receiving the
word `init`.

## Found, not fixed here

- `generator` treats a reply that parses to zero files as a success with an
  empty `files`, rather than as a failure with a reason. `bootstrap_component.py`
  then crashes verifying a directory that was never written. A truncated or
  unparseable reply deserves its own `model_call_error` category.
- Nothing warns a spec author that a component is heading past what one
  response can carry; the size caps in `R-LINT-012` count spec words and
  generated lines after the fact, not the size of the module a spec will
  produce.

## First round of `hotdocs-init`

Four of seven criteria passed outright (every provider-configuration and
usage-error criterion), with mutation score 1.0. The three failures were
specification gaps: the progress-line format was not pinned (a test matched
by substring and met the `.gitkeep` lines); a project without `llm-endpoint`
crashed `init` instead of skipping the provider step; and the wording of the
`claude` fix line was open. Each is now pinned in `R-INIT-001`, `R-INIT-003`,
and `R-INIT-004`.

The dispatcher's first round (`hotdocs-cli`, split) passed five of six
criteria at mutation score 1.0. The sixth asserted something its criterion
never stated (that the routed fake received no arguments, when the
dispatcher correctly appended `--repo-root`); the criterion now says only
exit codes are asserted.

A later round passed `AC-CLI-006` but failed `AC-CLI-003` the same way: its
tests compared whole forwarded argument lists and forgot the `--repo-root`
token `R-CLI-002` appends. The order of the two appended tokens (repo root
first, `--model` last) is now stated in `R-CLI-003` and the criterion lists
the forwarded tokens explicitly.

Second round of `hotdocs-init`: four more gaps. The test fake logged inside
the project, so a "no file changed" check saw its own log; loading the vendored
`llm-endpoint` left a `__pycache__` in the project (a real, small defect,
now specified away); "the same relative path" for `--example` was ambiguous
between the tool root and the example folder; and "exactly these lines" was
read as "this is all the output".
