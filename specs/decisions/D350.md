# D350 — An unanswerable blast radius makes verify not ready

## Context

`impact-analyzer` returns an empty `impacted` list with a non-null
`precondition_error` when it cannot compute a blast radius, for example
when the corpus fails `spec-linter`. Its report says callers MUST NOT read
that list as "nothing was impacted". `provenance-tracker`'s
`check_readiness` did not say how to handle the error, and the generated
code checked the empty scope and reported `ready: true`. The capability
scenario `CS-MERGE-VISIBILITY-001` exposed it: its test built a corpus that
failed lint, so the tracker reported a change with a failing component as
ready.

## Decision

`R-TRACK-009`: when `impact-analyzer` reports a `precondition_error`, the
scope is unknown. Nothing is checked, `ready` is false, and the only reason
is `blast radius unavailable: <precondition_error>`. `AC-TRACK-009` pins
it. `CS-MERGE-VISIBILITY-001` now states that its corpus passes
`hotdocs lint` at every step. The rationale text in `provenance-tracker`'s
`component.md` is shortened to pay for the new requirement text, since the
history it retold is in `D87`, `D88`, `D92` and `D93`.

## Consequences

`provenance-tracker` is regenerated, and so are its dependents
`component-gate-runner`, `provenance-tracker-ui` and
`review-packet-builder`. `hotdocs verify --changed=...` can no longer
report ready for a change whose impact it could not compute.
