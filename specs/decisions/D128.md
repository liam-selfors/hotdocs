# D128 — provenance-writer's inputs reads MUST use dual dict-or-attribute access, not only nested fields

First real cold-generation attempt for `provenance-writer` (seed 1):
6 of 12 criteria passed, `mutation_score=1.0`. All six failures
(`AC-PROV-003/005/007/010/011/013`) crashed with the same root cause,
confirmed by direct sandbox inspection: `build_manifest`'s own
top-level reads of `inputs` (`inputs.generation_result`,
`inputs.license_scan_result`, `inputs.secret_scan_result`,
`inputs.gate_versions`, `inputs.provenance_hit`, `inputs.attempts`)
are bare attribute access, even though the candidate's own `_field()`
helper correctly applies dual dict-or-attribute access to every field
*nested inside* those values. Every failing criterion's generated
test happened to construct `inputs` as a plain dict; every passing
criterion's test either wrapped its dict in an attribute-forwarding
shim or constructed a real `ProvenanceInputs(...)` instance.

This is the identical bug class `R-TRACK-012` already closed for
`provenance-tracker`, one level removed: there, the candidate read a
*called* dependency's return value bare; here, it reads a parameter
the *caller* hands in directly, bare. The same `D94` duck-typing
convention governs both — `interface/data/ProvenanceInputs.md`'s own
example renders the shape as a plain JSON object, exactly like every
other "data" interface type in this corpus, so a dict-shaped
`inputs` must be exactly as valid as a `ProvenanceInputs` instance.

New `R-PROV-014` states this explicitly. Retrying generation against
it next.
