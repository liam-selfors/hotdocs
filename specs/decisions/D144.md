# D144 — R-AUTHOR-024 itself guessed a sys.modules key, the exact thing R-AUTHOR-022 already forbids

## Context

Eighth `review-packet-builder` retry (after `D143`'s test-author fix):
a severe regression, 9 of 11 failing (down from 10/11 passing before
`D143`). Every new failure has the identical shape: a generated test
reads `sys.modules["provenance_tracker"]` (or an equivalent bare
dependency name) *after* calling `build_review_packet`, exactly as
`R-AUTHOR-024` newly instructed — but this round's real candidate
registers its dynamically loaded module under
`f"_hotdocs_dep_{slug}_{module_name}_{id(repo_root)}"`, a unique,
`repo_root`-qualified key, never the bare name. `R-AUTHOR-024`'s own
instruction told every test to guess exactly the bare-named
`sys.modules` key — the identical failure mode `R-AUTHOR-022`
(`D123`) already, correctly, forbade: "real loaders key dynamically
(often `repo_root`- or hash-qualified), so any guess is unreliable."
`R-AUTHOR-024` contradicted `R-AUTHOR-022` within the same prompt,
and the contradiction was invisible in the hand-maintained test suite
(`verification/test-author`) because that suite only checks the
*prompt text itself* contains certain words — it never runs a second,
independently-written candidate against the instruction the way a
real `generated-test` round does.

The root mistake: `D143` diagnosed the failure correctly (a test's
stale pre-call module reference never observes a candidate's later
`exec_module`) but prescribed the wrong fix. There is no reliable way
for a test to locate *which* `sys.modules` key a correct, defensively-
written candidate used — the key itself is exactly the thing
`R-GEN-018`/`R-AUTHOR-022` already say a test can never predict. The
only mechanism that survives regardless of module-object identity or
`sys.modules` key is a **file** — write the invocation record to a
path the test controls, not an in-process data structure at all.

## Decision

`R-AUTHOR-024` is rewritten (not superseded by a new id — never
shipped anywhere else yet): confirming a dynamically-loaded fake was
invoked MUST use a file-based invocation log — the fake's own code
appends its invocation record to a file under a path the test
constructs and controls — never an in-process, module-level list read
back through any `sys.modules` lookup, bare-named or otherwise, since
a correct candidate's own loader may key dynamically (`R-GEN-018`) and
the key is never predictable from the test's side. `R-AUTHOR-022`
amended to cross-reference this: its own "have the fake's own code
record its invocation" instruction now explicitly means a file, not
an in-memory list. `AC-AUTHOR-024` rewritten to match.

`test-author` is regenerated again against both amendments, same `D58`
path. `review-packet-builder` is retried next.
