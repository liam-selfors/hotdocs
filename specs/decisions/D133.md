# D133 — decision-drift-detector's acceptance criteria are generated-test, not compiled

First real cold-generation attempt: all three criteria failed
identically with `step '...' does not match any recognized template
in the step grammar`. Diagnosed directly against
`pipeline/criterion-compiler/criterion_compiler.py`'s own fixed
grammar (`R-COMPILE-001`): a `Given` step must be exactly `a <name> is
<literal>` or `a <TypeName> with <field>: <literal>, ...`; a `When`
must be exactly `<func> is invoked with <args>`; a `Then` must be
exactly `<path> equals <literal>` or a severity-finding check. None of
these express "build a git repo, make several commits, mark a
decision deprecated in one of them" — the grammar can only assemble
literal-value fixtures and a single function call, never arbitrary
setup code.

`find_decision_drift(repo_root: Path) -> DriftReport` and
`find_decision_impact(repo_root: Path, decision_id: str) ->
DecisionImpactReport` (`interface/library.md`) both read real git
history at `repo_root` directly — there is no way to drive them with
literal-value fixtures alone; a real test needs to construct an actual
git repo with real commits, exactly as `component.md`'s own prose
already said ("tested against a synthetic git repo built inside the
test itself ... not a mock"). That prose was self-contradictory: it
simultaneously claimed `kind: compiled` and described exactly the kind
of arbitrary setup code only `kind: generated-test` can express. This
was a pre-existing spec-authoring mistake, not a candidate defect —
caught on the very first generation attempt, before any candidate code
was even judged.

All three `AC-DRIFT-*` files' `Kind:` changed to `generated-test`;
`component.md`'s own prose corrected to match. Retrying generation
next.
