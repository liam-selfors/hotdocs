# D39 — Provenance-checker, narrowed `cache-manager`, and developer-triggered cold regen with trusted provenance

## Context

Investigating Finding #1 from a self-audit of the methodology (`R-MERGE-003`'s cache-hit short-circuit possibly trusting an unverified candidate) surfaced that `cache-manager` was being asked a question its own data could never answer: it records that a candidate was *produced*, never that it was *verified* — `verifier-orchestrator` never writes to it. A failing candidate and a passing one are cached under the same key with nothing to distinguish them on a later `get`. `R-MERGE-003` treated any hit as grounds to skip verification entirely, which both undermines `D11`'s "cache hit restores a prior verified state" claim and risks silently defeating `R-MERGE-018`'s "a plain re-run recovers from a transient failure" recovery path.

A proposed fix (a blockchain-style fingerprint, or a new cache artifact) turned out to be unnecessary: `.provenance.json` (`D7`, `SPEC_GUIDELINES.md` §7) already carries everything needed — `spec_bundle_hash`, `gate_versions`, and the full `verification_report` — committed under the same discipline as the code it describes, and only ever reaches that state because the merge gate already blocked it otherwise. No new artifact, no new cryptography.

This converged with a separate, larger question: whether generation should be exclusively a merge-time, CI-triggered activity. `D1` (`notes/initial-ideas.md`) already says developers can run a cold regen on demand during development — and the CLI already supports it (`hotdocs generate`, `hotdocs verify`, standalone of `hotdocs merge`) — but the standalone path never invoked `provenance-writer`, so a developer's on-demand run left no trail CI could ever recognize. Closing the provenance-trust gap and closing this gap turned out to be the same fix.

## Decision

**New component, `provenance-checker`.** Reads a component's committed `gen/<component>/.provenance.json` and compares its `spec_bundle_hash`/`gate_versions` against the caller-supplied current ones (`R-PROVCHECK-001`). A match is honored as a hit unconditionally for a component with no `llm-judge`-kind criterion; for one that has at least one, the hit is honored only when `VAR-TRUST-JUDGE-PROVENANCE` resolves to `true` (`R-PROVCHECK-002`/`003`). Read-only; never calls `cache-manager` (`R-PROVCHECK-004`). `merge-orchestrator`'s `R-MERGE-003` now checks this component instead of `cache-manager`, for non-sealed components only — a **sealed** component is never checked against it at all (`R-MERGE-015`): its `spec_bundle_hash` reflects only its spec, never `source_path`'s actual content, so a human editing the hand-maintained implementation directly would leave a prior committed manifest's hash unchanged, and trusting that hit would mean never re-running the one check that could catch exactly that edit.

**`cache-manager` narrows to pure cost-avoidance.** It no longer has any role in deciding whether verification is skipped — only whether a redundant model call is avoided, which `generator`/`test-author`/`license-scanner`/`secret-scanner`'s own per-gate checks already did and continue to do unchanged. This makes a second change safe that would have been risky before it: `VAR-CACHE-STORE-URL` becomes optional, falling back to a local `.hotdocs/cache/` store (`R-CACHE-009`) — fine now that a hit or miss here is correctness-neutral, and the right default for a single-developer project with no shared infrastructure to point at. A multi-developer project running merges through CI still needs a real shared store to get the benefit across runs; the fallback only means forgetting to configure one no longer means no caching at all.

**New var, `VAR-TRUST-JUDGE-PROVENANCE`.** Governs whether `provenance-checker` may honor a hit for a component with an `llm-judge` criterion. Defaults to `true` — a deliberate exception to this corpus's usual conservative-when-absent posture (`R-CACHE-004`, `R-ASSIST-007`), because this is a governance-maturity choice a project makes for itself, not a failure/degradation case. An early-stage repo leans on cheap, developer-triggered cold regen without unconditionally re-paying for a non-reproducible judge call; a maturing repo hardens its own governance later by setting it `false` — a one-line, visible, auditable posture change. `compiled`/`generated-test` criteria are never affected by this variable either way: running already-authored code against a candidate is always cheap and deterministic, so merge-time CI can — and does — always re-derive that truth itself regardless of trust.

**Renamed `cache_hit` to `provenance_hit`** everywhere it meant "this whole component's processing was skipped" (`MergeResult`, `TrackingRecord`, the provenance manifest schema, `ReviewPacket.cache_hit_status`) — this field never actually meant "`cache-manager` had an entry," and conflating the two names under one word was part of how the original gap went unnoticed. Every genuinely per-gate `cache_hit` field (`GenerationResult`, `TestAuthoringResult`, `LicenseScanResult`, `SecretScanResult`, `VerificationReport.criteria[].test_authoring`) is unchanged — those really are about `cache-manager`.

## Consequences

The verification-trust gap is closed without adding a store, a signature scheme, or new cryptography — the fix was recognizing an existing, already-committed artifact already had the right shape. `D1`'s "cold regen on demand" promise now has a real path to becoming durable: a developer's feature-branch run, once it also invokes `provenance-writer`, produces exactly the artifact `provenance-checker` later recognizes — the same mechanism serves both the correctness fix and the workflow extension.

`merge-orchestrator` is now at 3991/4000 `spec_bundle_words` — tight, trimmed repeatedly during this work rather than split, and the architecture's own tracked tension (`pipeline-decomposition.md`'s dedicated note) is no longer hypothetical: the next requirement-level addition here will likely need either further trimming elsewhere first or finally acting on the long-flagged fan-out/word-count question.
