# D104 — test-author states flow-style frontmatter lists and self-checks a synthetic fixture's lint-cleanliness; diagnose-prevent-scrub becomes standing practice

## Context

Diagnosing `spec-bundle-assembler`'s remaining seven failing criteria by hand (patching only the suspect lines in each failing test, in a sandbox, never committed) found that five of the seven shared one exact root cause: the synthetic fixture wrote a frontmatter list field (`owners`, `depends_on`) in YAML **block style** (`owners:\n  - x`), which this corpus's hand-authored frontmatter reader does not recognize as a list — every one of the 20+ real spec files in this corpus uses **flow style** (`owners: [x]`) exclusively, with zero exceptions, confirmed by a corpus-wide search. Patching just that one line per file, with no other change, made all five pass cleanly against the unmodified candidate — proving the regenerated `spec_bundle_assembler.py` was correct all along; only the test authorings had a defect, and the same defect, each time. The remaining two failures were independent one-offs (a synthetic `VAR-*.md` fixture using the wrong frontmatter schema entirely, and a dependency fixture missing an `acceptance/` file for its own requirement) — real, but not part of a repeated pattern, and not pursued further.

Every one of the five real failures surfaced the same way: a confusing, deep failure (a `BinderException` several call layers down, or a bare `KeyError`/`AttributeError` on a field that only exists on the success path) rather than a clear, immediate signal that the fixture itself was invalid. This made diagnosis slower than it needed to be, and would make it slower again for the next person (or agent) to hit the same class of mistake.

## Decision

**Specific fix:** `R-AUTHOR-012` gains a stated requirement that any list-valued frontmatter field (`owners`, `depends_on`, `realizes`, `uses_var`) in a synthetic fixture MUST use flow style (`[a, b]`), never block style — matching this corpus's own universal real-world convention exactly, not an arbitrary new rule.

**Structural safeguard:** `R-AUTHOR-012` additionally instructs that whenever a test constructs a synthetic fixture and the criterion under test depends on a precondition this component checks against `spec-linter` (directly or transitively), the test SHOULD call `spec-linter`'s own `lint()` against the constructed fixture **first**, as a self-check, and assert zero hard-fail findings before proceeding to the behavior actually under test — turning a confusing downstream crash into an immediate, legible "the fixture itself is broken" signal, with the real finding list attached, the moment it's wrong.

**Standing methodology, not a one-off**: this corpus's own reaction to a real, confirmed bug is now stated explicitly as three steps, not left implicit in `D36`'s "never hand-patch, fix the root cause" alone: (1) diagnose the actual root cause — never accept a surface symptom as the explanation; (2) fix it in the spec, and add a structural safeguard that would catch a recurrence early and legibly, not just the one instance found; (3) scrub the existing corpus (the already-committed `verification/` tree, and any spec file whose own prose might model the same mistake) for other live instances of the identical defect, not only the one that happened to be found first. A corpus-wide scrub for this specific defect (block-style frontmatter lists, in both `verification/` and `specs/`) found none — nothing had yet been committed carrying it.

`test-author` is cold-regenerated against the amended spec (generate-only, verified via the hand-maintained suite, never `bootstrap_component.py`'s own staged driver, per the standing `D58` exception); `spec-bundle-assembler` is re-authored and re-verified once this fix is in place.
