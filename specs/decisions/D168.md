# D168 — secret-scanner delegates detection to detect-secrets and gains a fail-closed allowlist

## Context

A real `hotdocs generate` recorded 36 secret-scan matches for a repository
holding no real secret, so every component's scan was `flagged` and
`hotdocs verify` could never report ready. The matches were identifiers
and paths such as `gate_version=GATE_VERSION`. Underneath sat a
statistical flaw in the hand-built entropy check. A 20-character window
has at most log2(20) = 4.32 bits per character, so the 4.0 threshold
needs about 16 distinct characters: identifiers clear it. Random hex
cannot clear it at all, because a 16-symbol alphabet tops out at exactly
4.0 and random strings fall short. In a simulation, 0% of random hex
secrets and about 66% of random 20-character base64 windows reached
it. The pattern database that `R-SECRET-001` required from a maintained
external source had never been supplied (`secret_scanner@0.0.0`), so
the repository was scanned by that check alone, and it missed most of the
deliberately planted fixtures.

## Decision

Detection is `detect-secrets==1.5.0`. Run over the same repository, with
all plugins but the keyword and public-IP detectors, it reported 11
findings instead of 36: ten planted test fixtures and git's well-known
empty-tree hash, with no suppression filters needed. The scan now covers
every text file in the repository, with no exception for the scanner's
own tests, skipping only `.git`, caches, the virtual environment, and
non-UTF-8 files.

Suppression is a committed allowlist, `.secret-allowlist.json`, built so
that the only way a finding disappears is a person reading it and
committing a hash:

- an entry matches on exact file, exact secret type, and exact SHA-1 of
  the secret: no globs, directories, or patterns;
- `planted-fixture` entries are honored only under `verification/` and
  `specs/`; `public-constant` entries only for a hex string;
- the file is scanned like any other, and stores hashes as `sha1:…` so
  it does not flag itself;
- anything malformed, unknown, or out of policy invalidates the **whole**
  list, reports every finding, and adds an `allowlist-invalid` match;
- every suppression is listed in the result, and unmatched entries too;
- scan results never carry a secret or its hash. `propose` prints
  candidate entries for a person to review and never writes the file.

## Known gaps, accepted

`KeywordDetector` is off. It catches the one thing entropy cannot, a
low-entropy password such as `password = "hunter2"`, but flagged 35 lines
here, nearly all `"secret_scanner": "secret_scanner@0.0.0"`, and 9 even
after excluding that name. Constant noise trains reviewers to approve
without reading, which undermines the allowlist. The entropy plugins
also read quoted strings only, so an unquoted random token is missed.
Separately, `provenance-checker` reuses the scan stored with a
component's provenance, so a secret added after a component was generated
is not seen by `hotdocs verify` until it is regenerated.

`VAR-SECRET-PATTERNS-PATH` and its database format are removed.

## First build

Round 1 of the rebuilt scanner passed 11 of 13 criteria at
`mutation_score` 1.0. Both failures were spec gaps: a test stand-in
embedded a temporary-directory path, which the entropy detector
rightly flagged (the instruction to read such values from an
environment variable had been lost in trimming and is restored), and
the spec never said whether `scan` returns an object or a dict, which
`library.md` now pins to an object with `to_dict()`.
