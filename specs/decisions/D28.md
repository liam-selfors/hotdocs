# D28 — R-LINT-022 codifies `SPEC_GUIDELINES.md` §4's decomposition signal as an actual lint finding

## Context

Proposal 3 from a simplification/user-friendliness review. `SPEC_GUIDELINES.md`
§4 (written during `D25`) describes the decomposition signal well — two
independent size-cap dimensions crowding their warn thresholds for the
same component at once — but nothing in `spec_linter.py` ever detected
it as its own finding. Across this session it had to be noticed by
eyeballing separate `R-LINT-012` warning lines and recognizing the
correlation by hand, three separate times.

## Decision

New `R-LINT-022`: when two or more `R-LINT-012` dimensions are over
their *warn* threshold for the same component at once, emit one
distinct warning naming which dimensions and pointing at
`SPEC_GUIDELINES.md` §4 — advisory only, never a hard failure,
deliberately keyed off *warn* rather than hard-fail so the signal
surfaces before a hard-fail forces the question (the way `D25`'s own
`merge-orchestrator` extraction happened only after the fact).

Implemented in the real `gen/spec-linter/spec_linter.py`
(`rule_decomposition_signal`, sharing its measurement computation with
`rule_size_caps` via a new `_size_measurements` helper so the two rules
can't silently drift apart on the same numbers) and covered by two real
pytest tests, per this project's standing discipline. Run against the
real corpus, it fires exactly where expected: `merge-orchestrator`
(`fan_out` + `spec_bundle_words`) and `spec-linter` itself
(`generated_code_loc` + `requirement_count` + `spec_bundle_words`).

## Consequences

The methodology now partially enforces its own best-practice guidance
instead of relying on a human to notice the correlation.

See `specs/components/spec-linter/requirements/R-LINT-022.md` for the
current, authoritative rule.
