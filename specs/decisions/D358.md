# D358 — hotdocs is packaged with its tool root inside the package

## Context

`hotdocs` ran only from an editable install of a checkout: the entry point
loaded `gen/hotdocs-cli/` from the repository, and every component finds the
tool root as the parent of the nearest directory named `gen` above its own
file (`D199`). At run time the components read four things from the tool
root: `gen/`, `pipeline/criterion-compiler/`, `examples/slugify/` (for
`hotdocs init --example`) and `requirements.txt` (`hotdocs init`'s
prerequisite check, `D203`). None of them writes there.

## Decision

The PyPI package `hotdocs` holds `hotdocs/_entry.py` (the unchanged
`tools/hotdocs_entry.py`) and the tool root at `hotdocs/_tool/`, which holds
`gen/`, `pipeline/`, `examples/` and `requirements.txt` in their checkout
layout, provenance manifests included. The entry point uses `_tool/` beside
itself when it exists, else the checkout, so editable installs still work and
no component changes. `tools/build_dist.py` stages and builds the sdist and
wheel, the version coming from `pyproject.toml` and the dependencies from
`requirements.txt`'s exact pins, kept exact so an installed tool runs what its
provenance records. `tools/release_check.py` is the gate before an upload: it
installs the wheel into a fresh environment, makes the installed package
read-only, and runs the fresh-project check with it. Not shipped: the tool's
own specs, verification suites, notes and hand tools, since a project reads
its own specs from its repository.

## Consequences

`pipx install hotdocs` and `uv tool install hotdocs` give a working tool with
no checkout. A Homebrew formula for a personal tap installs the same wheel
into a virtual environment. Publishing needs a PyPI token, and the name
`hotdocs` was free on PyPI when this was written.
