# D151 — a brand-new already-sealed component still read as a false transition, because non-existence was treated as not-sealed

## Context

Thirtieth `review-packet-builder` retry (after `D150`'s flat-markdown
fix): 11 of 12 pass, `mutation_score=1.0`. The one remaining failure
is the identical defect `D147` already diagnosed once — a repo with
exactly one commit, whose component is already `sealed: true` from
that one and only commit, expected `exemption_changes.sealed == []`
but got `["comp-main-foo"]` — but `D147`'s own fix did not actually
close it. Direct inspection of this round's correct, faithful
implementation of `D147`'s prescribed rule (`git show <base>:<path>`
to read content at the base, `None` meaning "doesn't exist") shows
why: `_is_sealed(None)` correctly returns `False` ("not sealed"), so
`(not base_sealed) and head_sealed` evaluates to `True` whether the
base reading is "exists, and reads `sealed: false`" (a genuine prior
unsealed state) or "doesn't exist at all" (no prior state of any
kind) — `D147`'s own prose ("doesn't exist... is already the correct
complete signal") was simply wrong: it collapses exactly the
distinction the whole fix was supposed to draw. The candidate
followed the prescribed rule faithfully; the rule itself still had
the bug.

## Decision

`R-PACKET-007` corrected: a `sealed` transition requires three
conditions, not two — the file must have **existed** at the base
(non-`None` content, not merely "read as not sealed"), read
`sealed: false`/absent there, and read `sealed: true` at `HEAD`.
Non-existence at the base now explicitly excludes a component from
`sealed` rather than being treated as a positive "not sealed" signal.
`review-packet-builder` is retried next.
