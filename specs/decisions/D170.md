# D170 — Sealed components get their own provenance file, which defines their ownership

## Context

`D166` recorded that a sealed component never receives a
`.provenance.json` from `component-gate-runner`, so `provenance-tracker`
reports it not ready forever. Looking closer found it worse: no layer
supported sealed components end to end. `component-gate-runner`'s
`R-GATE-007` said to re-run the characterization tests at `source_path`,
but `verifier-orchestrator` had no notion of `source_path` at all
(`verify("comp-criterion-compiler")` reported interface drift and failed
all fifteen criteria for lack of code under `gen/`), and nothing recorded
who owns a sealed component or what state it was last verified in.
`.provenance.json` is the wrong file for it regardless: its fields
describe a generation (model, prompt, spec hash), and a sealed
component's code was never generated.

## Decision

A sealed component carries `.sealed-provenance.json` at its `source_path`
— next to the code it attests, so it travels with it. It holds the
component's `owners`, a SHA-256 over the files under `source_path`
(excluding the manifest itself and `__pycache__`), the verifier version,
and the characterization verdict for exactly that source. Every field
is constrained and none is free text; any deviation makes the whole
manifest invalid and unhonored (the allowlist lesson of `D168`: exact
keys, fail closed). `provenance-writer` owns the schema and writes it;
`provenance-checker` owns the one definition of a sealed key (owners,
hash, verifier version) and the check; `component-gate-runner` writes it
after re-running the characterization tests; `provenance-tracker`
treats a sealed component as ready only on a valid, current, passing
manifest whose recorded owners equal the owners in `component.md`.

Ownership is therefore a checked fact, not a convention: changing a
sealed component's `owners` makes its manifest stale, and only a person
re-running `hotdocs generate` for it (an action attributable to them in
the commit that updates the manifest) makes it ready again.

## Found regenerating `provenance-checker`

The first round passed `R-PROVCHECK-007` and seven others and failed
three of `AC-PROVCHECK-012`'s tests. Two snapshotted the repository to
prove the check wrote nothing and tripped on the `__pycache__` that
importing a faked dependency creates (the third time this session; the
criterion now excludes it by name). The third expected a
`characterization_failed` result to still carry the manifest's
`verification_report`; the candidate returned `null` for every field on
every miss. The candidate had the better reading: a manifest that is
not a current, passing hit is not evidence, so none of it feeds a
readiness result. `SealedCheckResult.md` and `R-PROVCHECK-008` now say
so.

The round after found `AC-PROVCHECK-004` and `-005`, older criteria,
failing: the test for "`VAR-TRUST-JUDGE-PROVENANCE` is false" never set
the variable, assuming absent meant false, while its declaration makes
absent mean `true`. Both criteria now name the environment variable the
test sets (`D164`'s `VAR_<NAME>` rule).

## And the capability half of the same component

`provenance-tracker`'s third regeneration passed the new sealed criterion
but failed `AC-TRACK-010`: the candidate called only `run_capability_gates`
and never `check_capability_provenance`, so a capability miss with no
model was not a usage error. `R-TRACK-010` never stated the call order,
and its worked snippet still showed the signature from before `D174`
(`judge=`, `test_author=`), where the capability component now takes
`model`, `seed`, and `llm_backend`. It now lists the three steps in order
with the current signature, matching `capability-scenario-verifier`'s own
`interface/library.md`.
