# D158 — verifier-orchestrator's test runs need a timeout, and a timed-out mutant counts as killed

## Context

`provenance-tracker-ui`'s third bootstrap round ran for over forty-five
minutes instead of the usual five to ten, while the machine ran
critically short of memory. One `pytest` process from the
mutation-scoring pass had been running for twenty-four minutes against
a single mutant. The candidate's CLI parser advances an index inside
`while i < len(rest)`; an arithmetic mutation turning that index's
`+ 1` into `- 1` makes the loop never terminate. `verifier-orchestrator`
runs every test suite with no timeout at all (`_run_pytest` is a bare
`subprocess.run`), so a single such mutant stalls verification
indefinitely. Any candidate containing a counting loop, which is most
CLI parsers, is exposed.

Standard mutation-testing practice bounds every mutant run by a
multiple of the unmutated suite's own run time and counts a timeout as
a killed mutant: the behavior visibly changed, and the tests noticed by
never completing. Counting it as anything else would also depress
`mutation_score` for a reason no better test could fix.

The stalled run was stopped by hand; its score could not have been
trusted anyway.

## Decision

New `R-VERIFY-014`/`AC-VERIFY-016`: every test run gets a wall-clock
timeout of 10 seconds or ten times the unmutated suite's own run time,
whichever is larger, and the whole process tree is killed when it
fires. A timed-out mutant counts as killed; a timed-out run on
unmutated code fails that criterion. `verifier-orchestrator` is
regenerated directly against the real repository, as it cannot verify
itself through `bootstrap_component.py`, and validated by its own
hand-maintained suite plus a new looping-mutant fixture.
