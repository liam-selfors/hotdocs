# D77 — spec-linter's R-LINT-022 crowding signal is accepted, not a split candidate

## Context

`spec-linter` crowds four independent `SPEC_GUIDELINES.md` §4 size dimensions at their *warn* thresholds at once (`generated_code_loc`, `requirement_count`, `acceptance_count`, `component_doc_words`) — the exact signal `R-LINT-022` (`D15`) exists to surface, and the same shape of signal `D14` and `D76` each resolved by extracting a cohesive sub-responsibility out of `merge-orchestrator`. Unlike those two cases, this conclusion had never been given its own decision record — it lived only as unattributed prose in `SPEC_GUIDELINES.md` §4 and `notes/component-sizing-playbook.md`, a real judgment call (the opposite conclusion — split it — was a live, reasonable option) left untracked.

## Decision

No split. `spec-linter` is a single-pass structural linter whose rule count, generated code, and spec bundle all grow together because each new `R-LINT-<N>` rule is a genuinely separate, independent check against `SPEC_GUIDELINES.md`'s own rules — not a second responsibility hiding inside a thin coordinator, the shape `D14`/`D76` each found and extracted. The test `notes/component-sizing-playbook.md`'s Step 3 already states applies here: can this component's behavior honestly be split into two different one-sentence "why does this exist" statements, each serving a materially different consumer or capability? No — every rule here serves the same one consumer (a caller wanting to know whether a spec bundle is structurally valid before anything downstream runs) and the same one capability (`P-AMBIGUITY-GATE`). Splitting a single-pass linter into sub-checkers for no architectural reason would be premature abstraction wearing a size-cap excuse, the same posture `D4`/`D6` already reject. The near-misses are accepted as the honest cost of a cohesive component with many rules, not evidence the caps themselves are miscalibrated.
