# D85 — failure_detail's expected/actual values must be their original Python type, never raw strings

## Context

A real `generate()` candidate for `verifier-orchestrator` parsed a compiled criterion's failing assertion for `failure_detail.expected`/`.actual` by extracting the raw substrings pytest's own failure text renders — `'5'` rather than `5`. `VerificationReport.md`'s own worked example already shows these as JSON numbers, and `AC-VERIFY-013`'s Gherkin already says "its `failure_detail.expected` is `5`," but `R-VERIFY-012` never stated the type requirement explicitly, only implied it through an example.

## Decision

`failure_detail.expected`/`.actual` MUST carry each compared value as its original Python type (int, float, bool, `None`, or string), never a raw string rendering of a non-string value — recovered via the located substring (e.g. `ast.literal_eval`), not left as whatever text pytest's own failure output happened to print.
