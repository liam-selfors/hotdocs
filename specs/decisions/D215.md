# D215 — A usage card names its module's directory, and the bootstrap generates without the target's old code

## Context

Regenerating `spec-bundle-assembler` for `D213` (seed 54, mutation 1.0)
failed one criterion: `R-ASSEMBLE-011` asked for a dependency's
"currently-importable module path", which the candidate gave as the
directory `legacy/bar/` and the generated test checked as the file
`legacy/bar/bar.py`. Both readings fit the words.

Separately, `tools/bootstrap_component.py` left a target out of its
sandbox so the candidate is never tested beside old code, but the
sandbox's own `spec-linter` imports `graph-query-engine` when it loads,
so regenerating `graph-query-engine` (seed 4) failed before generating
anything.

## Decision

`R-ASSEMBLE-011` names the parts of a card: the module name, the
directory relative to `repo_root` with a trailing `/`, and for each public
callable its name, `inspect.signature` text and first docstring line.
`AC-ASSEMBLE-011` checks each part.

The bootstrap keeps a target that the machinery itself needs, and
deletes it from the sandbox immediately before generation, so the
candidate still never runs beside old code.

`R-ASSEMBLE-014`'s layout is exact too: a blank line, the
`## Implements:` line, a blank line, then the document. Two generated
tests (seeds 51 and 55) read "after a line" as "on the next line".

Seeds 55 to 57 lost one to six criteria each to tests that imported
`spec_linter` by name. `test-author`'s own prompt requires a test to lint
its fixture first (`R-AUTHOR-015`) while saying no dependency is
importable by name (`R-AUTHOR-010`), and the fixture section's "never
lints anything itself" lost to the prompt. The section now gives the
literal way to load `spec-linter` from the tool root beside the module
under test, as the assembler itself does.

## Consequences

No change to the hash, which reads files, not cards.
