# D200 — corpus-graph-builder gets concrete criteria and reads manifests as JSON

## Context

`corpus-graph-builder` was generated once, before `test-author`
existed, and was verified only by a hand-written suite. Running
`hotdocs corpus-graph build` from a project (`D199`) found two defects:
it imported `graph_query_engine` by bare name, and it copied
`component_provenance`'s typed columns into the graph, so a manifest's
`generated_at`, parsed by DuckDB into a timestamp, could not be written
as JSON. A first regeneration then failed because its acceptance
criteria named no concrete corpus ("two capabilities, three
components"), so the generated tests guessed a file layout and faked
`graph-query-engine` badly. `R-GRAPH-007` ("runs on every merge to
`main`") described the CI, not anything this component's code does.

## Decision

Each criterion now states a concrete corpus, in the layout
`graph-query-engine`'s views read, and tests run against the real
engine, found through the tool root. Nodes, edges, orphan rates and
size status still come from the shared views (`D13`), but a node's
verification and provenance are read from the manifest file itself, so
every value is the file's own JSON. `graph-query-engine` is loaded by
path (`R-GRAPH-010`). `R-GRAPH-007` now specifies the CLI, and the
rebuild cadence moves to the component's scope as the CI's job.

## Consequences

`hotdocs corpus-graph build` works from a project, and with it the
tracker page and the docs site that read its output. The output
format is unchanged for its readers.
