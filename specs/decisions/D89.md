# D89 — capability-scenario-verifier gets its own provenance, keyed on realizing components' actual current content

## Context

Every other check `hotdocs verify` (`D88`) reports on has its own provenance record to read — capability-scenario verification did not, so there was no way to know whether a capability's last real run is still current, only whether it had ever been run at all. The naive fix — key it on a hash of its realizing components' `spec_bundle_hash`es, mirroring component provenance — would reopen the exact blind spot this check exists to close (`D2`): a parent component changing something undeclared, invisible to spec-level hashing, that a dependent silently relies on. Pairwise parent/child provenance checks at generation time were considered and rejected for the same reason — multi-component interactions and whole-system product properties aren't decomposable into a set of pairwise facts.

## Decision

`CapabilityProvenance` is keyed on a hash of every realizing component's **actual current `gen/` content** (not its `spec_bundle_hash`) — invalidated by any real change anywhere in the capability's realizing set, whether or not blast-radius analysis or a declared `depends_on_guarantees` edge would have flagged it, strictly more conservative than relying on either. `capability-scenario-verifier` checks this provenance first on `hotdocs check-capability <capability-id>` (mirroring `component-gate-runner`'s own provenance-check-then-run pattern): a hit skips re-running the scenarios; a miss runs `run_capability_scenarios` and writes a fresh record. `provenance-tracker`'s `hotdocs verify` (`D88`) reads this the same uniform way it reads component provenance.
