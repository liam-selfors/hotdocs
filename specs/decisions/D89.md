# D89 — Piece 4: the actual diagnostic, and the capability gap it exposed

## Context

`D87`/`D88` made decision supersession real and queryable. The user's
original ask was for the actual payoff: a way to find spec files whose
own last-modified commit predates a decision that superseded something
they depend on or cite — candidates for staleness review that nothing
in the corpus could surface before.

No existing component fits this boundary. `spec-linter` never reads
git history. `impact-analyzer` reasons forward from a spec diff
(what needs regenerating), not backward from existing content against
decision history. `spec-completeness-assistant` judges whether a *new*
change is complete, not whether *old* content has drifted. Checking
`SPEC_GUIDELINES.md` §10's reuse discipline before writing anything:
`impact-analyzer` already has git plumbing (`_run_git`, a
`merge-base`-with-default-branch helper), but not either specific
operation this needs (a path's last-touching commit; an ancestry check
between two arbitrary commits) — genuinely new, not a duplicate to
avoid.

Assigning this a product capability (`realizes`, required for any
non-sealed component) surfaced a real gap of its own: none of the four
existing capabilities (`P-ZERO-EDIT`, `P-AMBIGUITY-GATE`,
`P-COMPLIANCE-GATE`, `P-MERGE-VISIBILITY`) describe a concern about the
corpus's own decision history staying internally consistent over time.
Forcing this into one of them (`P-AMBIGUITY-GATE` was the closest,
loosely) would have mischaracterized what it actually does.

## Decision

New component `decision-drift-detector`, `depends_on: [comp-
graph-query-engine]` only. `R-DRIFT-001` walks a citation's
`supersedes` chain in `decision_lineage` to the latest superseder, if
any; `R-DRIFT-002` compares the citing file's own last-touching commit
against that superseder's `last_ratified_commit` via
`git merge-base --is-ancestor` — ancestry, never a timestamp
comparison, since a non-linear history has no trustworthy order by
date alone. Purely diagnostic (`find_decision_drift(repo_root) ->
DriftReport`): no mechanism anywhere calls it as a merge precondition.

New product capability `P-DECISION-INTEGRITY` ("The Spec Corpus Stays
Honest About Its Own Decision History"), registered alongside
`spec-completeness-assistant` in `pipeline-decomposition.md`'s
"Advisory tooling" table (renamed from "Feature-branch tooling," since
this component is corpus-wide, not scoped to one feature branch).

Caught and fixed two structural issues while writing this against the
real, already-built `spec-linter`: `R-LINT-008`/`009` require
`Covers:` to name exactly one requirement, not a list (an initial
draft tried to cover two requirements from one acceptance criterion);
`R-LINT-024` — already a real rule, squarely in the spirit of this
whole session's direction — forbids a decision citation inside a
`Purpose` section, catching one in this component's own first draft.

## Consequences

Fourth and final piece of the user-scoped initiative (`D86`-`D89`
together). Fully spec-only — no `gen/` or `verification/` yet,
consistent with every other not-yet-built component. The real build
(a `generate()` call, real verification, real swap-in) is queued like
every other pending component this session, blocked on the same
exhausted API credits as `verifier-orchestrator`/`provenance-writer`'s
other pending work.
