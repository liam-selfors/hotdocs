# D13 — graph-query-engine's shared views are the one query surface every adopting component uses

## Context

Several components each needed the same graph-shaped facts about the corpus (dependency relationships, per-component size, provenance) and were each starting to reimplement the same scans independently — the exact risk of two divergent definitions of one fact. Decision records are also part of this graph: a decision's own supersession/dependency relationships are structurally identical to every other typed relationship here, and a first design giving them a separate, parallel view (reasoned at the time as lower-risk) didn't hold up once actually tested — the existing node/edge shapes already fit a decision record exactly, no new column needed.

## Decision

`graph-query-engine` owns a shared set of real, generated DuckDB views, embedded and local (no server, no network), using two community extensions: `yaml`'s `read_yaml_frontmatter()` (frontmatter directly out of existing spec files, native glob support) and `duckpgq` (SQL/PGQ graph-pattern matching for transitive reachability/cycle detection, instead of hand-rolled recursive CTEs). The views:

- `nodes`: one row per spec id across eight kinds (`component`, `capability`, `var`, `decision`, `guarantee`, `requirement`, `acceptance`, `capability_scenario`).
- `edges`: one row per `(source_id, target_id, edge_type)`, covering `depends_on`/`realizes`/`uses_var`/`depends_on_guarantees`/`covers`/`supersedes`/`builds_on`.
- `component_docs`, `component_context` (a dependency's Purpose text only, narrower than its full interface), `component_provenance`, `component_size` (word counts, matching spec-linter's own measurement exactly).
- `decision_lineage`: just `id` + `last_ratified_commit` — the one decision-specific fact with no equivalent column in `nodes`/`edges`.

Any component needing a graph-shaped fact queries these views rather than re-implementing the scan.

## Consequences

Technical rule, load-bearing: `read_yaml_frontmatter`'s struct-column auto-detection silently drops a column absent from every file in a glob at once (a bind-time error, not a null) — any sparse/optional frontmatter field (`supersedes`, `builds_on`, `uses_var`, `depends_on_guarantees`, `last_ratified_commit`) must be extracted via `read_text` + regex instead, never via automatic schema detection.
