# D127 — Land `provenance-tracker` at 5/7, document two remaining known limitations

After `D119`/`D120` (real `dependency_interfaces`) and `D123`–`D126`
(mutation-score union fix, `run_capability_gates` naming, fake-arity
alias resolution), `provenance-tracker` reached `mutation_score=1.0`
and 5/7 behaviorally passing (`AC-TRACK-004/007/008/011/012`).
`AC-TRACK-009` and `AC-TRACK-010` still fail after four retries
(seeds 1–4) that each surfaced and fixed a different real defect.
Direct sandbox inspection (running the candidate's own `check_readiness`
against each test's exact fixture, outside pytest) shows the candidate's
behavior is correct per `R-TRACK-010`'s check-then-run design; the two
failures are a minor literal gap in the candidate's own message
specificity and a test-authoring fixture bug, respectively. Given
`D95`–`D126` already spans 32 decisions for this one component and the
standing guidance to document known limitations rather than chase
every last gap indefinitely, this decision lands the component now
and records both as known limitations for a future retry.

**AC-TRACK-009 (minor real gap, candidate):** `R-TRACK-009` requires
`not_ready_reasons` to carry "which component, which check failed."
The candidate's message for a failing hit is a single generic string
("provenance hit but verification/scan not passing") regardless of
whether `verification_report`, `license_scan`, or `secret_scan` was
the actual cause, and never names the specific failing requirement id.
This is a real, literal shortfall against `R-TRACK-009`'s own text,
not merely the stricter test assertion. Left as a known limitation
rather than retried immediately: a retry risks the same shape of
regression chase seen across `D123`–`D126` for comparatively small
payoff, since `ready=False` and the component name are both already
correctly surfaced.

**AC-TRACK-010 (test-authoring fixture bug, not a candidate bug):**
Both failing scenarios in `AC-TRACK-010`'s generated test set up
`check_capability_provenance` to return `hit=True` unconditionally,
including in the two scenarios ("all pass" and "the capability run
fails") that are meant to exercise `run_capability_gates`'s result.
Per `R-TRACK-010`'s check-then-run design, a `hit=True` from
`check_capability_provenance` is a deliberate short-circuit:
`run_capability_gates` is correctly never called. Confirmed directly:
calling `check_readiness` against each test's exact fixture returns
the check-then-run-correct result in both cases — the capability is
judged ready in the "all pass" case (via the hit, never reaching
`run_calls.log`) and, in the "run fails" case, likewise judged ready
via the hit, since the injected failure lives in `run_capability_gates`,
which the hit makes unreachable. The fixtures needed `hit=False` from
`check_capability_provenance` to route through `run_capability_gates`
at all. This is a reusable test-authoring gap (any check-then-run
dependency shape — this corpus's recurring convention, mirrored in
`provenance-checker` itself — can hit it again) but is left
undocumented in `test-author`'s own spec for now rather than adding a
new requirement under `test-author`'s `R-LINT-012` word budget, which
has already needed trimming multiple times this session (`D126`
entry).

No spec or candidate change in this decision. `component.md`'s
changelog and `model_pin: claude-sonnet-5` are updated separately to
record the landing.
