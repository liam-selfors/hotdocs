# D195 — The secret allowlist is sealed by a hash in a ratified decision

## Context

`.secret-allowlist.json` (`D168`) suppresses secret-scan findings, so
whoever can edit it can silence the gate: a developer in a hurry, or one
of the tool's own agents making a failing scan pass. A file on the user's
disk cannot be made impossible to edit.

## Decision

The scanner honors a non-empty allowlist only if the SHA-256 of its exact
bytes equals `allowlist_sha256` in the highest-numbered ratified decision
that carries that key. Any other state invalidates the whole list and adds
an `allowlist-invalid` match, so the gate fails closed. An empty list needs
no decision, since it allows nothing.

Changing the list therefore takes two steps, a new list and a new decision
recording its hash, and the decision is a reviewed, numbered, git-tracked
record. An edit alone is inert, not silent.

## Consequences

- This is tamper-evident, not tamper-proof: someone who edits both files
  still passes, but the change shows in review and history.
- Review rules should treat `.secret-allowlist.json` and decisions that
  carry `allowlist_sha256` as protected paths. The generator writes only
  under `gen/` and `verification/`, so generated code never touches either.
- `propose` stays read-only; its output is reviewed, then written with a
  decision.
- `gate_version` becomes `secret_scanner@3.1.0+detect-secrets.<V>`.
