# D1 — One file per addressable unit, not one document type

## Context

A component's spec needs exact, file-level content hashing for blast-radius and cache-key purposes, and must avoid parsing block boundaries inside a shared file.

## Decision

Each component directory holds `component.md` (root: frontmatter + Purpose/Scope/...), one file per requirement (`requirements/R-<comp>-NNN.md`), one per acceptance criterion (`acceptance/AC-<comp>-NNN.md`), `interface/` split by kind (`cli.md`, `library.md`, one file per type under `data/`), and `constraints.md` as a single flat file (nothing addresses one constraint by id). Frontmatter lives only on `component.md`; every unit file's identity is its filename, carrying no frontmatter of its own. Capability scenarios stay inline per product-capability file; `specs/vars/` stays one file per variable.

## Consequences

Content hashing is exact (file-level), not approximated by block-boundary parsing.
