# D345 — The environment is part of provenance; an environment-only miss is re-verified before regenerating

## Context

Verification proves a component's code against its tests in one
environment: an interpreter version and a set of installed packages. A
different Python or a different package can break code that passed, so
a provenance key that ignores the environment overstates what was
proven. Recording it means every environment change misses, and a miss
has meant regeneration, a model call per component, although the code
was written from the spec and usually still passes.

## Decision

- The `python` adapter's `provision` reports `versions` with the full
  interpreter version, `"python": "3.14.6"`, and `"packages"`,
  `"sha256:"` plus the SHA-256 of the interpreter environment's installed
  distributions as sorted `name==version` lines, so packages nobody
  declared count too; both reach provenance through
  `VerificationReport.assets`.
- `provenance-checker` reports a miss caused only by an asset's
  `versions` or `lockfile_sha256` with the reason `environment differs`.
- On that reason `component-gate-runner` first re-verifies the committed
  code with the judge and test author it always uses, so `llm-judge`
  criteria are judged again and only a stale test is authored; when
  verification, license and secret checks pass it re-records
  provenance, without regenerating. Any other outcome goes to generation
  as before.
- A project may pin its interpreter in
  `environments/python/python-version`; `provision` then fails with
  `python environment: needs Python <pin>, found <version>` when the
  interpreter differs, so machines on different releases do not keep
  invalidating each other's manifests.

## Consequences

A Python patch release or a package change re-verifies every component
once, regenerating none that still pass; only `llm-judge` criteria call
a model. Supersedes `D344`'s plan to record only
major.minor, which never shipped.
