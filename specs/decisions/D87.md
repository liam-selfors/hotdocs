# D87 — merge-orchestrator is removed — a merge is a developer confirming hotdocs verify passes, then committing directly

## Context

`D86` already reduced `merge-orchestrator` to a single remaining job: checking whether every impacted component already has valid provenance, blocking if not. Once that is the *entire* job, an orchestrating component adds nothing a direct query can't answer on its own — "will a merge pass" and "does every impacted component (and, `D89`, every intersecting capability) have current, passing provenance" are the same question. The pieces `merge-orchestrator` used to coordinate either don't need coordinating anymore (`spec-linter`/`impact-analyzer` are each a direct, standalone check a developer or a git hook can run) or were already independently reachable (the provenance query itself, now `provenance-tracker`'s own job, `D88`).

## Decision

`merge-orchestrator` is deleted — not deprecated, not narrowed further, removed from the corpus entirely, along with `R-MERGE-*`/`AC-MERGE-*` and `comp-merge-orchestrator`. A "merge" is no longer a distinct automated action with its own component: a developer runs `hotdocs verify` (`provenance-tracker`, `D88`) to confirm every component and capability in scope already has current, passing provenance, and — once it does — commits `specs/`, `gen/`, and `verification/` directly, with ordinary version control. Nothing requires a human to run `verify` immediately before committing or forbids committing without it; it is a confirmation tool, not a technical gate enforced by any component standing between a developer and `git commit`. The actual enforcement this corpus still offers is `provenance-checker`'s own precondition on trusting stale work, unchanged, and whatever branch-protection a project layers on top of its own git history — outside this corpus's own scope, same as it always was.
