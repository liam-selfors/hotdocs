# D190 — verifier-orchestrator's CLI becomes hotdocs verify-component

## Context

Two components documented the verb `hotdocs verify`: `provenance-tracker`
(whole-corpus or blast-radius readiness, the check `D93` made the
canonical `hotdocs verify`) and `verifier-orchestrator` (verify one
component by id). A single `hotdocs` entry point cannot route one verb
to two programs. Looking at the second CLI also showed it was uncovered
by any requirement, despite `D162`, and that asking it to verify a
component that does not exist exited `1`, a failed verdict, instead of
`2`, a usage error, unlike every other CLI here.

## Decision

`verifier-orchestrator`'s command is `hotdocs verify-component
<component-id>`. `R-VERIFY-018` and `AC-VERIFY-021` cover its argument
parsing and exit codes, including the unknown-component case, which
becomes a usage error. Verification behavior is unchanged, so
`GATE_VERSION` is not bumped: only the command name, the usage message,
and one exit code move.

## A second gap, found regenerating

The regeneration this decision required returned `verify`'s report as a
plain dict, and 19 of the 29 hand tests failed on `report.criteria`. The
spec never said whether `verify` returns an object or a dict: every
consumer here (the hand suites, the bootstrap driver, the CLI) reads
attributes, and the previous implementation returned an object, so the
choice had been made by accident of one generation and carried by
convention. `interface/library.md` now states it: an object with
attribute access and a `to_dict()`.

The second regeneration still failed 12 of 29: each `criteria` entry came
back as a `CriterionResult` object, where every consumer indexes entries
as dicts (`c["result"]`). The spec had pinned only the report's own type,
so `library.md` now pins entries and `requirement_results` as plain dicts.
