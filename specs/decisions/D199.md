# D199 — The tool's components stay in the tool; a project holds only its own

## Context

`hotdocs init` copied the tool's own components into each project's
`gen/` and `pipeline/` (`D185`), because every component loads its
dependencies by path from `<repo_root>/gen/<slug>/`. A project's `gen/`
therefore mixed about twenty tool components with the user's own, every
lint, scan and review saw them, and upgrading the tool meant copying
them again. It also put the git empty-tree hash into every project,
which is why `D197` had `init` seed a sealed allowlist.

Loading from `<repo_root>` cannot simply be replaced: every generated
test fakes a dependency by writing a module under a temporary
`repo_root`, so that path must keep winning.

## Decision

A component loads a dependency from `<repo_root>/<dir>/` when that
directory exists, and otherwise from `<tool_root>/<dir>/`. `<dir>` is
`gen/<slug>`, or `pipeline/criterion-compiler` for the compiler.
`<tool_root>` is the parent of the nearest directory named `gen` above
the loading module's own file, so it is found without configuration
and works for flat and package layouts alike. Inside this repository
both roots are the same directory.

`init` no longer copies `gen/` or `pipeline/`. It creates an empty
`gen/` and an empty allowlist, which needs no seal under `D195`, so it
writes no decision; `D197`'s seeded entry is withdrawn. `hotdocs lint`
fails a project component whose slug is also a tool component's, since
the project's copy would shadow the tool's.

## Consequences

A project's `gen/` holds only its own components, and upgrading the
tool is upgrading the install. Components that reported a missing
dependency now do so only when neither root has it. The tool still
runs from an editable install, since its components are files in the
checkout.

Running the flow from a fresh project found two loads that only ever
worked inside this repository. A regenerated `provenance-tracker` became
a package while `hotdocs-cli` loads its flat file; its spec now requires
one module file. `corpus-graph-builder` imports `graph_query_engine` by
bare name and cannot serialize the timestamp DuckDB returns for a
provenance manifest, so `corpus-graph build`, and the tracker page and
docs site that read its output, fail in any project with a generated
component. Regenerating it needs sharper acceptance criteria first and
is left to its own change.
