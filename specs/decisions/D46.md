# D46 — `VAR-ANTHROPIC-API-KEY`'s resolution mechanism

## Context

`D45` built four Claude Code subagents to simulate `llm-endpoint`'s
real callers without writing a real backend yet. The natural next
question was whether `llm-endpoint` itself could dispatch through the
`claude` CLI's own non-interactive mode (`claude -p`) instead — using
whatever plan is already authenticated, rather than a from-scratch
Anthropic API client.

Tested directly, not assumed: `claude -p "..." --output-format json
--model sonnet` works exactly as hoped — a real, scriptable subprocess
call with explicit model selection and structured JSON output,
no `.claude/agents/*.md` file needed at all if the system prompt is
passed via `--system-prompt`/`--append-system-prompt` instead. But the
same test call's own output disclosed the one fact that actually
decides how it bills: `"apiKeySource":"ANTHROPIC_API_KEY"` and a real
`total_cost_usd` — because `ANTHROPIC_API_KEY` was set in the calling
environment, which **unconditionally** overrides a claude.ai/Pro-plan
login whenever present, confirmed by the CLI's own warning text, not
assumed.

Whether a given environment bills a given `complete()` call against a
Pro/Max plan or direct per-token API usage was never a fact this spec
could settle on its own — it depends on whether `ANTHROPIC_API_KEY` is
set in whatever environment actually invokes `llm-endpoint`, which is
real infrastructure state, out of this methodology's scope by
`SPEC_GUIDELINES.md` §9 the same way any other config *value* is.

## Decision

`VAR-ANTHROPIC-API-KEY` (`specs/vars/anthropic-api-key.md`) now states
its resolution mechanism explicitly: a direct process-environment
lookup of the OS variable named exactly `ANTHROPIC_API_KEY` — the same
name the Anthropic SDK and the `claude` CLI already read by default, so
this is the credential already present in any environment with either
configured, not a second, separately-provisioned secret. No vault or
secrets-manager indirection — v1's one backend (`R-ENDPOINT-003`) needs
no more than a plain lookup, and building one would be exactly the
premature abstraction `D18`/`D20` already reject elsewhere.

The var's own spec also states, as a fact a caller must confirm for
themselves rather than something this corpus can assert on their
behalf: if the variable is set, it always outranks a separate Pro/Max
plan login in the same environment. A project wanting `llm-endpoint`
calls billed against a subscription plan instead must ensure the
variable is unset wherever `llm-endpoint` actually runs; this project,
having it set, is choosing direct API billing for those calls.

`R-ENDPOINT-003` cross-references the var's own spec for this mechanism
and caveat, rather than restating it — single source of truth for a
fact that belongs to the var's contract, not the component that
consumes it.

## Consequences

`llm-endpoint`'s real implementation, whenever written, has an
unambiguous, already-verified credential-resolution story: read
`ANTHROPIC_API_KEY` from the process environment, nothing more. Whether
a given deployment's own environment happens to have that variable set
— and therefore which billing path it takes — stays, correctly, outside
this corpus's authority: a real fact about real infrastructure, which
`SPEC_GUIDELINES.md` §9 already draws the line at.

This decision does not itself build `llm-endpoint`, and does not change
`D45`'s open item (the four subagent definitions still aren't
reproducible from a clean clone) — a `claude -p`-based real
implementation would resolve that too, by embedding each caller's
system prompt directly in committed code instead of gitignored
`.claude/agents/*.md` files, but that rewrite is not done here.
