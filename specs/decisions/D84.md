# D84 — Applying the pre-generation audit backward, to an already-real component

## Context

The dependency-contract audits that found `D81`/`D82`/`D83` all looked
forward, at not-yet-built components. One of them, auditing
`merge-orchestrator`, also traced back through `capability-scenario-
verifier` (already real and swapped in since `D78`) and found its real
`_dispatch_generated_test` never checks a cache file before calling
`test_author` -- unlike `verifier-orchestrator`'s documented
`R-VERIFY-002` behavior. Nothing in `R-SCENARIO-001` said whether this
was deliberate or an oversight.

Direct investigation found a clean answer: there is no
`verification/<component>/`-shaped path a capability scenario could
anchor a cache file to (it spans the whole assembled system, not one
component), and `test_author` already checks `cache-manager`
internally before any model call (`R-AUTHOR-004`/`005`) -- so a
repeated dispatch for unchanged content is already a fast cache hit
one layer down. No real inefficiency, just an undocumented choice.

Writing this up (alongside `D82`'s bundle-shape fact, already living
in `R-SCENARIO-001`) pushed that file past spec-linter's 500-word
per-file hard-fail threshold -- a real decomposition signal per
`R-LINT-023`'s own design intent (D29: an oversized unit file is a
direct sign it stopped being one atomic fact), not just a budget
problem to route around.

## Decision

Documented the no-cache behavior as deliberate, split into a new
`R-SCENARIO-003` alongside `D82`'s bundle-shape fact (both independent
of `R-SCENARIO-001`'s core dispatch-mechanism statement). New
`AC-SCENARIO-004` and a real test confirm `test_author` is invoked on
every dispatch, never short-circuited. No code change -- the real
component already behaves this way; only the documentation and the
component.md's acceptance-criteria count (three to four) needed
updating.

## Consequences

First instance this session of the audit discipline running
*backward* onto an already-real, previously-verified component rather
than only forward onto not-yet-built ones -- worth keeping as a
standing practice, not a one-off: an undocumented real-code choice is
exactly as much of a risk for a future maintainer as an undocumented
spec gap is for a future `generate()` call, even though nothing here
needed a code fix.
