# D96 — test-author's prompt states this corpus's dynamic, repo_root-relative dependency-loading convention

## Context

The same `provenance-tracker` bootstrap that surfaced `D95` also surfaced a second, distinct real gap in `test-author`: three of its five `AC-TRACK-*` test authorings (`AC-TRACK-004`, `009`, `010`) failed for the same underlying reason, despite `D94`'s nonce-delimited protocol fix working correctly and producing clean, syntactically valid test code every time. Every real component in this corpus resolves its own cross-component dependencies at runtime, dynamically, from `<repo_root>/gen/<dependency-slug>/<module_name>.py` (or the package equivalent) — never via a static top-level `import <dependency>` Python's own import system can find on `sys.path`, and never registered under a predictable module name a test could patch with `sys.modules` tricks or `unittest.mock.patch("<name>.<fn>")`. Nothing in `test-author`'s prompt ever stated this, since `R-AUTHOR-002` deliberately withholds the target component's own `gen/` content and implementation details — but *this* is a corpus-wide structural convention every generated component's test has to work with, not implementation detail specific to one candidate.

Without it, `test-author` guessed three different, each-plausible-looking but wrong strategies: assuming a package submodule path (`provenance_tracker.library`, `AC-TRACK-010`), assuming dependencies are statically importable and therefore patchable by name (`AC-TRACK-009`, `AC-TRACK-010`), and — when it did correctly guess the real dynamic-loading shape for the component under test itself (`AC-TRACK-004`) — reproducing an *almost*-correct version of the loader that omitted the one genuinely non-obvious step every real loader in this corpus already gets right (registering the freshly-created module object in `sys.modules` *before* calling `exec_module`, required because a dataclass's class body resolves its own module via `sys.modules[__module__]` while executing). `AC-TRACK-007`'s separate failure (an unrealistic bare `SimpleNamespace` standing in for a real `GenerationResult`) is not part of this same root cause and is left to the next retry's own feedback, not a spec change.

## Decision

`test-author`'s prompt gains a new, always-included (not bundle-derived, the same "cross-cutting instruction" category `R-GEN-015` already established for `generator`'s own output-layout rule) statement of this corpus's dependency convention: a dependency is never statically importable; the target component's own code resolves it dynamically from `<repo_root>/gen/<slug>/<module_name>.py` (flat) or `<slug>/__init__.py` (package); a test needing to fake a dependency's behavior must write a fake module file at that exact path under a fresh temporary `repo_root` and pass that `repo_root` through to the function under test, never `sys.modules` injection or `unittest.mock.patch` by dependency name. The instruction includes the one correctness-critical step (`sys.modules[module_name] = module` before `exec_module`) as a literal worked snippet, not prose alone, since prose alone already proved insufficient once (`AC-TRACK-004`'s near-miss).

New requirement `R-AUTHOR-010` states this. `test-author` is cold-regenerated a third time against the updated spec bundle; the hand-maintained `AC-AUTHOR-*` suite (mocked-backend verification, `D58`) gains one new criterion (`AC-AUTHOR-010`) asserting the convention text and the worked snippet both appear in the prompt sent. `provenance-tracker`'s `AC-TRACK-004`/`009`/`010` are re-authored and re-verified against the fixed component once both this and `D95` are in place.
