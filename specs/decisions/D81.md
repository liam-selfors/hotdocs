# D81 — A gate version must bump whenever its underlying detection logic changes

## Context

`gate_version` is part of both `cache-manager`'s per-gate cache key and `provenance-checker`'s provenance-hit comparison (`gate_versions`) — either one trusting a stale version number would silently let an already-cached or already-committed result stand in for a gate whose actual detection logic has since changed (e.g. the license scanner's signature database gaining new entries), even though nothing about the spec or generated code changed. `SPEC_GUIDELINES.md` §7 stated the bump rule but had never recorded it as a decision — a real choice, since the alternative (leaving a gate's version static and accepting that a logic update silently goes unreflected in prior cache/provenance entries) was a live option with a real cost trade-off.

## Decision

A gate's own `gate_version` MUST bump whenever its underlying detection logic changes, regardless of whether anything in `specs/` or `gen/` changed. This is what makes a cache hit or a provenance hit trustworthy in the presence of gate logic that evolves independently of the corpus it's gating — without this rule, a cache-manager hit (`gate_version`, `model_pin` as part of the key) or a provenance-checker hit (`gate_versions` comparison) could paper over a genuinely changed risk that a human never asked to skip.
