# D120 — verifier-orchestrator's own module loader must cache by (repo_root, module_name), never module_name alone

## Context

The real retry against `D119`'s fix (`depends_on` gains `comp-spec-bundle-assembler`, `R-VERIFY-009` states the prohibition on a second `CriterionBundle`) passed the new dependency-interfaces test directly, confirming that fix works — but regressed on `AC-VERIFY-004`/`005`, both involving the interface-drift check. Diagnosis: calling the drift check (`check_interface_drift`) directly, outside the full `verify()` pipeline, with the exact same fixture, returned the correct answer — the check's own logic is sound. The real cause is `_loader.load_component_module`'s own `sys.modules[module_name]` cache, keyed by bare module name only. Every real test in this component's own hand-maintained suite verifies a component named `"foo"` against a fresh `tmp_path`; within one pytest session, a later test's `load_component_module(repo_root, "foo")` call silently returned an *earlier* test's already-cached "foo" module instead of loading the current `tmp_path`'s own code — the identical bug class `R-TRACK-011` already closed for `provenance-tracker`'s own loader.

## Decision

New `R-VERIFY-013`: every dynamically loaded module MUST be cached, if at all, by `(repo_root, module_name)`, never `module_name` alone. New `AC-VERIFY-014`. `verifier-orchestrator` is cold-regenerated against this amendment, validated directly against the hand-maintained suite (per `D119`'s own exemption from the full self-verifying bootstrap cycle).
