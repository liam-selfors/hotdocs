# D22 — DuckDB (`yaml` + `duckpgq` extensions) as the local graph-query engine; `impact-analyzer` rebuilt on it

## Context

Grew out of designing how merge/generation tracking should be queryable
(metrics, an eventual UI) into a broader realignment: `impact-analyzer`'s
blast-radius computation and the corpus's dependency graph are the same
kind of problem a real graph-query engine already solves, rather than
bespoke traversal code reinvented per component.

## Decision

**DuckDB**, embedded and local (no server, no network), with two
community extensions: **`yaml`** (`read_yaml_frontmatter()`), which
queries frontmatter directly out of existing spec files with native
glob support — no file restructuring needed, found only after an
initially-wrong WASM-compatibility read was caught and corrected against
raw HTML rather than a markdown-converted summary (which silently drops
SVG check-mark icons). **`duckpgq`** provides SQL/PGQ graph-pattern
matching for traversal — chosen over hand-rolled recursive CTEs for the
same reason `criterion-compiler` exists: a well-defined operation in its
own grammar beats reimplementing it in a general-purpose one.

`impact-analyzer` (`R-IMPACT-009`) is the first component rebuilt on
this engine — an implementation requirement, not a behavioral one;
`R-IMPACT-001`–`008` and `BlastRadiusReport` are unchanged.

**Realignment candidates flagged, not adopted here** (later resolved by
`D24`/`D25`/`D26`/`D27`): `spec-linter`'s graph-shaped rules,
`corpus-graph-builder`'s graph construction, `merge-orchestrator`'s
`R-MERGE-014` capability-intersection lookup.

**Also built in this decision:** the merge-tracking data store, flagged
elsewhere as "not yet speced," was built. `merge-tracker` writes one
`TrackingRecord` per merge attempt to `.hotdocs/tracking/` (new,
gitignored, non-gating), queryable by DuckDB core `read_json` — no
`duckpgq`, since `TrackingRecord` is plain JSON, not graph-shaped. It
depends only on `provenance-writer`, not `merge-orchestrator`,
specifically to avoid a dependency cycle. `merge-tracker-ui` renders it
client-side (later given a serving mechanism by `D26`). New product
capability `P-MERGE-VISIBILITY` names what this pair delivers.

Two real, pre-existing gaps were found and fixed while designing this:
`R-MERGE-005`/`006` only triggered best-of-k's retry on a *verification*
failure, never on `generator`'s own `model_call_error` — a bigger
problem now that `D21` removed `generator`'s own retry; and
`provenance-writer`'s `ProvenanceInputs` type was referenced in three
places but never actually defined.

See `specs/architecture/graph-query-engine.md`,
`specs/components/impact-analyzer/requirements/R-IMPACT-009.md`,
`specs/components/merge-tracker/`, `specs/components/merge-tracker-ui/`,
and `specs/product/merge-visibility.md` for the current, authoritative
rules.
