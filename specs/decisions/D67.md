# D67 — license-scanner's first real generate() call, and a fourth instance of the SPEC_GUIDELINES.md gap

## Context

A real `generate()` call for `license-scanner` produced a genuinely
well-reasoned 503-line candidate: correct 9-token k-gram tokenization
and hashing, correct severity-vs-confidence notification split
(`R-LICENSE-003`), a bounded, never-retried webhook call with proper
failure classification, correct `cache-manager` integration, and an
injectable, versioned reference-corpus design (a JSON file carrying
`block_threshold`/`reporting_floor` alongside its hash entries, with
an environment-variable path override).

One real problem: it defaulted the corpus's lookup path to
`.hotdocs/license_corpus.json`. `SPEC_GUIDELINES.md` §1 defines
`.hotdocs/` as gitignored, local-only, "never read by any gate's
pass/fail decision" — and this corpus's content directly determines
`blocked`. Nothing in `license-scanner`'s own spec named a real
location for this input at all, and (as with `D62`'s output-layout
gap and `D65`'s `depends_on_guarantees` gap) `SPEC_GUIDELINES.md`
itself is never part of any `SpecBundle`, so a candidate reading only
its own spec's bundle had no way to know this path was wrong.

## Decision

New `VAR-LICENSE-CORPUS-PATH`, added to `license-scanner`'s `uses_var`.
`R-LICENSE-001` now states explicitly where the real corpus lives
(that var, never `.hotdocs/`) and that a missing or unreachable corpus
must still produce a real, recorded clean result — never an error,
never a silently-skipped scan, matching the fail-to-empty posture this
corpus already uses elsewhere (`R-GQE-005`/`R-CACHE-004`-style).

The candidate's `gen/license-scanner/` output was deleted before being
committed, never swapped in.

## Consequences

A retry, with this fix in place, is the next real test. This is the
fourth real instance of the same root cause (`D62`, `D65`, now `D67`):
a genuine, already-documented corpus rule in `SPEC_GUIDELINES.md` that
no `SpecBundle` ever surfaces to a generating model. Three fixes so
far have each been handled locally — in `generator`'s own prompt
(`D62`) or in the specific component's own requirement text (`D65`,
`D67`) — rather than by changing what `spec-bundle-assembler` includes
in every bundle. Worth naming as a pattern now that it has recurred
three times: a future decision could reasonably ask whether some core
subset of `SPEC_GUIDELINES.md` belongs in every bundle going forward,
rather than being rediscovered component-by-component. Not resolved
here — flagged, consistent with this corpus's own bias against
building generality before a second or third real need has already
shown up (which it now has).
