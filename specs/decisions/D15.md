# D15 — One file per addressable unit, not one file per document type

## Context

Arose from a blast-radius question: how should `impact-analyzer` tell an
`interface.md` *contract* change from a cosmetic edit without full
semantic diffing? On examination, the question generalized into a
better answer than it asked for.

## Decision

Replace the original four-flat-files component anatomy (`spec.md` /
`interface.md` / `acceptance.md` / `constraints.md`) with one file per
addressable unit:

```
components/<component>/
  component.md                 # root: frontmatter + Purpose/Scope/...
  requirements/R-<comp>-NNN.md  # one requirement per file
  interface/
    cli.md
    library.md
    data/<TypeName>.md         # one schema/type per file
  acceptance/AC-<comp>-NNN.md   # one criterion per file
  constraints.md                 # stays one flat file
```

Frontmatter lives only on `component.md`; every unit file carries none —
its filename is its identity. `constraints.md` stays flat deliberately
(nothing in the corpus addresses one constraint by id). Golden scenarios
stay inline per product-capability file, and `specs/vars/` stays one
file per variable — neither had a splitting reason.

## Consequences

Content hashing for blast-radius/cache-key purposes becomes exact
(file-level) rather than approximated by parsing block boundaries inside
a shared file. `spec-linter`'s block-boundary regex parsing — which had
already caused one real bug during its own bootstrap (the RFC-2119 check
missing multi-line continuations) — is replaced by directory listing,
which can't have that class of bug by construction.
`spec-bundle-assembler` gained a human-readable flattened-view mode for
anything that still wants to read a component as one document.

This was a genuine redesign, not a refinement: it touched every
component's file layout, `spec-linter`'s real implementation and test
suite, and every component referencing old file names directly.

See `SPEC_GUIDELINES.md` §1–§5 and `notes/initial-ideas.md`'s own D15
entry for the full discussion.
