# D146 — exemption_changes entry shape was the third undocumented ReviewPacket sub-shape

## Context

Thirteenth `review-packet-builder` retry (after `D145`'s CLI
criterion and `AC-PACKET-012`'s `argv` fix): 11 of 12 pass,
`mutation_score=1.0`. The one remaining failure, `AC-PACKET-007`, now
exercises exactly the real two-commit sealed-change transition its
own Gherkin asks for — the candidate correctly detects the change, but
appends the raw diffed file path (`specs/components/foo/component.md`)
to `exemption_changes.sealed`, not the component id
(`comp-foo`) the test (and `R-PACKET-007`'s own "includes that
component" wording) expects. `interface/data/ReviewPacket.md` showed
`"exemption_changes": { "sealed": [], "pinned_overrides": [] }` with
no worked example of either array's own entry shape — the third time
this exact gap has surfaced for this component (`residual_risk`,
`compliance_flags.license_scan`/`secret_scan` were the first two,
both already fixed this session).

## Decision

`ReviewPacket.md` amended with a worked `"sealed": ["comp-foo"]`
example and explicit prose: entries are bare component ids, matching
`regenerated_components`'s own shape, never the file path the change
was detected in. `review-packet-builder` is retried next.
