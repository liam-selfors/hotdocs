# D21 — No custom retry/timeout logic in `generator`; re-running a blocked merge is the recovery mechanism, for free

## Context

Resolved `generator`'s model-API retry/timeout policy, which grew into
something smaller than originally scoped once two observations landed:
a well-behaved model SDK already has its own bounded timeout and will
eventually error on its own — `generator` doesn't need to reinvent
that, just not disable it — and `generator` never caches a failed call
(`R-GEN-006` writes only on success), so re-running a merge after *any*
failure is already a correct, free retry: components that already
succeeded are a cache hit, only the failed one gets a fresh attempt.

## Decision

- **`generator` (`R-GEN-011`):** no internal retry-with-backoff, no
  invented timeout duration. A single call either succeeds or fails
  within the SDK's own bound; any failure is `model_call_error`
  (`R-GEN-008`) exactly once. Explicitly **not** the same mechanism as
  `D17`'s best-of-k retry — that retries *generation* with a new seed
  after *code* fails verification; this is about infrastructure
  failures before any code exists to verify.
- **`merge-orchestrator` (`R-MERGE-017`/`018`):** every impacted
  component MUST be processed to completion before block status is
  evaluated — no fail-fast short-circuiting. This also resolved the
  separate, previously-open parallelization-mechanism question: the
  requirement constrains the *outcome* (every component attempted),
  not whether that happens sequentially or concurrently.

## Consequences

Re-running a blocked merge is the designed, complete recovery path
(`R-MERGE-018`) — the same "rollback is a cache hit, not a dedicated
incident feature" posture D11 established for reverts, applied to
moving a partially-failed merge forward.

See `specs/components/generator/requirements/R-GEN-011.md` and
`specs/components/merge-orchestrator/requirements/R-MERGE-017.md`/
`R-MERGE-018.md` for the current, authoritative rules.
