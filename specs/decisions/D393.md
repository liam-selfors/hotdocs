# D393 — Requirement ids reach the blast radius; the driver reads unseen elements; dependencies are used only through their interface

## Context

Three follow-ups from the `D390` round:

- `hotdocs impact --changed R-DOCS-008` gave an empty blast radius, so a
  review packet built for a requirement change listed no regenerated
  component; only component ids reached `impact-analyzer`'s rules.
- The browser driver's reads waited for a visible element, and a
  vertical or horizontal SVG line has an empty box, so no test could
  read a `depends_on` edge's class or colour (`AC-DOCS-015` needed
  diagonal edges).
- `review-packet-builder` called `provenance-tracker`'s `to_json`, seen
  in its code but not its interface; the dependency-surface check asks
  only whether a name exists, so the slip reached the criteria.

## Decision

- `R-IMPACT-012`: an `R-` or `AC-` id resolves to the component holding
  its file, which is then a `direct` change.
- `test-driver-browser.md`: `attribute` and `style` wait for one match
  attached to the page, visible or not.
- `R-SURF-002`: a name used on a dependency must also occur in that
  dependency's own `interface/` files (`dependency_undocumented`), never
  counting its `Implements:` documents, whose names are conventions each
  implementer carries itself; an alias is scoped to the function that
  assigns it. `tools/bootstrap_component.py`'s gate applies the same
  rule.

## Consequences

Regenerated: `impact-analyzer`, `driver-browser`, `surface-checker`;
their dependents re-verify (`D379`). No committed component uses an
undocumented dependency name today.
