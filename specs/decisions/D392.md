# D392 — CS-COMPLIANCE-001's retry is a retry inside one generate run

## Context

`CS-COMPLIANCE-001` said a licensed-code finding "appears in the review
packet even if a subsequent retry resolves it". The scenario test written
before `D390` read the retry as `generation-loop`'s: an attempt fails
verification, the loop retries, the scan blocks the final candidate, and
the packet shows it. The test written by `hotdocs verify --model` after
`D390` read it as a second `generate` run whose clean scan should still
leave the first run's finding in the packet. Nothing keeps scan results
across runs: a run's manifest holds its own `license_scan`, attempt
records hold no scan (`AttemptRecord`), and `R-PACKET-005` lists a
component's flag only while its scan is blocked. That test could never
pass.

## Decision

The scenario states the first reading: the finding is in the packet built
after the blocking run, also when that run's loop retried an earlier
failed attempt; a later run whose scan is clean replaces the manifest's
`license_scan`, and its packet shows the clean result.

The scenario's tracker stand-in also reports each component's
`license_scan` as its manifest records it: the packet reads the flag only
from `VerifyReport.components` (`R-PACKET-005`), and the first test
written for the clarified text returned entries without it.

## Consequences

Only `P-COMPLIANCE-GATE`'s scenario test is authored again. Keeping a
resolved finding visible across separate runs would need a scan history
in the attempt records and a packet section for it; that is a product
change of its own, not made here.
