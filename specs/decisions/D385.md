# D385 — The test author's own probe knows the component's test drivers

## Context

`test-author` probes every test it writes before returning it
(`R-AUTHOR-020`), with the bundle and module name only. Since `D373`
the probe stubs a test driver's fixture only when told the fixture's
name; told none, it treats a test using `browser` as using an unknown
fixture, a test bug. In the `D373`–`D384` wave every test of
`docs-site-renderer`'s browser criterion `AC-DOCS-012` was rejected
this way, after two repairs each.

## Decision

`R-AUTHOR-020`'s probe call passes `drivers`: the name in each
`## Test driver: <name>` heading `spec-bundle-assembler` puts in the
bundle's `testing` (`R-ASSEMBLE-017`). A driver's `FIXTURE` equals its
`NAME`, so the name is the fixture's; `comp-driver-browser`'s interface
states both as `"browser"`, and every driver added later keeps them
equal. The rule lives here and in `R-AUTHOR-020`, not in
`specs/architecture/test-drivers.md`: that document is in the bundles of
`run-environment` and `test-probe`, which never read it, and a line
there would regenerate the verifier stack for nothing.

## Consequences

Tests of components that declare a driver pass the test author's own
check. `test-supply`, which knows the adapters, already passed the
fixture names (`R-SUPPLY-003`). Regenerated: `test-author` and the
components its code hash reaches.
