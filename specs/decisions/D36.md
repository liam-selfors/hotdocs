# D36 — Rename `golden-scenario-verifier` to `capability-scenario-verifier`; per-scenario granularity and `rationale` field

## Context

Analysis of `notes/backlog.md`'s flagged gap ("`GoldenScenarioReport` has
no `rationale` field") confirmed the user's instinct that the fix is an
instance of a shared `{result, rationale}` pattern already present in
`Finding`, `VerificationReport.criteria[]`, and `CompletenessReport` —
and that `SPEC_GUIDELINES.md` §5 already states the governing rule
("an `llm-judge` criterion MUST emit structured rationale alongside its
verdict"); `GoldenScenarioReport` simply never honored it.

The same analysis surfaced a second, deeper gap: `GoldenScenarioReport`
reported one aggregate verdict per `P-id`, unlike `VerificationReport`'s
per-criterion granularity one level down. Latent today — every product
capability has exactly one golden scenario — but a real design flaw the
moment any capability gains a second one, since a single failing
scenario among several would be indistinguishable from all of them
failing.

Separately, the user challenged the name itself: "golden scenario"
communicates nothing about what the thing actually is or where it sits
in the corpus's scope hierarchy.

## Decision

**Rename**, corpus-wide, live documents only (decision records and
`notes/initial-ideas.md`'s historical brainstorm stay untouched, per
standing convention):

- Component: `golden-scenario-verifier` → `capability-scenario-verifier`
- Id prefix: `GS-<cap>-NNN` → `CS-<cap>-NNN`
- Requirements: `R-GOLDEN-001`/`002` → `R-SCENARIO-001`/`002`
- Acceptance: `AC-GOLDEN-001`/`002` → `AC-SCENARIO-001`/`002`
- Type: `GoldenScenarioReport` → `CapabilityScenarioReport`
- Library function: `run_golden_scenarios` → `run_capability_scenarios`
- `MergeResult` field: `golden_scenarios` → `capability_scenarios`
- DuckDB `nodes` node kind: `golden_scenario` → `capability_scenario`
- Product doc headings: `## Golden scenario` → `## Capability scenario`

Rationale for the new name: it mirrors "Acceptance Criterion" (`AC-id`,
component-scoped) exactly one level up — "Capability Scenario" (`CS-id`,
capability-scoped) — which communicates scope and purpose where
"golden" communicated neither.

**Structural fix**, folded into the same change since both touch
`CapabilityScenarioReport`'s shape: it now reports one entry **per
scenario** (`scenarios: [{id, kind, result, rationale?}]`), each
carrying an optional `rationale` present only for `llm-judge`-kind
scenarios that ran — plus an `overall` field aggregating them the same
way `VerificationReport.overall` aggregates `criteria` (a `skipped`
`llm-judge` scenario alone doesn't fail `overall`, per the existing
`R-VERIFY-005` convention). New `AC-SCENARIO-003` tests this directly.

The other three `{result, rationale}` sites found during analysis
(`VerificationReport`, `Finding`, `CompletenessReport`) were already
correct — no change needed there. Deliberately **not** unified into one
shared container type: each has its own shape driven by its own
consumers (per-criterion vs. per-capability vs. per-lint-finding vs.
per-redundant-pair), and forcing a single type would serve none of them
well.

## Consequences

`notes/backlog.md`'s flagged gap is closed. A failing or skipped
judgment-based capability scenario's *why* is now structurally
recorded, and a capability with multiple scenarios gets a truthful,
per-scenario result instead of one verdict that silently conflates them.

Historical narrative in `pipeline-decomposition.md` and
`graph-query-engine.md` keeps the old name parenthetically where useful
("named `golden-scenario-verifier` at the time; renamed by `D36`") —
consistent with the convention `D34`/`D35` already established for
describing history accurately without editing frozen records.

See `specs/components/capability-scenario-verifier/` for the current,
authoritative spec.
